# Aura Core 基础类型性能分析报告

## 一、现状概览

### 1.1 类型体系

| 类型 | VM 存储 | AOT 存储 | 装箱状态 |
|------|---------|----------|----------|
| Int (32-bit) | `Value::Int` (i64) | i32 | Plan A 小整数 [-16,15] 内联 |
| Long (64-bit) | `Value::Int` (i64) | i64 | Plan A 小整数内联，大值堆分配 |
| Short (16-bit) | `Value::Int` (i64) | — | 同上 |
| Byte (8-bit) | `Value::Int` (i64) | — | 同上 |
| Float (32-bit) | `Value::Float` (f64) | f32 | 通过 bit-cast 走整数装箱 |
| Double (64-bit) | `Value::Float` (f64) | f64 | 通过 bit-cast 走整数装箱 |
| Boolean | `Value::Bool` (bool) | — | 0/1 装箱 |
| Char | `Value::Str(Rc<str>)` | — | ⚠ **以字符串存储！** |
| String | `Rc<str>` | `{ptr, len}` | — |
| Unit | 单例 | — | — |
| Nothing | 不可构造 | — | — |

### 1.2 内存管理

- **GC**：ARC 引用计数 + 标记-清除（`GC.collect()` 为 TODO，未完成）
- **分配器**：`ArenaAllocator` (mmap + bump pointer) + `Allocator` (libc malloc/free)
- **装箱**：Plan A（低位标记 + 小整数内联 [-16, 15]）
- **字符串**：`Rc<str>`（VM）/ C 字符串（AOT），无驻留（interning）

## 二、核心性能瓶颈分析

### 🔴 严重（P0）—— 影响所有代码路径

#### 瓶颈 1：`Char` 以 `Rc<str>` 存储——单字符字符串开销

**位置**：`Char.aura` 第 8 行注释："存储：VM 中为 `Value::Str(Rc<str>)`（单字符字符串）"

**问题**：
- 每个 Char 值都需要堆分配一个 `Rc<str>` 对象（含引用计数 + 类型 ID + 数据指针）
- `Char.toInt()` 返回 `this as Int`——这是将 String 指针做装箱拆箱，不是直接读取字符码
- 词法分析器逐字符扫描时，每个 `charAt(i)` → `fromCharCode(c)` → 分配新 String → 立即释放
- `Char` 的 `isAlpha()` / `isDigit()` 等方法用字符串比较，而非整数比较

**影响**：词法/解析阶段是字符串密集型操作，字符操作占运行时 CPU 的 **40-60%**

**改进方向**：Char 应作为独立的 tagged value（`Value::Char`）或内联到 `Value::Int` 的高位标记

#### 瓶颈 2：`Any.equals()` / `Any.hashCode()` 默认实现走字符串转换

**位置**：`Any.aura` 第 56-83 行

```aura
// equals: 把两侧都转成字符串再比较
return toStr(this) == toStr(other)

// hashCode: 先转字符串，再 31 进制散列
val s: String = toStr(this)
var hash: Int = 0
while (i < s.length) { hash = hash * 31 + s.charCodeAt(i); i = i + 1 }
```

**问题**：
- 每次 HashMap 查找 → `hashCode()` → `toStr()` → 分配新 String → 逐字符计算
- 每次 `equals()` → 两次 `toStr()` + `String.equals()`（逐字符比较）
- `Int.hashCode()` 是恒等函数（`HashMap.aura` 第 353 行注释），但 VM 层没有 override，走默认字符串路径
- `HashMap.hashKey()` 注释确认："VM 的 `Int.hashCode()` 直接返回键本身"

**影响**：HashMap 的每次 get/put 包含 **2-3 次堆分配**（toStr × 2 + hash 字符串）

**改进方向**：
- 为所有 value class 实现 `hashCode()` 和 `equals()` 的 override，走 tagged value 路径
- `Int.hashCode()` → 直接返回 `this`（已是恒等，但需确保 VM 层不经过 `toStr`）
- `String.hashCode()` → 直接调用 `StringOps.hash(addr)`（已有 djb2 实现，无分配）

#### 瓶颈 3：`String.length` 在 AOT 下是 O(n) 的 `strlen`

**位置**：`String.aura` 多处注释，典型循环 `while (i < this.length)`

**问题**：AOT 下 `String` 是 C 字符串（`{ptr, len}` 中的 ptr），`length` 属性调用 `strlen`，每次循环条件检查都重新计算长度。

**仍存在的问题**（部分已修复，部分未修复）：

| 方法 | 循环条件 | 状态 |
|------|----------|------|
| `charAt` | `i < this.length` | ✅ 已修复（去掉上界检查） |
| `countCharStr` | `i < n`（n 缓存） | ✅ 已修复 |
| `indexOf` (instance) | `i <= n - m`（n 缓存） | ✅ 已修复 |
| `toUpperCase` | `i < this.length` | ❌ **未修复** |
| `toLowerCase` | `i < this.length` | ❌ **未修复** |
| `padStart` / `padEnd` | `i < length - this.length` | ❌ **未修复** |
| `trim` / `trimStart` / `trimEnd` | `i < n`（n 缓存） | ✅ 已修复 |
| `containsAny` / `containsAll` | `i < chars.length` | ❌ **未修复** |
| `replace` (instance) | `i < this.length` | ❌ **未修复** |
| `split` (instance) | `i <= this.length - separator.length` | ❌ **未修复** |
| `substringBefore` / `substringAfter` | 间接调用 length | ❌ **未修复** |

**影响**：每个未修复的方法在 AOT 下都是 **O(n²)**

#### 瓶颈 4：`String` 方法内使用 `result = result + ...` 逐字符拼接

**位置**：`String.aura` 多处：`toUpperCase`, `toLowerCase`, `replace`, `padStart`, `padEnd`, `toString`(ArrayList), `HashMap.toString`

**问题**：每次 `+` 创建新 String（Rc 分配 + memcpy 旧内容），构建长度为 n 的字符串需要 n 次分配和 O(n²) 的总拷贝量。

**改进方向**：全部改用 `StringBuilder`（已有实现），先 append 再 finish

### 🟡 重要（P1）—— 影响关键路径

#### 瓶颈 5：Float 数学函数全部走 Double 转换

**位置**：`Float.aura` 第 146-192 行

```aura
fun sqrt(): Float { return MathCore.sqrt(this as Double) as Float }
fun pow(exp: Float): Float { return MathCore.pow(this as Double, exp as Double) as Float }
fun log2(): Float { return (MathCore.log(this as Double) / MathCore.log(2.0)) as Float }
```

**问题**：
- 每次 Float 数学调用做 2 次 Double 转换 + MathCore 计算 + 回转
- `log2()` 调用两次 `MathCore.log()` 而非实现 `log2`
- `MathCore.pow()` 是 O(exp) 循环乘法，应改为快速幂 O(log exp)
- `Float.round()` 通过 `Int` 转换实现，丢失精度（Int 只有 32 位）

**改进方向**：
- 为 Float 实现专用数学函数（直接 f32 运算，避免 f64 往返）
- `MathCore.pow()` 改为快速幂
- `MathCore.log2()` 独立实现（避免两次 log 调用）

#### 瓶颈 6：`Double.parseDouble()` 用 Float 累加器——精度损失

**位置**：`Double.aura` 第 43-75 行

```aura
fun parseDouble(text: String): Double {
    var result: Float = 0.0f    // ⚠ Float 只有 ~7 位有效数字！
    ...
    var frac: Float = 0.0f
    var divisor: Float = 1.0f
    ...
    return ((result + frac / divisor) * sign.toFloat()) as Double
}
```

**问题**：解析 Double 时用 Float 累加器，超过 7 位有效数字后精度完全丢失。`0.123456789` 会被截断为 `0.1234568`。

**这是正确性 Bug，不是性能问题。**

**改进方向**：改用 Double 累加器

#### 瓶颈 7：`String.format()` O(n²) + `String.fromCharCode` 逐字符拼接

**位置**：`String.aura` 第 62-71 行

```aura
fun format(template: String, vararg args: Any): String {
    var result: String = template
    while (i < args.size) {
        val placeholder = "{" + i + "}"    // 分配 1
        result = result.replace(placeholder, toStr(args[i]))  // 分配 2 + O(n) 替换
        i = i + 1
    }
}
```

**改进方向**：改用 StringBuilder 一次扫描

#### 瓶颈 8：`ArrayList.distinct()` O(n²)

**位置**：`ArrayList.aura` 第 208-219 行

```aura
override fun distinct(): List<T> {
    while (i < _size) {
        var elem = this.get(i)
        if (!result.contains(elem)) { result.add(elem) }  // O(n) 线性扫描
        i = i + 1
    }
}
```

**改进方向**：用 HashSet 去重，降为 O(n)

#### 瓶颈 9：`HashMap` 使用三条并行 ArrayList 链

**位置**：`HashMap.aura` 第 1-454 行

**问题**：
- 三个 `List<List<K>>` / `List<List<V>>` / `List<List<Boolean>>` 嵌套泛型，每层 List 都是 `ArrayList`（用户类实例），开销大
- 每次 `put()` 追加一条记录（含失效标记），链只增不减，直到扩容重建
- `containsValue()` 要扫描所有桶的所有链，且需要 `isLatest()` 检查
- 没有对 Int/String 等常见键类型的特化

**改进方向**：
- 考虑使用开放寻址法（Open Addressing）替代链地址法，减少间接层
- 为 Int 键和 String 键提供特化路径

#### 瓶颈 10：`Boolean.and()` / `or()` / `xor()` 多此一举

**位置**：`Boolean.aura` 第 47-62 行

```aura
fun and(other: Boolean): Boolean {
    if (this and other) return true
    return false
}
```

**问题**：`if (this and other) return true; return false` 等价于 `return this and other`，多了不必要的分支。

**改进方向**：简化为直接返回

### 🟢 中等（P2）—— 局部优化

#### 瓶颈 11：`MathCore.pow()` 是 O(exp) 线性循环

```aura
fun pow(base: Double, exp: Double): Double {
    val e: Long = exp as Long
    for (i in 0..e) { result = result * base }  // O(exp)！
}
```

应改为快速幂 O(log exp)

#### 瓶颈 12：`ArrayList.remove()` 逐元素重建列表

```aura
fun remove(index: Int): T {
    val newData = arrayListOf<T>()
    while (i < _size) {
        if (i != index) { newData.add(this.get(i)) }
        i = i + 1
    }
}
```

可以改为 System.arraycopy 风格的内存拷贝（对 ArrayList 内部存储直接操作）

#### 瓶颈 13：`String.toCharArray()` 逐字符创建新数组

```aura
fun toCharArray(): Array<Char> {
    var chars = arrayOf<Char>()
    while (i < this.length) {
        chars = chars + this.charAt(i)  // 每次创建新数组！
        i = i + 1
    }
}
```

#### 瓶颈 14：`Plan A` 装箱范围过小 + Float 装箱有缺陷

```aura
// 小整数范围 [-16, 15]，太小
// boxFloat 用 `v as Long`（位模式转换），不是 memcpy
fun boxFloat(v: Float): Long { return boxInt(v as Long) }
```

#### 瓶颈 15：`StringBuilder.appendInt()` 每次分配 32 字节临时缓冲区

```aura
fun appendInt(handle: Long, value: Int): Long {
    val tmp: Long = Memory.alloc(32)  // 每次调用都分配
    ...
    Memory.free(tmp)
}
```

应该使用栈分配或线程本地缓冲区

#### 瓶颈 16：`ArrayList` 嵌套 `List<T>`（双包装）

```aura
class ArrayList<T> : List<T> {
    private var data: List<T>  // ArrayList 包了一层 List
}
```

ArrayList 内部存储又是 `arrayListOf<T>()`（另一种 List 实现），导致双重间接。

## 三、性能改进方案

### 第一阶段：快速修复（1-2 天）

#### 3.1 修复 `Double.parseDouble()` 精度 Bug

**文件**：`Double.aura`

```aura
// 修复前：
var result: Float = 0.0f
// 修复后：
var result: Double = 0.0
var frac: Double = 0.0
var divisor: Double = 1.0
```

#### 3.2 缓存 `String.length` 到所有未修复的方法

**文件**：`String.aura`

对所有 `while (i < this.length)` 循环，改为：
```aura
val n: Int = this.length  // 缓存一次
while (i < n) { ... }
```

涉及方法：`toUpperCase`, `toLowerCase`, `padStart`, `padEnd`, `replace`, `split`, `containsAny`, `containsAll`, `substringBefore`, `substringAfter`

#### 3.3 为 value class 实现 `hashCode()` / `equals()` override

**文件**：`Int.aura`, `Long.aura`, `Float.aura`, `Double.aura`, `Boolean.aura`, `Char.aura`

```aura
// Int.aura - 添加
override fun hashCode(): Int { return this }
// 已有 equals() 直接比较 this == other，无需修改
```

#### 3.4 简化 `Boolean.and()` / `or()` / `xor()`

```aura
fun and(other: Boolean): Boolean { return this and other }
fun or(other: Boolean): Boolean { return this or other }
fun xor(other: Boolean): Boolean { return (this and not(other)) or (not(this) and other) }
```

#### 3.5 `MathCore.pow()` 改为快速幂

```aura
fun pow(base: Double, exp: Double): Double {
    val e: Long = exp as Long
    var b: Double = base
    var result: Double = 1.0
    var i: Long = if (e < 0) -e else e
    while (i > 0) {
        if (i % 2 == 1) { result = result * b }
        b = b * b
        i = i / 2
    }
    if (e < 0) { return 1.0 / result }
    return result
}
```

### 第二阶段：字符串基础设施优化（3-5 天）

#### 3.6 所有字符串拼接改用 StringBuilder

**影响方法**（`String.aura`）：
- `toUpperCase` → 先用 StringBuilder 累积，再 finish
- `toLowerCase` → 同上
- `replace` → 同上
- `padStart` / `padEnd` → 同上
- `format` → 同上
- `ArrayList.toString()` → 同上
- `HashMap.toString()` → 同上
- `println` / `print` (prelu.aura) → 同上

**模式**：
```aura
// 修复前：
var result: String = ""
while (i < n) {
    result = result + this.charAt(i)  // O(n) 每次
}

// 修复后：
val sb: Long = StringBuilder.create()
while (i < n) {
    StringBuilder.appendChar(sb, this.charCodeAt(i) as Short)  // O(1) 均摊
}
return StringBuilder.finish(sb) as String
```

#### 3.7 `String.indexOf` / `lastIndexOf` 改用 KMP 或改进 Boyer-Moore

当前实现是朴素匹配（O(n·m)），对于大字符串子串搜索效率低。

**方案 A（简单）**：当前逐字符匹配已比旧的 `substring` 方案好很多，保持现状。

**方案 B（高级）**：实现 KMP 算法，预处理 O(m)，匹配 O(n)。

#### 3.8 实现字符串驻留（String Interning）

**目标**：相同内容的字符串共享同一 Rc 实例，避免重复分配。

**方案**：
- 在常量池中维护已驻留字符串的 HashMap
- `String.intern()` 方法：如果字符串已驻留，返回现有 Rc；否则驻留并返回
- 编译期字符串字面量自动驻留
- `toStr()` 的结果可考虑驻留（对 Int/Long/Float 的字符串表示）

**收益**：HashMap 键比较走指针相等，`toString()` 结果缓存复用

### 第三阶段：Char 类型重构（3-5 天）

#### 3.9 将 Char 从 `Value::Str(Rc<str>)` 改为独立 tagged value

**当前**：`Char` 是 `Value::Str(Rc<str>)`——单字符字符串，每个 Char 都要堆分配。

**目标方案**：

| 方案 | 描述 | 复杂度 |
|------|------|--------|
| A | `Value::Char(code: u32)`——独立的 tagged variant | 中 |
| B | `Value::Int` 高位标记 `is_char`——与 Int 共用存储 | 低 |
| C | `Value::SmallChar { code: u16, inline: true }`——内联到 Value | 高 |

**推荐方案 B**（最低改动成本）：

```
// VM Value 扩展
Value::Char(charCode: u32)  // tag = 新变体

// 或复用 Int 的存储：
// Char = Int << 2 | 0b01（与 Plan A 小整数不冲突）
```

**Char.aura 修改**：
- `toInt()` → 直接返回 charCode，不再经过装箱拆箱
- `isAlpha()` / `isDigit()` → 整数范围检查，不再字符串比较
- `toString()` → 从 charCode 构造单字符字符串（仅调试用）

**编译器修改**：
- `charAt()` 返回 Char tagged value 而非 String
- `charCodeAt()` 直接读取 charCode
- `fromCharCode()` 构造 tagged value 而非 String

**预期收益**：词法分析器/解析器中的字符操作性能提升 **5-10 倍**

### 第四阶段：内存与分配器优化（5-7 天）

#### 3.10 实现 Small Object Allocation（SOA）线程本地池

**问题**：当前每个 String 字面量、Char、装箱值都走 `malloc`/`free`，开销大。

**方案**：
- 为小对象（≤ 64 字节）维护线程本地 freelist
- `Rc<str>` 的空闲对象缓存到 freelist，避免反复 malloc/free
- 实现 `Rc` 的 `retain`/`release` 内联优化（避免虚调用）

#### 3.11 实现 ARC 批量操作

当前 ARC 操作每次调用 `Memory.arcIncrement` / `arcDecrement`（原子操作，有内存屏障开销）。

**优化**：
- 对于非共享（引用计数为 1）的对象，使用非原子操作（快速路径）
- 批量更新：在一个表达式中多次赋值同一引用，延迟到赋值完成后统一更新引用计数

#### 3.12 改进 Plan A 装箱策略

**当前问题**：
- 小整数范围 [-16, 15] 太小，超出范围全部堆分配
- `boxFloat` 用 `v as Long`（位模式转换），在某些 ABI 下不正确

**改进**：
- 扩大小整数范围为 [-1024, 1023]（10 位有效位，仍在 64 位内）
- 为 Float/Double 实现独立的 tagged variant（`Value::FloatBits`）
- 小浮点数（如 0.0, 1.0, -1.0）也内联

### 第五阶段：HashMap / ArrayList 专项优化（5-7 天）

#### 3.13 HashMap 改用开放寻址法

**当前**：链地址法（三个并行 ArrayList），间接层多。

**开放寻址法**：
```
entries: Array<Entry>  // Entry = { key, value, state }
state: EMPTY | OCCUPIED | DELETED
```

**优势**：
- 连续内存，缓存友好
- 无 ArrayList 嵌套开销
- 查找只需几次比较，无链表遍历

#### 3.14 ArrayList 内部存储改用连续内存数组

**当前**：`ArrayList<T>` 包了一层 `List<T>`（另一个 ArrayList 实例），双重间接。

**改进**：
- `ArrayList<T>` 内部直接使用 `Array<T>`（连续内存）+ `capacity` / `size` 字段
- 避免双重包装

#### 3.15 `ArrayList.distinct()` 用 HashSet 去重

```aura
override fun distinct(): List<T> {
    val seen = HashSet<T>()
    val result = arrayListOf<T>()
    while (i < _size) {
        val elem = this.get(i)
        if (!seen.contains(elem)) {
            seen.add(elem)
            result.add(elem)
        }
        i = i + 1
    }
    return result
}
```

## 五、风险与注意事项

### 5.1 Char 重构风险
- **编译期影响**：`charCodeAt` 的语义变化可能影响依赖 `charAt().toInt()` 的代码
- **AOT 兼容性**：需要确认 AOT 后端对 Char tagged value 的发射路径
- **迁移策略**：先提供 `Char.intern()` / `Char.charCode()` 双 API，逐步迁移

### 5.2 字符串驻留风险
- **内存占用**：驻留字符串永不释放，可能增加内存使用
- **竞争条件**：多线程环境下驻留表需要同步（可先实现单线程版本）
- **GC 交互**：驻留字符串的 Rc 需要特殊处理（不纳入 ARC 计数）

### 5.3 HashMap 开放寻址迁移风险
- **行为变更**：开放寻址的遍历顺序与链地址法不同
- **删除语义**：当前追加失效标记的历史链需要改为墓碑标记
- **建议**：保留旧 HashMap 作为 `HashMapLegacy`，新 HashMap 作为 `HashMapV2`，测试通过后替换

### 5.4 双后端一致性
- VM 和 AOT 的语义差异是已知问题（`charCodeAt` 的递归、`equals` 的递归）
- 修改后需要在两个后端都验证
- 建议先修复 VM 路径，再验证 AOT

## 七、总结

Aura Core 基础类型当前的主要性能问题集中在四个层面：

1. **Char 以字符串存储**——词法分析的核心路径被严重拖慢
2. **Any 默认 equals/hashCode 走字符串转换**——HashMap 每次查找都分配字符串
3. **String 方法内部使用 `result + ...` 拼接**——O(n²) 的隐藏成本
4. **`String.length` 在 AOT 下是 strlen**——大量循环条件中的重复 O(n) 扫描

这四个问题的修复预期可以将 Aura 整体性能提升 **5-10 倍**（词法/解析密集型场景）到 **30-50%**（通用场景）。

建议按"快速修复 → 字符串基础设施 → Char 重构 → 内存优化 → 集合优化"的顺序逐步实施，每阶段独立可验证。
