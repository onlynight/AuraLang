# Aura 自举编译器「脱 Rust」现状分析

> **文档定位**：现状评估（Phase 0）
> **前置文档**：`02-纯Aura化改造方案.md`（详细改造路线）
> **日期**：2026-09-13
> **范围**：除 `compiler/src/bootstrap/`（最小引导层，明确保留）外，Aura 自举编译器是否已可完全脱离 Rust 编译器？

---

## 一、总体结论

| 问题 | 结论 |
|------|------|
| Aura 编译器源码是否已用 Aura 写完？ | ✅ 写完（`aura/compiler/aura/lang/compiler/` 65 个 `.aura` 文件，Phase 0–9 全部标 ✅） |
| Aura 编译器能否编译**单文件** Aura 程序并 AOT 出 exe？ | ✅ 可以（`Main.aura` 走 `aotBuildExeSource`；`build/bin/aura-compiler-native.exe` 已产出，能对 1 行 hello.aura 生成正确 exe） |
| Aura 编译器能否**编译自身**（Main.aura + 48 个依赖模块）为原生 exe？ | ❌ **不能**（Phase 6.5.10 仍为 🚧；见 `aura/compiler/README.md:315-399`） |
| 用户日常 `aura run/build --aot` 是否依赖 Rust？ | ✅ 完全依赖（`cli/main.rs` + `compiler/` 由 `cargo build` 生成 `aura.exe`） |
| `aura.exe` 启动后能否完全脱离 Rust 运行？ | ❌ 否。Aura 侧 `Process.run`/`FileSystem.writeText` 等 std 函数仍是 Rust native（`compiler/src/std/std_process.rs` 等），Aura 编译器在 VM 上跑时每次 `llc`/`clang` 调用都经过 Rust 侧 |

**一句话**：Aura 编译器代码写完、单文件自举能力已具备，但**自举闭环（编译自身→原生 exe→再编译自身）尚未跑通**，且**运行时 std native 层仍是 Rust**——两处都意味着「脱 Rust」尚未成立。

---

## 二、当前仍存在的 Rust 依赖（除 bootstrap 外）

### 2.1 构建期依赖（每次发版都逃不掉）

| 依赖 | 位置 | 说明 |
|------|------|------|
| Rust 1.75+ / cargo | `Cargo.toml`、`compiler/Cargo.toml` | 编译 `compiler`、`cli`、`loom` 三个 crate → 产出 `aura.exe` / `aura-lsp` / `aura-debug` / `loom` |
| `build.rs` (compiler) | `compiler/build.rs` | 用 `toml` crate 解析根 `Cargo.toml` 的 `llvm-home` 等配置 |
| Rust crate 生态 | `compiler/Cargo.toml` | `cranelift`、`serde/serde_json`、`chrono`、`rand`、`regex`、`base64`、`hex`、`libc`、`tar`、`zstd`、`sha2`、`hmac`、`toml`、`thiserror`、`object`、`ed25519-dalek`、`rand_core` |
| LLVM 23.1.0 (llc/clang/lld-link) | 外部工具 | AOT 后端必需（Aura 与 Rust 两侧都用文本 IR + 外部子进程方案） |
| C 编译器（cl.exe / gcc） | 外部工具 | 编译 `compiler/src/std/cffi/aura_std_cffi.c`（AOT 运行库实现） |

### 2.2 运行时 Rust native 依赖（Aura 编译器运行时调用）

Aura 编译器代码虽然是 Aura，但它在 VM 上跑时调用的以下 std 函数**仍然是 Rust native**（`compiler/src/std/*.rs` 与 `aura_std_cffi.c`）：

| 函数 | Rust 源 | 用途 |
|------|---------|------|
| `Process.run` / `Process.arg` / `Process.argCount` / `Process.spawn` | `std_process.rs` | **AOT 后端调 llc/clang 的唯一入口**（`Aot.aura:299,333,344`） |
| `FileSystem.writeText` / `FileSystem.exists` | `std_fs.rs` | 落盘 IR / 检查文件（`Aot.aura:287`、`Main.aura:421`） |
| `IO.println` / `IO.readText` / `IO.readLine` | `std_io.rs` | 编译器诊断输出 |
| `Clock()` / `CString` / `ptrToInt` / `makeCallback` | `std_builtin.rs` | 性能计时、FFI |
| `Math.*` / `String.*` / `List.*` / `Map.*` / `Iterator.*` | `std_math.rs` / `std_string.rs` / `std_collections.rs` / `std_iter.rs` | 编译器大量使用（发射期 15k 节点、49876 行 IR） |
| `Actor` / `Channel` / `Coroutine` / `ThreadPool` | `std_concurrent.rs` | loom 构建系统 / 多进程 CLI |
| `JSON.stringify` / `JSON.parse` | `std_json.rs` | LSP、包格式、docgen |
| `Hash` / `SHA256` / `HMAC` / `Ed25519` | `signature.rs` / `signing.rs` | `.auz` 包签名 |
| `Tar` / `Zstd` | — | `.auz` / `.apkg` 容器 |
| `chrono` / `regex` / `base64` / `hex` | — | LSP / 文档 / URL |

**关键点**：这些函数注册在 `NativeRegistry`（`vm/native.rs`），VM 通过函数指针调用 Rust 代码。**只要 Aura 编译器跑在 VM 上，就绕不过 Rust。**

### 2.3 Aura 源码库与 Rust 运行时实现漂移

- `aura/core/aura/lang/std/*.aura`（38 个文件）——「文档/IDE 用源码」，**不参与运行时**
- `compiler/src/std/*.rs`（24 个文件）——**真正的运行时实现**
- `aura_std_cffi.c`——AOT 调用的 C 实现

三套并存，形成「上移只是文档」的双层漂移（见 `docs/完全Aura化技术方案-final.md:33-86`）。

### 2.4 尚无 Aura 等价实现的关键 Rust 模块

| Rust 模块 | 行数（粗估） | 状态 |
|-----------|--------------|------|
| `compiler/src/vm/interp.rs` + `heap.rs` + `value.rs` + `gc.rs` | ~5000 | 主 VM（Aura 侧 `vm/Vm.aura` 只是字符串字节码解释器，非生产 VM） |
| `compiler/src/vm/jit.rs` + `jit_opt.rs` + `abi.rs` + `aot_runtime.rs` | ~2500 | Cranelift JIT（Aura 侧 `jit/` 仅 IR 文本 + 引导层） |
| `compiler/src/codegen/aot/emit.rs`（Rust AOT 后端） | ~5000 | **Aura 自举当前用的就是这个**——`aura-compiler-native.exe` 就是 Rust AOT 编译 Main.aura 出来的 |
| `compiler/src/lsp.rs` | 39KB | LSP 服务（Aura 侧无对应物） |
| `compiler/src/docgen.rs` | 70KB | 文档生成 |
| `compiler/src/package.rs` | 65KB | 包管理 |
| `compiler/src/linker.rs` / `signature.rs` / `signing.rs` | ~25KB | 模块链接 / 签名 |
| `compiler/src/bootstrap/*` | ~4000 | **明确保留**（最小引导层，允许保留 Rust） |
| `loom/src/**`（50 文件） | ~15000 | 构建系统（全 Rust，无 Aura 对应） |
| `cli/src/main.rs`（65KB）+ `lsp_main.rs` + `debugger_main.rs` + `debugger.rs` | ~90KB | CLI / 调试器 |

### 2.5 阻塞 Aura 自举的两个硬缺陷（Rust AOT 后端）

来自 `aura/compiler/README.md:393-408`：

1. **类类型按值传递**（`%struct.X` 拷贝）而非按引用（`i8*`）——Aura 面向对象语义硬要求。最小复现 `build/probe7/identity.aura`：VM 返回 1、AOT 返回 0。
2. **String 表示不统一**：AOT 把 `String` 映射为 `{i8*, i64}`，但 String 方法（`contains`/`startsWith`/`split`…）按 `i8*` 调用点实现——在「重度使用字符串方法」的 Aura 编译器上**静默错误**。

这两项都位于 `compiler/src/codegen/aot/emit.rs`（Rust 侧），直接阻塞「Aura 编译器 AOT 自身」。

### 2.6 Aura 侧编译器自身的未完成项

来自 `aura/compiler/README.md:407-411`（Phase 6.5 尚未完成）：

| # | 未完成项 | 影响 |
|---|----------|------|
| 6.5.10 | Aura 编译器自身 AOT 出 exe | 自举闭环不成立 |
| 6.5.13 | AOT `try/catch` | 需 `setjmp/longjmp` 桥（平台 ABI） |
| 6.5.14 | AOT 闭包 / lambda | HIR 尚未降级 lambda |
| 6.5.7c | std 签名表接入 sema | sema 仍按名解析（`String.split` 推断为 `Any`） |
| HIR 完整性 | `when` / lambda / 字符串插值 / `try` 降级不完整 | Aura 编译器源码本身用到这些语法 |

### 2.7 性能瓶颈

`aura/compiler/README.md:318-360`：

- VM 解释器 ≈ **1 µs / op**；发射 15k 节点 / 49876 行 IR 需数分钟
- 单条 `HirReturn` 就要 0.4–1.5s（非 O(n²)，是 VM 解释执行速度）
- 合并 48 个模块可完成（1–2 分钟），但**不足以支撑全量自举**

## 三、阶段化改造路线（摘要）

按「最小引导层保留 Rust」为前提，分 5 个阶段推进：

| 阶段 | 目标 | 工作量 | 关键产出 |
|------|------|--------|----------|
| **A** | 加固 Rust AOT 后端 | 1–2 周 | `%struct.X` → `%struct.X*`；String 表示统一；`emit_call` 尊重返回类型 |
| **B** | 补全 Aura 侧 HIR | 1 周 | `when`/lambda/字符串插值/`try` 降级完整 |
| **C** | Aura 编译器自举闭环 | 2–3 周 | `aura-compiler-native.exe` 能重编译自身 |
| **D** | std native 上移到 Aura | 3–5 周 | std 函数全部由 Aura 源码 + C syscall 实现 |
| **E** | CLI / LSP / loom 上移 | 4–8 周 | 可删除 `compiler/` + `cli/` + `loom/` |

**总计 11–19 周**（约 2.5–4 个月，单人全职），与迁移计划「14–15 人月」估算一致。

> 详细每阶段任务清单、文件级改造点、验证标准见 `02-纯Aura化改造方案.md`。

## 五、关键风险

| 风险 | 说明 | 缓解 |
|------|------|------|
| **性能** | VM 解释执行 ≈ 1 µs/op，Aura 编译器自举需 50k 节点级处理 | 必须先让编译器以原生进程运行（阶段 A）才能支撑阶段 C/D/E |
| **std 双层漂移** | `aura/core/aura/lang/std/` 与 `compiler/src/std/` 长期并存导致 bug 修一处漏另一处 | 阶段 D 初期就建立「单一真相源」机制 |
| **AOT 类型系统加固牵一发动全身** | `%struct.X` → `%struct.X*` 的改动影响所有 AOT 编译的用户程序 | 全量回归测试（`build/probe7/identity.aura` + 全部 p0–p14 测试） |
| **阶段 D 期间用户感知不到改善** | 用户日常仍用 `cargo build` 的 `aura.exe` | 保留 Rust 编译器作为 fallback，直到阶段 E 完成 |
| **LLVM 工具链锁定** | 当前方案硬编码 LLVM 23.1.0 | 五级探测机制（`AURA_LLVM_HOME` / `C:/LLVM` / `C:/Program Files/LLVM` / PATH）已就位，需补充 Linux 路径 |

---

## 六、结论

> **目前 Aura 自举编译器不能脱离 Rust**：Rust AOT 后端仍有 2 个阻塞级 bug（类按值传递 + String 表示不一致），Aura 侧 HIR 对 `when`/lambda/`try`/字符串插值降级不完整，std native 层仍是 Rust 实现，CLI/loom/LSP/调试器全 Rust。按「阶段 A→E」推进需约 11–19 周；bootstrap 层（`compiler/src/bootstrap/`）+ C 运行库（`aura_std_cffi.c`）+ LLVM 工具链是**唯一保留**的非 Aura 依赖。
