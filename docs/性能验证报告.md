## 4. 三种执行模式对比

### 4.1 VM（字节码解释器）

- **优势**：启动快、无编译依赖、跨平台
- **劣势**：执行速度较慢，函数调用开销大
- **适用场景**：开发调试、快速原型

### 4.2 JIT（Cranelift 即时编译）

- **优势**：热点函数自动加速，无需预先编译
- **劣势**：需 `jit` feature，首次调用有编译开销
- **适用场景**：长运行程序、热点代码加速

### 4.3 AOT（LLVM 原生编译）

- **优势**：执行速度最快，接近 C 语言性能
- **劣势**：需 LLVM 工具链，编译时间长
- **适用场景**：生产部署、性能敏感场景

## 5. FFI AOT 直接 vs 间接调用

### 5.1 直接调用

FFI AOT 直接调用通过 `extern interface` 声明，使用 JitValue ABI 零转换直接调用：

```aura
extern interface Math {
    default fun loadLibrary(): String = "aura_std_math"
    fun abs(x: Int): Int
}
```

### 5.2 间接调用

间接调用通过包装函数中转，增加一层调用开销：

```aura
fun helper(x: Int): Int {
    Math.abs(x)
}
```

### 5.3 性能差异分析

| 对比维度 | 直接调用 | 间接调用 |
|----------|---------|---------|
| 调用层级 | 1 层 | 2 层 |
| 参数转换 | 零转换 (JitValue ABI) | 可能需要转换 |
| 缓存支持 | FfiCallCache 内联缓存 | 需额外缓存层 |
| 预期加速 | 1.0x (基准) | 0.6-0.8x |

## 8. 结论与建议

### 8.1 主要发现

1. **VM 模式稳定可靠**：所有标准库模块在 VM 模式下编译和执行正常
2. **FFI AOT 配置完备**：三种执行模式下的 FFI 配置均通过验证
3. **自举流程完整**：从 Aura 源码到 `.auz` 包的全流程验证通过
4. **平台检测准确**：Windows x86_64 平台识别正确

### 8.2 优化建议

1. **启用 JIT 加速**：建议对热点函数启用 JIT 编译，预期 2-5x 加速
2. **启用 AOT 编译**：生产环境建议使用 AOT 编译，预期 5-10x 加速
3. **FFI 内联缓存**：已实现 `FfiCallCache`，建议在生产环境中启用
4. **标准库模块化**：按需加载标准库模块，减少启动开销
