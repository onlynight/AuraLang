## 零、为什么"重新分析"

前三轮的分析都是从**源码推测**成本模型，实测推翻了两条：

| 轮次 | 推测结论 | 实测结果 |
|---|---|---|
| §10.114 | 5.5× 差距 = 函数序言 66~176 条/指令 | 序言只占 ~5% |
| §10.115 路线 | 类型分派（`isFloat`/`isString`）是大头 | **只值 1.3%** |
| 本轮起点 | 分派链深度是主因 | **8.7%**（确认，但非全部）|

本轮改为**先造仪器、再用数据说话**。

## 一、方法学：三个消除干扰的测量装置

### 1. per-opcode 动态计数器（新造仪器）

给 `Vm.run()` 加 256 槽 Memory 计数表（索引 `op+3`，容纳 `OP_NOP=-2`），
`AURA_OP_PROF=1` 启用，收尾单趟倾印。**这是本轮所有结论的基础**。

工具已固化为 `tools/photon-prof/`（含 `Vm_instrumented.aura` + README）。

### 2. 斜率法消除启动开销

每个 guest 跑 N 与 2N 两档，取 `(T(2N)−T(N))/N`——进程启动、.auc 装载、
库初始化全部相减抵消。

### 3. 固定宿主、只换客体 ⇒ 零布局噪声

本项目最大的测量障碍是「布局敏感雷」（同源码不同布局 ⇒ ±5% 波动）。
解法：**宿主二进制固定不变，只替换客体 `.auc`**。客体是指令*数据*，
不是宿主代码，因此宿主机器码布局完全不变。

**LOAD_LOCAL + STORE_LOCAL = 67~72%。** 这是全局最大的一块。

### 2.2 每条 `if (op == N)` 的成本 = 11 条 x86

反汇编实证：
```asm
movq  $0xa, %r10          ; 常量落栈
movq  %r10, -0xb0(%rbp)
movq  -0xa8(%rbp), %r10   ; op 读回
cmpq  $0xa, %r10
sete  %r10b               ; 比较结果物化
movzbq %r10b, %r10
movq  %r10, -0xb8(%rbp)   ; ← 落栈
movq  -0xb8(%rbp), %r10   ; ← 立即读回同一槽（纯 no-op！）
cmpq  $0x0, %r10
jne   ...
jmp   ...
```
命中第 d 个臂须付 **11×d** 条。原链里：

| op | 执行次数 | 原链深度 | 仅比较链的 x86 |
|---|---|---|---|
| **112 RETAIN** | 2,056,917 | **95** | **2.15 B** |
| **34 LE** | 1,028,457 | **45** | **0.51 B** |
| 50 JUMP | 514,228 | 17 | 0.10 B |
| 65 RETURN | 1,028,457 | 16 | 0.18 B |
| 60 CALL | 1,028,457 | 15 | 0.17 B |

**RETAIN 一项 = fib28 全程序 x86 的约 28%**，纯粹因为它排在链的第 95 位。

### 2.3 序言与帧（第二个固定成本）

| 函数 | 代码 | 帧 | 栈探测 |
|---|---|---|---|
| Vm_dispatch | 44 KB | 18120 B | 5 次 |
| Vm_callOrBuiltin | **53 KB** | 24568 B | 6 次 |
| VmStack_push | 1.5 KB | 2728 B | — |
| VmLocals_getSlot | 823 B | 2472 B | — |
| Vm_arg0IntOf | 1280 B | 2600 B | — |

- 序言固定 **8 push**（7 callee-saved + rbp）+ mov + sub = 10 条
- 结语 **leave + 7 pop + ret = 9 条** ⇒ **19 条/调用**
- 帧普遍 2.4~2.9KB，来源是 `X86Emitter` 的 `frame = 144 + range*8 + 2048`
  那 **2048 字节 blanket 边际**（P223 退役 canary 时遗留）

### 2.4 生成代码的质量问题（第三个固定成本）

| 函数 | 指令数 | 存栈 | 读栈 | 栈往返占比 |
|---|---|---|---|---|
| VmStack_push | 264 | 69 | 72 | **48%** |
| VmLocals_getSlot | 159 | 35 | 36 | **38%** |
| Vm_arg0IntOf | 246 | 50 | 50 | **33%** |
| Vm_incRef | 260 | 51 | 49 | **31%** |

- **31~48% 的生成指令是栈往返**
- 其中 **961 对是相邻的「存栈 → 立即读回同一槽」纯 no-op**（占静态 5.1%）
- 每对还带一次 ~5 cycle 的 store-forwarding 依赖

`VmStack_push` 的真实工作量约 10 条指令，实际编译出 264 条。

## 三、成本模型与校准

```
单条 guest 指令成本 = 循环头 10 + call/序言 22 + 结语 9
                    + 11 × 链深度
                    + 臂体
```
按 fib28 实测计数展开：

| 项 | x86 条数 | 占比 |
|---|---|---|
| 分派链比较（改前） | 3.76 B | — |
| 序言+结语+循环头 | 1.29 B | — |
| 臂体 | ~23 B | — |
| **合计** | **~28 B** | |

**校准**：P412 削减 2.4B 条 x86 ⇒ 实测 8.7% 墙钟 ⇒ 折算总量 ≈ 28B 条，
即 IPC ≈ 2、~15B 周期 @3GHz ≈ 5s — 与实测吻合，模型可用。

**改后剩余分布**：分派链 ~5%，固定序言 ~5%，**臂体 ~90%**。

## 四、已落地：P412（分派链按实测频次重排）

**改动**：在 `dispatch()` 热臂前置块中，把 `RETAIN`(112) 与 `LE`(34)
两条臂插到 depth 4/5（原 95/45），臂体与原链逐字一致。

**结果**：

| 基准 | 基线 P409 | P412 | 增益 |
|---|---|---|---|
| fib28 | 5247 ms（5224-5254）| **4791 ms**（4772-4857）| **8.7%** |
| loop1M | 7955 ms | **7695 ms** | **3.3%** |

五门全绿（micro1/2/3 + fib28 + loop1M）。
loop1M 增益较小符合模型——其 RETAIN 占比仅 3.8% 且无 LE。

**定位**：这是「低成本、一次性」的收益。链深度从 10.9 降到 3.9，
继续调序的边际收益已不足 1%（见下）。

## 五、优化方案（按优先级，含预期与前置条件）

### P0 — 修 `aura build --aot` 的非确定构建【硬阻塞】

**症状**：连续两次构建同一份 `PhotonHatCompile.aura`，md5 不同；
用它编译的宿主五门 0~2/5（micro2 输出 `m2=0`）。
唯一可用驱动是 `PhotonHatCompile_old.exe`（14:47 构建）。

**为什么是 P0**：**它阻塞一切发射器侧优化**。下面的 P1/P2 全部要改
`X86Emitter`/`InstructionSetlection`，无法重建驱动就无法验证。
在 ±5% 布局噪声 + 非确定驱动的环境下，任何发射器改动都不可测量。

**排查方向**：驱动是 seed AOT（LLVM 后端）产的，怀疑
①构图/符号表迭代顺序依赖哈希；
②`.hat` 序列化里的非确定字段；
③链接期符号顺序。用「连续两次构建 → 二进制 diff → 定位首个差异字节」
收窄。

### P1 — 攻臂体（占 90%）：消除栈往返

这是与 Seed VM 差距的**真正根因**。当前发射器把每个 SSA 值都物化到栈槽、
每次使用再读回——31~48% 的指令是栈流量，且形成串行的
store-forwarding 依赖链（~5 cycle/次），把 IPC 压到 ~2。

**1a. 相邻存→读同槽 peephole（最小、最安全）**
961 对纯 no-op（静态 5.1%）。在 `X86Emitter` 里做一条「若上一条是
`mov [rbp-X], r` 且本条是 `mov r, [rbp-X]` 且中间无写入，则删除两条」。
纯发射器、零语义风险、可直接用 P412 的 A/B 方法验证。
预期 **3~5%**（还要算上被消除的 store-forwarding 依赖）。

**1b. 寄存器分配质量（中期、正解）**
让 SSA 值在同一基本块内留在寄存器里，只在跨块/跨调用时落栈。
这是把 IPC 从 2 拉到 4+ 的唯一途径。
预期：**1.5~2×**（若栈流量减半）。

**1c. 帧与序言**
- `+2048` blanket 边际 → 按实际槽数收敛（帧 2.9KB → ~600B）
- 8 push → 按需 push（P396 曾失败，根因是「栈参判定不完备」；
  前置是参数布局改为固定区 + 显式栈参区，让 push 数不影响偏移）
预期合计 **3~6%**。

### P2 — 融合（已实现、待解锁）

`fuseHotPairs` 的 204/202/203 三条规则正是为 LOAD/STORE churn 设计的：
`local[a] OP const[c] → local[s]` 把「LOAD−LOAD_CONST−ADD−STORE」
四合一。P408 实测：fib28 4.8%、loop1M 9.3%、micro3 60%。

**当前禁用**，前置（§10.116/§10.118）：
1. `SsaBuilder.buildIf` 的 else 分支无条件回滚 varMap（P406，一行）
2. 后端 phi 合并形态缺陷（P407）——否则 P406 落地后宿主静默坏
预期 **5~9%**。**风险高**，需在 P0 完成后做，才能可靠二分。

### P3 — 继续调链序（边际收益 < 1%）

把 200~206（融合禁用时是死臂）与 20/21/32/60/65/50 交换位置，
可再省 ~310M 条 x86 ≈ 1.3%。**暂不做**——收益不足布局风险。

## 六、明确不要做的事（负面结果存档）

| 尝试 | 结果 | 原因 |
|---|---|---|
| 类型谓词去字符串化（P409） | 1.3% | 类型分派本就只占 1% |
| 内联 `aura_typeof`（P410） | 无法验证 | 驱动非确定 |
| 算术臂手写内联（P404b） | **-9%** | P400 后调用消解已到收益边界 |
| dispatch 内联进 run（P402） | 布局回归 | P44 家族 |
| 热臂全量内联（P403） | 全回退 | 撞四类编译器陷阱 |

**结论**：**源码级"调用消解"类优化已到边界**（P400/P404b/P412 三次实证）。
剩余杠杆全在**发射器**——因此 P0 是本轮之后唯一的高杠杆动作。
