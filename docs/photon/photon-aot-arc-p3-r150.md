# Photon AOT —— ARC P3 实施报告（受限逃逸释放落地与安全边界）

> 日期：2026-10-21　阶段：P3（性能优化 + 受限逃逸释放 + 收尾）
> 上游：`arc_implementation_plan.md` / `photon_aot_arc_p0_p1_2026-10-20.md` / `photon_aot_arc_p2_2026-10-20.md`
> 路线（用户选定）：**稳健收尾 + 受限逃逸释放**，样例快验打底、全链自举验收

---

## 一、一句话结论

**找到了一条真正可用、端到端自举逐字节一致的释放通道：`x = <expr>` 的「槽覆盖释放」（String 静态类型 + 逃逸扫描放行）。**
它让自举驱动的存活堆块数下降 **16.8%（41.28M → 34.35M 块，真回收 692 万个对象）**，`.hat` / `.obj` 仍与 R147 基线 **md5 逐字节一致**，产物 `BOOT-4` 全过，而墙钟只涨 **+7.9%**（修完 D2c 防线热点后）。

**作用域退出释放 / return 出口释放两条通道则无论单独还是叠加都无法通过验证**，已默认关闭——中间加的第四层「定值自有性」闸门也没能救回来。
所以 P3 的交付形态是：**安全档 = 开关打开时的默认组合；不安全档 = 必须显式 opt-in**，而不是把释放全面打开。

## 三、P3 做了什么

### 3.1 受限逃逸分析（`scan_escapes` + `ArcLocal.releasable`）

在 `emit_function` 入口对函数体做一趟 AST 扫描算出**逃逸**变量集；`declare_var` 登记 ARC 局部量时据此打 `releasable` 标志，只有放行的槽参与 release。

逃逸写点（命中即拉黑该变量）：字段/下标赋值、未在本帧声明的赋值目标（模块级全局）、存储型调用实参（`__list_push`/`mapSet`/`put`/`add`/`set`…）、`New` 实参、`Box`/`WeakRef`/`Await` 操作数、`defer`/`try` 块内出现过的变量。

配套闸门（`arc_releasable`）：逃逸集 → Aura 类型明确（空 / `Any` / 标量一律不放行）→ 静态类型须为 `String`。
实测放行率 **2206 / 3248（67.9%）**。

### 3.2 retain/release 配对消除与自赋值省略（`AURA_ARC_PEEP`）

`x = x` 的 retain/release 净 0，两条都不发；覆盖释放与新值 retain 的配对窥孔一并去除。

### 3.3 第四层：定值自有性闸门（`AURA_ARC_OWNED`，**默认关闭**）

比逃逸更严：要求变量的**每个定值**都既可证实独占、又在发射方向收支配平——复制类右值（`is_copy_expr` 为真，发射层已 retain）或新建值（字面量/拼接/算术，rc=1 且无人持有）。
`Call` / `New` / `Lambda` / 枚举变体无法静态证明独占 ⇒ 整变量失去释放资格。

> 这层把放行率从 67.9% 压到 **499 / 3248（15.4%）**，却**没能救回任何一条失败通道**，所以它默认关闭，只作为继续探索时的收紧项。

### 3.4 D2c 防线的热点消除（第二部分时间收益的来源）

`aura_ptr_in_freed_rgn()` 原为**对 1024 项区间表的线性扫描**，释放开启后成为最热分支（自举里 ARC 进入 C 侧达 4 亿次、探活 3563 万次），且成本随释放规模超线性增长——这正是「样例只慢 3~8%、自举慢 77%」的原因。
改为**按 4KB 页缓存判定结果**（带标签 + 标签校对），每次登记新区间整体失效：

- 保守方向：页与任一区间**有交集**即记命中（宁可多一次探活，绝不漏判 ⇒ 不产生假阴性 ⇒ 不会退化成 AV）；
- 效果：`rgn_reused` 由 36,048,842 降到 35,636,334，墙钟 1288s → **785s**，产物 md5 完全一致。

### 3.5 工程化

- 发射期一次性打印完整开关组合，出问题时一行判定「跑的是哪一档」：
  `[ARC-P3] emit: arc locals=3248 releasable=2206 (67.9%) escape=on stringonly=on owned=off assign=on scope=off return=off release=on`
- **不安全档改为 opt-in**：`AURA_ARC_SCOPE` / `AURA_ARC_RETURN` / `AURA_ARC_OWNED` 必须显式 `=1` 才打开（此前未设一律默认为开，是个陷阱）。
- 默认路径零指令变化：同一代码库的「默认自举」产出的 `.hat`/`.obj` 与 R147 基线逐字节一致，且新驱动的 IR 与已验收的 bx-D 配置 md5 完全相同（`7c5aaa94…`），证明二者等价。

## 四、为什么作用域 / return 释放过不了

二分矩阵（样例 `02_simple_vars`，基线 `.obj` = 15489 B）：

| 档位 | ASSIGN | SCOPE | RETURN | STRINGONLY | OWNED | 结果 |
|---|---|---|---|---|---|---|
| D | ✅ | ✗ | ✗ | ✅ | ✗ | **PASS** |
| F（全关，对照） | ✗ | ✗ | ✗ | ✅ | ✗ | PASS |
| G | ✗ | ✅ | ✗ | ✅ | ✗ | FAIL（`.obj` 变形，`bad_magic=0`） |
| H | ✗ | ✗ | ✅ | ✅ | ✗ | FAIL（`.obj` 68B） |
| E | ✗ | ✅ | ✅ | ✅ | ✗ | FAIL |
| I | ✅ | ✅ | ✅ | ✅ | ✅ | FAIL（`bad_magic=1`） |

关键观察：

1. **只有覆盖释放稳定通过**；单独开任意一条无条件释放通道都会坏。
2. G 档 `bad_magic=0` 却仍产出错误的 `.obj` ⇒ 失败形态是**释放仍被引用的活对象后被静默复用**，没有崩溃信号，只能靠产物字节比对发现。
3. 加上最严的第 4 层闸门（I 档，只放行 15.4%）**仍然失败**。
4. 新增诊断抓到 I 档的坏释放点，调用栈为 `aura_arc_release ← main`（本机 AOT 产物缺可靠 unwind 信息，回溯两帧后失去线索）。

**结论**：无条件释放要求「零 false-negative」，而本代码库存在多处**编译器不可见的别名**（结构体值副本、`aura_lists[32]` 静态注册表、`{i8*,i64}` Any 包装、模块级全局、枚举载荷，与 P2 报告 §三.(3) 同源）。覆盖释放之所以安全，是因为它只在「槽内旧值被本语句替换掉」时触发，语义上存在明确的所有权转移点。

> 由此 P2 报告 §四 的路线排序得到实证支持：**②局部逃逸分析不足以支撑无条件释放**；真正值得做的是 **①阶段 region 回收**（天然规避别名，且可复用 P0 的 D1 时代闸门与 D2c 区间防线）。

## 五、收益与代价

- **收益**：存活块 −16.8%（−692 万），多为 ≤64B 小对象；`bad_magic=0`、产物逐字节一致。
  同一分配序列上的累计用量在第 3494 万次分配处由 4172MB → 4136MB（差 36MB，全部来自被回收后复用的小块）。
- **代价**：修完 D2c 热点后为 **+7.9%**（785s vs 727.6s）。样例级 3 次均值 +2.7%~+7.7%：

  | 样例 | 默认 | 释放档 | 差 |
  |---|---|---|---|
  | `04_control_flow` | 479 ms | 516 ms | +7.7% |
  | `03-functions` | 490 ms | 503 ms | +2.7% |
  | `14-string-interp` | 497 ms | 525 ms | +5.6% |

- **payload 只降 0.9%**：自举的payload 由少数 MB 级大块主导（10.9MB 的 `.hat` 拼接缓冲、`aura_scr_alloc` 大临时物），692 万个 ≤64B 小块只值 36MB。
  **想降 RSS，下一步必须打大块的复用/分块化，而不是继续拓宽 release。**
- **峰值 RSS**：本轮仍未取到（`PeakWorkingSet64` 采样异常，恒为 0）。内存结论以 C 运行时的堆记账为准。

### 5.1 代价是被怎么掐掉的

释放档 vs 默认的差值（同一自举）：`retain` +126.3M、进入 C 侧次数 +407M、`rgn_reused` +34.5M、`mem_free_calls` +6.92M。
线性扫描区间表就是那个「小负载无感、大负载爆炸」的因子。加页缓存后这一项被砍掉，代价从 +77% 回到 +7.9%。
剩余部分主要是 692 万次真实 `aura_mem_free` 的记账与局部性损失。

> 这也解释了为什么 P2 的 retain-only 只有 +0.7%：不释放时几乎没有区间登记，D2c 的成本趋于零。代价来自「释放」这个动作本身。

## 六、怎么开、怎么回退

```bash
# 推荐安全档（= 已通过全链自举的那一档；这些就是现在的默认值）
export AURA_ARC=1 AURA_ARC_RELEASE=1        # 其余闸门按上述默认值即可

# 更保守：只 retain 不 release（P2 已验证）
export AURA_ARC=1

# 继续探索（默认关闭、未通过验证，仅用于研究）
export AURA_ARC_SCOPE=1 AURA_ARC_RETURN=1 AURA_ARC_OWNED=1

# 诊断
export AURA_ARC_DEBUG=1 AURA_LEAK_REPORT=1 AURA_LINK_MAP=1
```

回退：P3 全部逻辑都在 `AURA_ARC` 之后，默认路径一行 IR 都不变（本次默认自举已验证逐字节一致）；回滚只需还原 `emit.rs` / `aura_std_cffi.c` 并重编 seed 编译器。

## 七、后续建议（P4，性价比排序）

1. **阶段 region 回收**（P2 路线①）：按 Lexer→Parser→Sema→Codegen 切片，切片末 RegionReset；跨切片存活对象沿用 D1 时代闸门 + D2c 区间防线判别。唯一能同时降时间与内存的方向。
2. **大临时物分块化**：`.hat` 拼接缓冲与 `aura_scr_alloc` 的大临时物是payload 主体，改为定长块链表 + 末次拼接。
3. 释放点的**运行时探测**：给候选槽加「影子计数」，只在计数证明独占时才真正释放——用一轮自举的代价换一批自动化的释放点，比静态分析更贴合实际别名分布。
4. 修好 `PeakWorkingSet64` 采样，下一轮起 peak WS 与 C 堆记账双口径对照。
