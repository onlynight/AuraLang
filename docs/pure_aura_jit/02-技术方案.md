### 1.2 分层职责矩阵

| L1 前端 | `compiler/src/{lexer,parser,sema,codegen}/` | Rust | 词法/语法/语义/HIR/MIR | ❌（独立迁移，不在本文档范围） |
| L2 字节码发射 | `compiler/src/codegen/emit.rs` | Rust | MIR → 字节码 | ❌（已有 Aura 侧 `codegen/Codegen.aura`） |

| L4 JIT 优化 | `aura/.../jit/JitOpt.aura` | **Aura** | 7 个优化 pass | ✅ |
| L5 JIT IR 发射 | `aura/.../jit/JitLower.aura` | **Aura** | JitUnit → Clif 文本 IR | ✅ |
| L6 JIT 派发 | `aura/.../jit/JitDispatch.aura` | **Aura** | 派发决策/回退 | ✅ |
| L7 JIT 状态机 | `aura/.../jit/JitState.aura` | **Aura** | 热点检测/编译顺序 | ✅ |
| L8 FFI 边界 | `compiler/src/bootstrap/jit_ffi.rs`（新增） | Rust | 3 个 FFI 函数 | ❌（bootstrap 保留） |
| L9 机器码后端 | `compiler/src/vm/jit.rs` 的 `cranelift_backend` | Rust | Cranelift 编译 | ❌（复用或抽取） |
| L10 OS syscall | 操作系统 | — | mmap/mprotect | ❌（物理限制） |

**纯 Aura 侧**（L3–L7）共 5 层，~2000 行，**已完成**。
**Bootstrap 侧**（L8–L9）共 2 层，~500 行（新增 FFI 边界 + 复用 cranelift_backend），**待开发**。

## 二、数据流

### 2.1 完整 JIT 数据流

```text
                        纯 Aura 侧（L3–L7）                        Bootstrap 侧（L8–L9）
    ──────────────────────────────────────────────────────────────────────────────────
    
    字节码（.auc 模块）
        ↓
    ┌─────────────────────────────────────────┐
    │ L3 JitCore.aura：预解码                    │
    │ - 解析指令序列（行表）                       │
    │ - 分支目标：绝对行号 → 相对偏移              │
    │ - 常量池索引 → 字面量内联                   │
    │ - 输出：JitUnit                           │
    └─────────────────────────────────────────┘
        ↓
    ┌─────────────────────────────────────────┐
    │ L4 JitOpt.aura：7 个优化 pass             │
    │ 1. foldConstants   常量折叠               │
    │ 2. eliminateDeadCode 死码消除             │
    │ 3. threadJumps     跳转线程化             │
    │ 4. strengthReduce  强度削弱               │
    │ 5. scheduleInstructions 指令调度          │
    │ 6. inlineFunctions 函数内联（占位）        │
    │ 7. unrollLoops     循环展开               │
    │ - 输出：优化后的代码 + 新增常量             │
    └─────────────────────────────────────────┘
        ↓
    ┌─────────────────────────────────────────┐
    │ L5 JitLower.aura：发射 Clif 文本 IR       │
    │ - 字节码 opcode → Clif 指令助记符          │
    │ - 局部变量 → local_tag/local_payload      │
    │ - 运算栈 → SSA 值名                       │
    │ - 输出：.clif 文本                        │
    └─────────────────────────────────────────┘
        ↓
    ┌─────────────────────────────────────────┐
    │ L7 JitState.aura：状态机决策              │
    │ - 热点计数、阈值检查                       │
    │ - Fix A：入口强制编译                      │
    │ - Fix B：递归可达、编译顺序                │
    └─────────────────────────────────────────┘
        ↓
    ┌─────────────────────────────────────────┐
    │ L6 JitDispatch.aura：派发决策             │
    │ - NATIVE: 已编译走原生码                  │
    │ - SKIP: 已跳过回退解释器                  │
    │ - DEFER: 未达阈值暂用解释器                │
    └─────────────────────────────────────────┘
        ↓
    ══════════════════════════════════════════╗
        ↓  FFI 边界（调用 jit_compile）        ║
    ╔═════════════════════════════════════════╝
    ║
    ║  ┌─────────────────────────────────────────┐
    ║  │ L8 jit_ffi.rs：FFI 边界                 │
    ║  │ - jit_compile(clif_text) → blob         │
    ║  │   调用 Cranelift 编译                   │
    ║  │ - jit_load(blob) → entry_token          │
    ║  │   mmap(RW) → copy → protect(RX)        │
    ║  │ - jit_call(entry_token, args, out)      │
    ║  │   dispatch_table + call_indirect        │
    ║  └─────────────────────────────────────────┘
    ║
    ║  ┌─────────────────────────────────────────┐
    ║  │ L9 cranelift_backend（复用 vm/jit.rs）    │
    ║  │ - JITBuilder + JITModule                 │
    ║  │ - FunctionBuilder 编译 .clif             │
    ║  │ - 输出机器码 blob                         │
    ║  └─────────────────────────────────────────┘
    ║
    ║  ┌─────────────────────────────────────────┐
    ║  │ L10 OS syscall                            │
    ║  │ - mmap / mprotect / munmap                │
    ║  └─────────────────────────────────────────┘
    ╚══════════════════════════════════════════════
```

### 2.2 调用时序（热点函数首次编译）

```text
VM 执行字节码
    ↓
L6 JitDispatch.aura：check hotspot
    ↓  达阈值或 Fix A 强制
L7 JitState.aura：编译顺序规划（Fix B）
    ↓  被调用者先编译
L3 JitCore.aura：预解码被调用者 → JitUnit
    ↓
L4 JitOpt.aura：优化被调用者
    ↓
L5 JitLower.aura：被调用者 → Clif 文本 IR
    ↓
FFI：jit_compile(clif) → blob
    ↓
FFI：jit_load(blob) → entry_token
    ↓
L7 JitState.aura：insert(idx, entry_token)
    ↓
（重复上述步骤编译所有可达被调用者）
    ↓
L3–L5：编译自身函数
    ↓
FFI：jit_compile + jit_load
    ↓
L7 JitState.aura：insert(self_idx, entry_token)
    ↓
L6 JitDispatch.aura：派发 → NATIVE
    ↓
FFI：jit_call(entry_token, args, out)
```

### 2.3 回退路径（去优化）

```text
FFI：jit_call 返回 Deopt 信号
    ↓
L6 JitDispatch.aura：回退解释器
    ↓
VM 解释器执行该函数
    ↓
（后续调用仍尝试 JIT，直到 skip 或达阈值）
```

## 三、ABI 契约

### 3.1 JitValue

```text
JitValue = { tag: i64, payload: i64 }   // 16 字节，双字段
```

**内存布局**：

```text
Offset  0  : tag      (i64, 8 bytes)
Offset  8  : payload  (i64, 8 bytes)
```

**类型标签**（13 个，与 Rust `vm/abi.rs:15-36` 逐位一致）：

| Tag | 名称 | payload 含义 |
|-----|------|-------------|
| 0 | `INT` | 直接存储 i64 值 |
| 1 | `FLOAT` | f64 的位模式（`as i64`） |
| 2 | `BOOL` | 0 或 1 |
| 3 | `NULL` | 0（无载荷） |
| 4 | `STR` | Aura String 句柄（堆对象指针） |
| 5 | `PTR` | 裸指针 |
| 6 | `OBJ` | Aura 对象句柄（堆对象指针） |
| 7 | `FUNC` | 函数引用（函数表索引） |
| 8 | `ARRAY` | 数组句柄 |
| 9 | `LIST` | 堆列表句柄 |
| 10 | `MAP` | 堆 Map 句柄 |
| 11 | `CLOSURE` | 闭包句柄 |
| 12 | `CSTRING` | NUL 结尾字符串指针（C ABI） |

### 3.2 入口签名

```text
void entry(
    JitValue* args,         // 参数数组指针
    JitValue* out,          // 返回值输出指针
    usize argc,             // 参数个数
    void* dispatch_table    // 分发表指针（用于 call_indirect）
)
```

**VM / JIT / AOT 三路共享该 ABI**，任何一路都不得改变语义。

### 3.3 函数描述符

```text
AuraFuncDesc {              // 32 字节
    entry: u64,             // 机器码入口地址（偏移量）
    param_count: u32,       // 参数个数
    local_count: u32,       // 局部变量个数
    total_size: u32,        // 栈帧大小
    return_tag: u32,        // 返回值类型标签
    name_hash: u64,         // 函数名哈希（调试用）
    _pad: u32,              // 对齐填充
}
```

### 3.4 段格式（.auc v4）

```text
.auc v4 段 id：
  SEG_BYTECODE     = 0    // 字节码
  SEG_MACHINE      = 1    // 机器码 blob
  SEG_DESC_TABLE   = 2    // 函数描述符表
  SEG_DEBUG        = 3    // 调试信息
  SEG_STRING_POOL  = 4    // 字符串池
  SEG_SIGNATURE    = 5    // 签名

段表条目：16 字节（offset + length）
```

## 四、FFI 边界契约

### 4.1 三个 FFI 函数

纯 Aura 侧通过 `@native` 调用以下三个 FFI 函数，由 bootstrap 层实现：

#### 4.1.1 `jit_compile`

```text
@native fun jit_compile(clif_text: String): String
```

**语义**：接收 Cranelift 文本 IR（.clif），返回机器码 blob（base64 或 hex 编码的字节数组字符串）。

**输入**：
- `clif_text`：Cranelift 文本 IR，格式见 `JitLower.aura:16-28` 示例

**输出**：
- 成功：base64 编码的机器码字节
- 失败：空字符串（纯 Aura 侧检测到空串后回退解释器）

**bootstrap 实现要点**：
- 调用 `cranelift_jit::JITModule` 编译
- 提取 `JITModule::finalized_code`
- 转为 base64 字符串返回

#### 4.1.2 `jit_load`

```text
@native fun jit_load(blob_b64: String): String
```

**语义**：接收机器码 blob（base64），执行 mmap 装载，返回 entry_token。

**输入**：
- `blob_b64`：base64 编码的机器码字节

**输出**：
- 成功：entry_token 字符串（如 `"fn#0"` 或指针哈希）
- 失败：空字符串

**bootstrap 实现要点**：
- base64 解码
- `mmap(RW)` 匿名映射
- 拷贝机器码
- `mprotect(RX)` 切换权限
- 注册到分发表，返回 entry_token

#### 4.1.3 `jit_call`

```text
@native fun jit_call(entry_token: String, args: String, out_slot: Int): String
```

**语义**：通过 entry_token 调用已编译的函数，结果写入 out_slot。

**输入**：
- `entry_token`：`jit_load` 返回的 token
- `args`：JitValue 数组的序列化形式（记录表：`idx|tag|payload`）
- `out_slot`：输出槽位索引

**输出**：
- 成功：返回值的序列化形式（`tag|payload`）
- Deopt：返回特殊标记 `"DEOPT"`
- 失败：空字符串

**bootstrap 实现要点**：
- 从 entry_token 查找机器码入口
- 反序列化 args 为 JitValue 数组
- 调用机器码入口
- 序列化返回值

### 4.2 FFI 边界设计原则

1. **最小化**：仅 3 个 FFI 函数，覆盖全部 JIT 操作
2. **字符串传递**：所有输入输出均为字符串（base64/记录表），避免复杂类型跨 FFI 边界
3. **错误处理**：FFI 失败返回空字符串，纯 Aura 侧统一回退解释器
4. **无状态**：FFI 函数本身无状态，状态由纯 Aura 侧 `JitState.aura` 管理
5. **可测试**：每个 FFI 函数可独立用 Rust 单元测试覆盖

### 4.3 FFI 边界位置

```text
compiler/src/bootstrap/
├── mod.rs
├── jit_ffi.rs          ← 新增（本文档 §四 定义）
├── jit_core.rs         ← 已有（基线 JIT，不复用）
├── vm_core.rs
├── aot_core.rs
├── memory.rs
├── runtime.rs
├── any_core.rs
├── type_core.rs
└── value_check.rs
```

### 4.4 FFI 边界与现有 Cranelift 代码的关系

现有 Cranelift 代码在 `compiler/src/vm/jit.rs:205-464`（`cranelift_backend` 模块）。
bootstrap 侧的 `jit_ffi.rs` 需要**复用**这段代码。

**两种方案**：

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| **A. 直接复用** | `jit_ffi.rs` 调用 `crate::vm::jit::cranelift_backend::jit_compile_cranelift` | 零重复代码 | 需要 `jit` feature |
| **B. 抽取独立 crate** | 将 `cranelift_backend` 抽取到 `cranelift-aura` crate | 解耦、可独立测试 | 需要重构 |

**推荐方案 A**（短期），后续如需要再抽取 crate。

## 五、W^X 装载策略

### 5.1 策略概述

来源：`JitRuntime.aura:14-20` 与 `compiler/src/vm/aot_runtime.rs`。

```text
1. mmap(RW)   ——  匿名映射可写内存
2. copy       ——  拷贝机器码段
3. mprotect(RX) ——  切换为可读可执行（禁止写）
```

**任何环节失败 → 模块不装载，调用回退解释器。**

### 5.2 W^X 状态机

```text
    ┌─────────┐
    │  IDLE   │  初始状态，无映射
    └────┬────┘
         │ mmap(RW)
         ↓
    ┌─────────┐
    │  RW     │  可写可读，可拷贝机器码
    └────┬────┘
         │ mprotect(RX)
         ↓
    ┌─────────┐
    │  RX     │  可读可执行，禁止写
    └────┬────┘
         │ munmap
         ↓
    ┌─────────┐
    │  IDLE   │  释放，回到初始状态
    └─────────┘
```

### 5.3 安全考虑

1. **W^X 策略**：机器码段一旦装载为 RX，禁止再写入，防止代码注入
2. **调用深度限制**：`jitMaxCallDepth() = 1024`，防止栈溢出
3. **去优化回退**：JIT 执行失败时回退解释器，保证语义一致
4. **分发表稳定性**：`JitState.ensureCapacity` 保证分发表指针稳定，避免悬挂引用

### 5.4 跨平台差异

| 平台 | mmap | mprotect | 注意事项 |
|------|------|----------|---------|
| Linux | `mmap` + `PROT_READ`/`PROT_WRITE`/`PROT_EXEC` | `mprotect` | 标准 POSIX |
| macOS | 同 Linux | 同 Linux | 同 Linux |
| Windows | `VirtualAlloc(MEM_COMMIT)` | `VirtualProtect` | 需要不同 API |

**当前状态**：Cranelift 的 `JITModule` 已处理跨平台 mmap，bootstrap 侧无需重复实现。

## 六、纯 Aura 侧职责边界

### 6.1 纯 Aura 侧**必须**做

1. **字节码预解码**：`JitCore.aura` 将字节码转为 JitUnit 形态
2. **字节码优化**：`JitOpt.aura` 执行 7 个优化 pass
3. **Cranelift IR 生成**：`JitLower.aura` 输出 .clif 文本
4. **派发决策**：`JitDispatch.aura` 决定 NATIVE/SKIP/DEFER
5. **状态管理**：`JitState.aura` 管理热点计数、编译集合、分发表
6. **Fix A / Fix B**：入口强制编译 + 递归编译顺序

### 6.2 纯 Aura 侧**不做**

1. ❌ 实际 Cranelift 编译（FFI 调用）
2. ❌ mmap/mprotect（FFI 调用）
3. ❌ 机器码装载与分发表重建（FFI 调用）
4. ❌ 原生代码调用（FFI 调用）
5. ❌ 任何操作系统 syscall（通过 FFI 间接调用）

### 6.3 纯 Aura 侧**可选**做

1. ⚪ 去优化检测（当前由 FFI 返回 Deopt 信号，纯 Aura 侧可简化处理）
2. ⚪ 性能监控（编译次数、去优化次数统计，当前 `JitState.aura` 已支持）
3. ⚪ 诊断输出（`JitState.diagnose()` 已实现）

### 6.4 边界审计清单

| # | 检查项 | 通过标准 | 审计位置 |
|---|--------|---------|---------|
| 1 | 纯 Aura 侧无 `@native` 调用 OS syscall | 仅调用 3 个 jit_ffi 函数 | grep `@native` in `aura/.../jit/` |
| 2 | 纯 Aura 侧无 Cranelift 依赖 | 无 `cranelift` 引用 | grep `cranelift` in `aura/.../jit/` |
| 3 | FFI 边界仅 3 个函数 | `jit_compile` / `jit_load` / `jit_call` | `compiler/src/bootstrap/jit_ffi.rs` |
| 4 | FFI 输入输出均为字符串 | 无复杂类型跨边界 | 代码审查 |
| 5 | FFI 失败回退解释器 | 空串/DEOPT 标记 | `JitDispatch.aura` |

## 七、与自举链的联动

### 7.1 自举链当前状态

自举闭环已跑通（`docs/pure_aura/03-自举验证报告.md:5-48`）：

```text
Stage-1: Rust 编译器编译 Aura 编译器源码 → aura-compiler-native.exe
Stage-2: 原生载体编译自身 → aura-compiler-native2.exe
Stage-3: 自举产物编译用户程序（含 @native FFI）→ 用户 exe
```

**关键事实**：自举链用的是 **AOT（LLVM）后端**，不是 JIT。

### 7.2 JIT 与自举链的关系

JIT 是**运行时**优化，自举链验证**编译期**能力。两者独立：

```text
自举链（编译期）：
  Rust 编译器 → Aura 编译器源码 → 原生载体 → 自举产物 → 用户程序 exe
  （AOT 后端，不涉及 JIT）

JIT 路径（运行时）：
  用户程序 exe → VM 解释器 → 热点检测 → Cranelift JIT → 原生码执行
  （JIT 后端，不涉及自举链）
```

### 7.3 未来联动可能

自举产物（`aura-compiler-native2.exe`）如果启用 `--features jit`，
可在运行时对编译出的用户程序启用 JIT 优化。但这需要：

1. 自举产物链接 Cranelift（通过 bootstrap FFI 边界）
2. 自举产物运行时调用 `jit_compile` / `jit_load` / `jit_call`
3. 用户程序字节码包含 JIT 可编译函数

**当前状态**：自举产物**不**启用 JIT，仅用 VM 解释器执行编译期逻辑。
JIT 是**用户程序运行时**的优化，与自举链解耦。

## 八、关键设计决策记录

### 8.1 决策 1：为什么保留 Cranelift 在 bootstrap

**背景**：纯 Aura 化目标要求脱离 Rust，但 JIT 机器码后端必然踩 OS syscall。

**选项**：

| 选项 | 描述 | 评估 |
|------|------|------|
| A | 保留 Cranelift 在 bootstrap | ✅ 推荐 |
| B | 用文本汇编 + 外部汇编器（nasm/as）替换 | ❌ JIT 延迟涨到 50–100ms |
| C | 用 WAMR（WASM Micro Runtime，纯 C）做后端 | ❌ WASM 语义与 Aura OOP 差异大 |
| D | 彻底放弃 JIT，只用 AOT + VM | ❌ 丢失热点检测 + 渐进优化 |

**决策**：选项 A。

**理由**：
1. Cranelift 是成熟、活跃维护的后端，自己重写等价物代价高、收益低
2. 这是 Rust、Go 等成熟语言的标准做法（bootstrap 层保留不可脱的最小实现）
3. 自举链已跑通，bootstrap 的存在不影响自举——只是自举产物里**包含** bootstrap
4. JIT 的机器码装载必然踩 OS syscall，Aura 无法绕过

### 8.2 决策 2：为什么用 3 个 FFI 函数

**背景**：FFI 边界需要覆盖 JIT 的全部操作。

**选项**：

| 选项 | 描述 | 评估 |
|------|------|------|
| A | 3 个函数：compile / load / call | ✅ 推荐 |
| B | 1 个函数：jit_run(clif, args) → result | ❌ 无法缓存编译结果 |
| C | 5+ 个函数：编译/加载/卸载/派发/去优化/... | ❌ 边界过大，审计困难 |

**决策**：选项 A。

**理由**：
1. 最小化：仅 3 个函数，覆盖全部 JIT 操作
2. 可缓存：编译结果可缓存，同一 .clif 只需编译一次
3. 可审计：边界清晰，易审计
4. 字符串传递：避免复杂类型跨 FFI 边界

### 8.3 决策 3：为什么用扁平字符串表示

**背景**：当前 Aura VM 对 `List`/`Map` 的支持仍有限制。

**选项**：

| 选项 | 描述 | 评估 |
|------|------|------|
| A | 扁平字符串（行表/记录表） | ✅ 当前方案 |
| B | 结构化数据（List/Map） | ❌ VM 支持有限 |
| C | 混合（热点路径用字符串，冷路径用结构化） | ⚪ 未来可考虑 |

**决策**：选项 A。

**理由**：
1. 与 Ast/Hir/Mir/AOT 各阶段采用同一策略，保持一致性
2. 字符串在 Aura VM 中有完善支持
3. 待 VM 对集合类型支持完善后可逐步迁移

### 8.4 决策 4：为什么字节码契约与 VM 统一（Phase 9）

**背景**：早期设计有独立的「引导指令集」，与 VM 字节码不同。

**决策**：Phase 9 统一为「JIT 直接消费与 VM 相同的字节码」。

**理由**：
1. 避免维护两套指令集
2. JIT 预解码阶段处理指令集差异
3. 常量以字面量内联，分支目标在预解码阶段由绝对行号转为相对偏移

## 九、总结

### 9.1 技术方案核心

1. **分层**：纯 Aura 侧（L3–L7）+ Bootstrap 侧（L8–L9）+ OS（L10）
2. **数据流**：字节码 → 预解码 → 优化 → Clif IR → FFI 编译 → mmap 装载 → 派发
3. **ABI**：JitValue（16 字节）+ 入口签名（4 参数）+ 函数描述符（32 字节）
4. **FFI 边界**：3 个函数（`jit_compile` / `jit_load` / `jit_call`）
5. **W^X**：mmap(RW) → copy → mprotect(RX) → munmap
6. **自举联动**：JIT 是运行时优化，自举链是编译期，两者解耦
