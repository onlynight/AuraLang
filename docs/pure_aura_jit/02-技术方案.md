# 02 · 技术方案

> **范围**：全域架构分层、VM+JIT+AOT 三种执行模式数据流、ABI 契约、FFI 边界、纯 Aura 侧职责
> **配套文档**：[01-现状分析.md](./01-现状分析.md)（现状）、[03-分阶段开发计划.md](./03-分阶段开发计划.md)（推进）
> **设计原则**：纯 Aura 侧只做纯函数翻译，所有 OS syscall 归 bootstrap FFI 边界；syscall 运行库用 Rust 重写（替代原 C 实现），不 Aura 化
> **覆盖模式**：VM 解释器 + JIT（Cranelift）+ AOT（LLVM）三种执行模式

**不 Aura 化的层**（L8–L10）：syscall/C + JIT + Bootstrap，保留 native 实现。

## 二、数据流

### 2.1 VM 模式数据流（纯 Aura，100%）

```text
                    纯 Aura 侧（L1–L3）
    ──────────────────────────────────────────────────────────────────────────
    
    源码 (.aura)
        ↓
    ┌─────────────────────────────────────────┐
    │ L1 前端：词法 → 语法 → AST → 语义 → HIR → MIR │
    │ (Aura 侧已完成)                            │
    └─────────────────────────────────────────┘
        ↓
    ┌─────────────────────────────────────────┐
    │ L2 字节码发射：Codegen.aura                │
    │ - MIR → 字节码指令序列                      │
    │ - 输出：.auc 模块                           │
    └─────────────────────────────────────────┘
        ↓
    ┌─────────────────────────────────────────┐
    │ L3 VM 解释器：Vm.aura + VmRunner.aura     │
    │ - 栈式字节码解释                            │
    │ - 支持：算术/比较/跳转/调用/对象/闭包/异常    │
    │ - 直接执行，无编译开销                       │
    └─────────────────────────────────────────┘
        ↓
    程序运行完成
```

**VM 模式特点**：
- **纯 Aura**：全部 7 个 VM 文件均为 Aura 实现，无 Rust 依赖
- **零编译开销**：直接解释执行字节码
- **完整功能**：支持 Aura 全部语言特性（OOP、闭包、异常、协程）

### 2.2 AOT 模式数据流（纯 Aura 发射器 + 外部 LLVM 工具链）

```text
                    纯 Aura 侧（L1–L4）              外部工具链（非 Rust）
    ──────────────────────────────────────────────────────────────────────────
    
    源码 (.aura)
        ↓
    ┌─────────────────────────────────────────┐
    │ L1 前端：词法 → 语法 → AST → 语义 → HIR → MIR │
    │ (Aura 侧已完成)                            │
    └─────────────────────────────────────────┘
        ↓
    ┌─────────────────────────────────────────┐
    │ L4 AOT 发射器：Emit.aura + EmitBuffer.aura │
    │ - HIR → 文本 LLVM IR (.ll)                 │
    │ - 类型映射：TypeMapper.aura                │
    │ - FFI 发射：Ffi.aura + FfiAot.aura        │
    │ - 运行时声明：Runtime.aura                  │
    │ - 优化：Optimize.aura                      │
    │ - 输出：.ll 文本文件                        │
    └─────────────────────────────────────────┘
        ↓
    ══════════════════════════════════════════╗
        ↓  外部工具链（LLVM 23.1.0）            ║
    ╔═════════════════════════════════════════╝
    ║
    ║  llc -filetype=obj -o output.o input.ll  ║
    ║  clang -o program.exe output.o + cffi.o  ║
    ║  lld-link（Windows）                       ║
    ╚══════════════════════════════════════════
        ↓
    用户程序 exe（原生）
```

**AOT 模式特点**：
- **纯 Aura 发射器**：L4 的 16 个文件均为 Aura 实现，无 Rust 依赖
- **外部工具链**：通过 `@native` 调用 `Process.run` 执行 llc/clang（syscall 层，不 Aura 化）
- **完成度 85%**：缺 6.5.10（自举产物 AOT 出 exe）、6.5.13（try/catch）、6.5.14（闭包/lambda）、6.5.7c（std 签名表）
- **AOT native 内容不动**：`compiler/src/codegen/aot/emit.rs`、`linker.rs`、`Process.run`、`@native` 机制均不做修改

### 2.2 JIT 模式数据流（纯 Aura 侧 + FFI 边界）

```text
                    纯 Aura 侧（L3–L7）                    Native 侧（L8–L9）
    ──────────────────────────────────────────────────────────────────────────
    
    字节码（.auc 模块）
        ↓
    ┌─────────────────────────────────────────┐
    │ L3 JitCore.aura：预解码                    │
    │ - 解析指令序列（行表）                       │
    │ - 分支目标：绝对行号 → 相对偏移              │
    │ - 常量池索引 → 字面量内联                   │
    │ - 输出：JitUnit                           │
    └─────────────────────────────────────────┘
        ↓
    ┌─────────────────────────────────────────┐
    │ L4 JitOpt.aura：7 个优化 pass             │
    │ 1. foldConstants   常量折叠               │
    │ 2. eliminateDeadCode 死码消除             │
    │ 3. threadJumps     跳转线程化             │
    │ 4. strengthReduce  强度削弱               │
    │ 5. mergeBbs        块合并                 │
    │ 6. eliminateBranch 分支消除               │
    │ 7. simplifyGEP     GEP 简化               │
    └─────────────────────────────────────────┘
        ↓
    ┌─────────────────────────────────────────┐
    │ L5 JitLower.aura：Clif IR 发射            │
    │ - JitUnit → Cranelift 文本 IR (.clif)     │
    │ - 函数声明：`export fn ...`                │
    │ - 块标签：`ss1:` `bbN:`                   │
    │ - 指令：`i32.const` `i32.add` `call`...   │
    │ - 输出：.clif 文本                        │
    └─────────────────────────────────────────┘
        ↓
    ══════════════════════════════════════════╗
        ↓  FFI 边界（bootstrap/jit_ffi.rs）    ║
    ╔═════════════════════════════════════════╝
    ║
    ║  jit_compile(clif_text) → blob_b64       ║
    ║  - Cranelift JITBuilder 编译 .clif       ║
    ║  - 返回 base64 编码的机器码               ║
    ╚══════════════════════════════════════════
        ↓
    ══════════════════════════════════════════╗
        ↓  FFI 边界                           ║
    ╔═════════════════════════════════════════╝
    ║
    ║  jit_load(blob_b64) → entry_token        ║
    ║  - mmap(RW) → copy → mprotect(RX)       ║
    ║  - 注册到 dispatch_table                  ║
    ║  - 返回 entry_token                       ║
    ╚══════════════════════════════════════════
        ↓
    ┌─────────────────────────────────────────┐
    │ L6 JitDispatch.aura：派发决策             │
    │ - 已编译？ → "native"（走原生码）          │
    │ - 已跳过？ → "skip"（回退解释器）          │
    │ - 达阈值？ → tryJitCompile()             │
    │ - 未达阈值？ → "defer"                   │
    └─────────────────────────────────────────┘
        ↓
    ══════════════════════════════════════════╗
        ↓  FFI 边界                           ║
    ╔═════════════════════════════════════════╝
    ║
    ║  jit_call(entry_token, args, out) → ret  ║
    ║  - dispatch_table + call_indirect        ║
    ║  - 返回 tag|payload 或 "DEOPT"           ║
    ╚══════════════════════════════════════════
        ↓
    程序运行完成
```

**JIT 模式特点**：
- **纯 Aura 侧 100%**：Clif IR 生成、优化、派发、状态管理全部 Aura 实现（~3440 行）
- **FFI 边界最小**：仅 3 个函数（compile/load/call），全部字符串输入输出
- **W^X 安全**：mmap(RW) → copy → mprotect(RX)，符合现代安全模型
- **Fix A / Fix B**：入口强制编译 + 递归编译顺序，解决热点检测 + 递归编译问题
- **回退机制**：FFI 失败或 DEOPT 信号自动回退 VM 解释器

### 2.3 三种模式对比

| 维度 | VM 模式 | AOT 模式 | JIT 模式 |
|------|--------|---------|---------|
| **编译时机** | 无（解释执行） | 编译期 | 运行期 |
| **纯 Aura 化** | ✅ 100% | ⚠️ 85% | ✅ 纯 Aura 侧 100% |
| **工具链** | 无 | 外部 llc/clang | 进程内 Cranelift |
| **Rust 依赖** | ❌ 无 | ❌ 无（发射器纯 Aura） | ✅ 仅 FFI 边界（3 个函数） |
| **延迟** | 0（直接执行） | 数百毫秒（编译期） | 1–5 毫秒（运行期） |
| **本方案范围** | ✅ 在范围内 | ✅ 在范围内 | ✅ 在范围内 |

## 三、ABI 契约

> **说明**：JitValue ABI 是 VM/JIT/AOT 三种模式共享的调用约定。
> 本方案聚焦 VM + AOT 两种纯 Aura 模式；JIT 模式保留 Rust/Cranelift，不在本方案范围内。
> 但 AOT 嵌入机器码段（`.auc` v4）也使用同一 ABI，因此 ABI 契约仍适用。

### 3.1 JitValue

```text
JitValue = { tag: i64, payload: i64 }   // 16 字节，双字段
```

**内存布局**：

```text
Offset  0  : tag      (i64, 8 bytes)
Offset  8  : payload  (i64, 8 bytes)
```

**类型标签**（13 个，与 Rust `vm/abi.rs:15-36` 逐位一致）：

| Tag | 名称 | payload 含义 |
|-----|------|-------------|
| 0 | `INT` | 直接存储 i64 值 |
| 1 | `FLOAT` | f64 的位模式（`as i64`） |
| 2 | `BOOL` | 0 或 1 |
| 3 | `NULL` | 0（无载荷） |
| 4 | `STR` | Aura String 句柄（堆对象指针） |
| 5 | `PTR` | 裸指针 |
| 6 | `OBJ` | Aura 对象句柄（堆对象指针） |
| 7 | `FUNC` | 函数引用（函数表索引） |
| 8 | `ARRAY` | 数组句柄 |
| 9 | `LIST` | 堆列表句柄 |
| 10 | `MAP` | 堆 Map 句柄 |
| 11 | `CLOSURE` | 闭包句柄 |
| 12 | `CSTRING` | NUL 结尾字符串指针（C ABI） |

### 3.2 入口签名

```text
void entry(
    JitValue* args,         // 参数数组指针
    JitValue* out,          // 返回值输出指针
    usize argc,             // 参数个数
    void* dispatch_table    // 分发表指针（用于 call_indirect）
)
```

**VM / JIT / AOT 三路共享该 ABI**，任何一路都不得改变语义。

### 3.3 函数描述符

## 四、FFI 边界契约

### 4.0 Syscall 运行库层（保留 Rust，不 Aura 化）

`compiler/src/std/cffi/`（~3000 行，**Rust 重写**）提供 ~100 个 C ABI 函数，是 Aura 与操作系统的**唯一 syscall 入口**。

**保留原因**：
- syscall 是操作系统级操作（`mmap`/`read`/`write`/`open`/`fork`/`clone`...），必须用底层语言实现
- `@native` 机制本身是 Rust 侧实现，属于 bootstrap 层
- syscall 运行库已被 AOT/VM/JIT 三种模式共用，是成熟基础设施
- **用 Rust 重写**：替代原 C 实现（`aura_std_cffi.c`），减少语言种类（3→2）

**主要函数族**：

| 函数族 | 用途 | 调用方 |
|--------|------|--------|
| `aura_println` / `aura_print` / `aura_puts` | 控制台输出 | VM + JIT + AOT |
| `aura_io_*` | IO + 文件操作 | AOT（`Process.run` 调 llc/clang） |
| `aura_math_*` | 数学函数 | VM + JIT + AOT |
| `aura_string_*` | 字符串操作 | VM + JIT + AOT |
| `aura_collections_*` | 集合操作 | VM + JIT + AOT |
| `aura_concurrent_*` | 并发 API（Actor/Channel/Coroutine） | VM + JIT + AOT |
| `aura_syscall_dispatch` | 系统调用分发 | VM + JIT + AOT |

**边界规则**：
- 纯 Aura 侧通过 `@native` 调用 syscall 运行库函数
- syscall 运行库函数通过 `extern "C"` 暴露给 Rust bootstrap 层（**Rust 重写，保持 C ABI 兼容**）
- Rust bootstrap 层负责 `@native` 注册和分发
- **不 Aura 化**：syscall 运行库用 Rust 重写（替代原 C 实现），减少语言种类（3→2）
- **AOT native 内容不动**：`emit.rs`/`linker.rs`/`Process.run`/`@native` 机制不做修改

### 4.1 三个 JIT FFI 函数

纯 Aura 侧通过 `@native` 调用以下三个 FFI 函数，由 bootstrap 层实现：

#### 4.1.1 `jit_compile`

```text
@native fun jit_compile(clif_text: String): String
```

**语义**：接收 Cranelift 文本 IR（.clif），返回机器码 blob（base64 或 hex 编码的字节数组字符串）。

**输入**：
- `clif_text`：Cranelift 文本 IR，格式见 `JitLower.aura:16-28` 示例

**输出**：
- 成功：base64 编码的机器码字节
- 失败：空字符串（纯 Aura 侧检测到空串后回退解释器）

**bootstrap 实现要点**：
- 调用 `cranelift_jit::JITModule` 编译
- 提取 `JITModule::finalized_code`
- 转为 base64 字符串返回

#### 4.1.2 `jit_load`

```text
@native fun jit_load(blob_b64: String): String
```

**语义**：接收机器码 blob（base64），执行 mmap 装载，返回 entry_token。

**输入**：
- `blob_b64`：base64 编码的机器码字节

**输出**：
- 成功：entry_token 字符串（如 `"fn#0"` 或指针哈希）
- 失败：空字符串

**bootstrap 实现要点**：
- base64 解码
- `mmap(RW)` 匿名映射
- 拷贝机器码
- `mprotect(RX)` 切换权限
- 注册到分发表，返回 entry_token

#### 4.1.3 `jit_call`

```text
@native fun jit_call(entry_token: String, args: String, out_slot: Int): String
```

**语义**：通过 entry_token 调用已编译的函数，结果写入 out_slot。

**输入**：
- `entry_token`：`jit_load` 返回的 token
- `args`：JitValue 数组的序列化形式（记录表：`idx|tag|payload`）
- `out_slot`：输出槽位索引

**输出**：
- 成功：返回值的序列化形式（`tag|payload`）
- Deopt：返回特殊标记 `"DEOPT"`
- 失败：空字符串

**bootstrap 实现要点**：
- 从 entry_token 查找机器码入口
- 反序列化 args 为 JitValue 数组
- 调用机器码入口
- 序列化返回值

### 4.2 FFI 边界设计原则

1. **最小化**：仅 3 个 FFI 函数，覆盖全部 JIT 操作
2. **字符串传递**：所有输入输出均为字符串（base64/记录表），避免复杂类型跨 FFI 边界
3. **错误处理**：FFI 失败返回空字符串，纯 Aura 侧统一回退解释器
4. **无状态**：FFI 函数本身无状态，状态由纯 Aura 侧 `JitState.aura` 管理
5. **可测试**：每个 FFI 函数可独立用 Rust 单元测试覆盖

### 4.3 FFI 边界位置

```text
compiler/src/bootstrap/
├── mod.rs
├── jit_ffi.rs          ← 新增（本文档 §四 定义）
├── jit_core.rs         ← 已有（基线 JIT，不复用）
├── vm_core.rs
├── aot_core.rs
├── memory.rs
├── runtime.rs
├── any_core.rs
├── type_core.rs
└── value_check.rs
```

### 4.4 FFI 边界与现有 Cranelift 代码的关系

现有 Cranelift 代码在 `compiler/src/vm/jit.rs:205-464`（`cranelift_backend` 模块）。
bootstrap 侧的 `jit_ffi.rs` 需要**复用**这段代码。

**两种方案**：

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| **A. 直接复用** | `jit_ffi.rs` 调用 `crate::vm::jit::cranelift_backend::jit_compile_cranelift` | 零重复代码 | 需要 `jit` feature |
| **B. 抽取独立 crate** | 将 `cranelift_backend` 抽取到 `cranelift-aura` crate | 解耦、可独立测试 | 需要重构 |

**推荐方案 A**（短期），后续如需要再抽取 crate。

## 五、W^X 装载策略

W^X 装载策略是 JIT 模式的运行期机器码加载机制（mmap(RW) → copy → mprotect(RX)）。
AOT 模式不需要 W^X 装载（编译期直接生成 exe）。

### 5.1 策略概述

来源：`JitRuntime.aura:14-20` 与 `compiler/src/vm/aot_runtime.rs`。

```text
1. mmap(RW)   ——  匿名映射可写内存
2. copy       ——  拷贝机器码段
3. mprotect(RX) ——  切换为可读可执行（禁止写）
```

**任何环节失败 → 模块不装载，调用回退解释器。**

### 5.2 W^X 状态机

```text
    ┌─────────┐
    │  IDLE   │  初始状态，无映射
    └────┬────┘
         │ mmap(RW)
         ↓
    ┌─────────┐
    │  RW     │  可写可读，可拷贝机器码
    └────┬────┘
         │ mprotect(RX)
         ↓
    ┌─────────┐
    │  RX     │  可读可执行，禁止写
    └────┬────┘
         │ munmap
         ↓
    ┌─────────┐
    │  IDLE   │  释放，回到初始状态
    └─────────┘
```

### 5.3 安全考虑

1. **W^X 策略**：机器码段一旦装载为 RX，禁止再写入，防止代码注入
2. **调用深度限制**：`jitMaxCallDepth() = 1024`，防止栈溢出
3. **去优化回退**：JIT 执行失败时回退解释器，保证语义一致
4. **分发表稳定性**：`JitState.ensureCapacity` 保证分发表指针稳定，避免悬挂引用

### 5.4 跨平台差异

| 平台 | mmap | mprotect | 注意事项 |
|------|------|----------|---------|
| Linux | `mmap` + `PROT_READ`/`PROT_WRITE`/`PROT_EXEC` | `mprotect` | 标准 POSIX |
| macOS | 同 Linux | 同 Linux | 同 Linux |
| Windows | `VirtualAlloc(MEM_COMMIT)` | `VirtualProtect` | 需要不同 API |

**当前状态**：Cranelift 的 `JITModule` 已处理跨平台 mmap，bootstrap 侧无需重复实现。

## 七、与自举链的联动

### 7.1 自举链当前状态

自举闭环已跑通（`docs/pure_aura/03-自举验证报告.md:5-48`）：

```text
Stage-1: Rust 编译器编译 Aura 编译器源码 → aura-compiler-native.exe
Stage-2: 原生载体编译自身 → aura-compiler-native2.exe
Stage-3: 自举产物编译用户程序（含 @native FFI）→ 用户 exe
```

**关键事实**：自举链用的是 **AOT（LLVM）后端**，不是 JIT。

### 7.2 JIT 与自举链的关系

JIT 是**运行时**优化，自举链验证**编译期**能力。两者独立：

```text
自举链（编译期）：
  Rust 编译器 → Aura 编译器源码 → 原生载体 → 自举产物 → 用户程序 exe
  （AOT 后端，不涉及 JIT）

JIT 路径（运行时）：
  用户程序 exe → VM 解释器 → 热点检测 → Cranelift JIT → 原生码执行
  （JIT 后端，不涉及自举链）
```

### 7.3 未来联动可能

自举产物（`aura-compiler-native2.exe`）如果启用 `--features jit`，
可在运行时对编译出的用户程序启用 JIT 优化。但这需要：

1. 自举产物链接 Cranelift（通过 bootstrap FFI 边界）
2. 自举产物运行时调用 `jit_compile` / `jit_load` / `jit_call`
3. 用户程序字节码包含 JIT 可编译函数

**当前状态**：自举产物不启用 JIT（`--features jit` 默认关闭）。
**未来可能**：如果 P2 完成且性能达标，可考虑在自举产物中启用 JIT。

**当前状态**：自举产物**不**启用 JIT，仅用 VM 解释器执行编译期逻辑。
JIT 是**用户程序运行时**的优化，与自举链解耦。

## 八、关键设计决策记录

### 8.1 决策 1：为什么保留 Cranelift 在 bootstrap

**背景**：纯 Aura 化目标要求脱离 Rust，但 JIT 机器码后端必然踩 OS syscall。

**选项**：

| 选项 | 描述 | 评估 |
|------|------|------|
| A | 保留 Cranelift 在 bootstrap | ✅ 推荐 |
| B | 用文本汇编 + 外部汇编器（nasm/as）替换 | ❌ JIT 延迟涨到 50–100ms |
| C | 用 WAMR（WASM Micro Runtime，纯 C）做后端 | ❌ WASM 语义与 Aura OOP 差异大 |
| D | 彻底放弃 JIT，只用 AOT + VM | ❌ 丢失热点检测 + 渐进优化 |

**决策**：选项 A。

**理由**：
1. Cranelift 是成熟、活跃维护的后端，自己重写等价物代价高、收益低
2. 这是 Rust、Go 等成熟语言的标准做法（bootstrap 层保留不可脱的最小实现）
3. 自举链已跑通，bootstrap 的存在不影响自举——只是自举产物里**包含** bootstrap
4. JIT 的机器码装载必然踩 OS syscall，Aura 无法绕过

### 8.2 决策 2：为什么用 3 个 FFI 函数

**背景**：FFI 边界需要覆盖 JIT 的全部操作。

**选项**：

| 选项 | 描述 | 评估 |
|------|------|------|
| A | 3 个函数：compile / load / call | ✅ 推荐 |
| B | 1 个函数：jit_run(clif, args) → result | ❌ 无法缓存编译结果 |
| C | 5+ 个函数：编译/加载/卸载/派发/去优化/... | ❌ 边界过大，审计困难 |

**决策**：选项 A。

**理由**：
1. 最小化：仅 3 个函数，覆盖全部 JIT 操作
2. 可缓存：编译结果可缓存，同一 .clif 只需编译一次
3. 可审计：边界清晰，易审计
4. 字符串传递：避免复杂类型跨 FFI 边界

### 8.3 决策 3：为什么用扁平字符串表示

**背景**：当前 Aura VM 对 `List`/`Map` 的支持仍有限制。

**选项**：

| 选项 | 描述 | 评估 |
|------|------|------|
| A | 扁平字符串（行表/记录表） | ✅ 当前方案 |
| B | 结构化数据（List/Map） | ❌ VM 支持有限 |
| C | 混合（热点路径用字符串，冷路径用结构化） | ⚪ 未来可考虑 |

**决策**：选项 A。

**理由**：
1. 与 Ast/Hir/Mir/AOT 各阶段采用同一策略，保持一致性
2. 字符串在 Aura VM 中有完善支持
3. 待 VM 对集合类型支持完善后可逐步迁移

### 8.4 决策 4：为什么字节码契约与 VM 统一（Phase 9）

**背景**：早期设计有独立的「引导指令集」，与 VM 字节码不同。

**决策**：Phase 9 统一为「JIT 直接消费与 VM 相同的字节码」。

**理由**：
1. 避免维护两套指令集
2. JIT 预解码阶段处理指令集差异
3. 常量以字面量内联，分支目标在预解码阶段由绝对行号转为相对偏移

### 9.1 技术方案核心
