## 二、技术风险详解

### R1：Clif IR 格式与 Cranelift 0.116 不兼容

**描述**：`JitLower.aura` 输出的 Cranelift 文本 IR（.clif）格式可能与实际 Cranelift 0.116 编译器不兼容。

**影响**：S2 阻塞——.clif 无法被 Cranelift 编译，后续 FFI 边界无法实现。

**根因分析**：
- Cranelift 文本 IR 格式可能随版本变化
- `JitLower.aura` 的实现可能遗漏某些格式要求（如基本块标签格式、SSA 值命名规则）
- Cranelift 对 .clif 的解析可能比预期严格

**缓解措施**：
1. **S2 预留 2 天修复时间**（已包含在 S2 工作量估算中）
2. **参考 Cranelift 官方文档**：`cranelift/codegen/src/isa/` 下的 .clif 测试用例
3. **渐进式验证**：从最简单的函数（`add(a, b)`）开始，逐步增加复杂度
4. **格式对比**：将 `JitLower.aura` 输出与 Cranelift 内置的 `.clif` 测试文件逐字节对比

**回退策略**：
- 如果格式差异无法在 2 天内修复，回退到 S1，暂不推进 S2
- 记录所有格式差异到 `05-风险与开放问题.md`
- 等待 Cranelift 文档更新或社区反馈

**触发条件**：S2 验证时 10 个 .clif 中 >3 个编译失败。

**当前状态**：⚠️ 未验证（S2 待开始）

### R2：FFI 边界数据格式不匹配

**描述**：纯 Aura 侧与 Rust FFI 边界之间的数据格式（字符串编码、记录表格式）可能不匹配。

**影响**：S3 阻塞——FFI 调用失败，JIT 编译/装载/调用全部不可用。

**根因分析**：
- 字符串编码差异（UTF-8 vs UTF-16 vs CStr）
- 记录表格式差异（`key|value` vs `key=value` vs 其他）
- 数值范围差异（i64 vs i32 vs u64）
- 换行符差异（`\n` vs `\r\n`）

**缓解措施**：
1. **S0 定义清晰的字符串格式契约**（已在 `02-技术方案.md` §四 定义）
2. **FFI 函数输入输出均为 CStr**（`*const c_char`），避免编码差异
3. **base64 编码**机器码 blob，避免二进制数据跨 FFI 边界
4. **记录表格式**统一为 `key|value1|value2...`，与 `JitUtil.aura` 一致

**回退策略**：
- 如果 FFI 调用失败，检查数据格式
- 逐步简化：先用最简格式（单个整数参数）验证 FFI 通路
- 记录格式差异到文档

**触发条件**：S3 FFI 单元测试中 >3 个用例失败。

**当前状态**：⚠️ 未验证（S3 待开始）

### R3：mmap 在目标平台失败

**描述**：`jit_load` 中的 mmap 调用可能在目标平台（特别是 Windows）失败。

**影响**：S3 阻塞——机器码无法装载到可执行内存。

**根因分析**：
- Windows 使用 `VirtualAlloc` 而非 `mmap`，API 不同
- macOS 的 mmap 行为可能与 Linux 不同
- 某些平台禁止可写可执行内存映射（W^X 限制）

**缓解措施**：
1. **Cranelift 已处理跨平台 mmap**：`JITModule` 内部处理平台差异
2. **先在 Linux/macOS 验证**：S3 初期在 POSIX 平台验证
3. **Windows 后补**：S3 后期补充 Windows 支持
4. **错误处理**：mmap 失败返回空字符串，纯 Aura 侧回退解释器

**回退策略**：
- 如果 Windows mmap 失败，暂不支持 Windows JIT
- 记录平台差异到文档
- 等待 Cranelift 更新或社区反馈

**触发条件**：S3 在 Windows 上 `jit_load` 返回空串。

**当前状态**：⚠️ 未验证（S3 待开始）

### R4：派发接线引入回归

**描述**：S4 将 JIT 派发接线到 VM 路径，可能引入回归（如非 JIT 函数执行异常、VM 解释器路径被破坏）。

**影响**：S4 阻塞——VM 解释器路径被破坏，现有功能失效。

**根因分析**：
- 派发接线可能修改 VM 核心路径
- JIT 启用标志可能影响非 JIT 函数执行
- 状态管理（`JitState`）可能与 VM 帧管理冲突

**缓解措施**：
1. **保留 VM 回退路径**：JIT 失败时自动回退解释器
2. **逐步接线**：先接线单个函数，验证无回归后再扩展
3. **独立桥接层**：`VmJitBridge.aura` 作为独立模块，不修改 VM 核心
4. **完整回归测试**：接线后运行 `bootstrap_c4_tests.aura` 等自举测试

**回退策略**：
- 如果接线引入回归，回退到 S3
- 删除 `VmJitBridge.aura` 和 `Main.aura` 中的 JIT 集成代码
- 记录回归原因到文档

**触发条件**：S4 派发测试中 >3 个用例失败，或自举链断裂。

**当前状态**：⚠️ 未验证（S4 待开始）

### R5：JIT 性能不达标

**描述**：JIT 加速比未达到预期（< 1.3× VM），可能由于优化不足、派发开销大、或回退频繁。

**影响**：S5 验收失败——JIT 路径无实际性能收益。

**根因分析**：
- 优化传递（`JitOpt.aura`）可能不够激进
- FFI 调用开销大（字符串序列化/反序列化）
- 回退频繁（白名单限制、编译失败）
- 基准测试设计不合理（冷启动开销被计入）

**缓解措施**：
1. **逐步优化**：S5 预留 3 天优化时间
2. **基准测试设计**：预热 100 次，测量 1000+ 次迭代
3. **性能剖析**：使用 `perf` / ` VTune` / `Instruments` 定位瓶颈
4. **必要时回退**：如果性能不达标，JIT 启用为可选项，默认 VM

**回退策略**：
- 如果性能 < 1.3× VM，记录到性能报告
- JIT 启用为可选项（`--enable-jit`），默认 VM
- 不阻塞 S5 验收（验收标准为「可运行」，非「必须加速」）

**触发条件**：S5 性能基准中平均加速比 < 1.3× VM。

**当前状态**：⚠️ 未验证（S5 待开始）

### R6：自举产物启用 JIT 失败

**描述**：自举产物（`aura-compiler-native2.exe`）启用 `--features jit` 后，运行时 JIT 路径可能失败。

**影响**：S5 验收部分失败——自举联动验证不通过（但 JIT 性能基准仍可验收）。

**根因分析**：
- 自举产物可能未链接 Cranelift
- 自举产物运行时可能无法调用 FFI 边界
- 自举产物的字节码格式可能与 JIT 预期不匹配

**缓解措施**：
1. **自举产物 JIT 启用为可选项**：不强制要求，仅验证可行性
2. **逐步验证**：先验证 FFI 边界可调用，再验证完整 JIT 路径
3. **记录差异**：如果失败，记录原因到性能报告

**回退策略**：
- 如果自举产物 JIT 失败，标记为「已知限制」
- 不阻塞 S5 验收（性能基准为硬性标准，自举联动为软性标准）

**触发条件**：S5 自举联动验证中 Stage-3/4 失败。

**当前状态**：⚠️ 未验证（S5 待开始）

## 三、ABI 漂移风险

### 3.1 风险描述

JitValue ABI（13 个类型标签 + 16 字节结构体 + 入口签名）是纯 Aura 侧与 Rust FFI 边界的**核心契约**。任何一侧的标签值变化都会导致**静默错误**（机器码执行崩溃或结果错误）。

### 3.2 漂移场景

| # | 场景 | 影响 | 检测难度 |
|---|------|------|---------|
| 1 | 新增类型标签（如 TAG_TUPLE = 13） | Rust 侧不认识新标签，执行崩溃 | 中（可通过标签范围检查） |
| 2 | 标签值重排（如 INT = 1, FLOAT = 0） | 所有数据错位，静默错误 | 高（需逐标签验证） |
| 3 | 结构体大小变化（如 16 → 20 字节） | 内存越界，崩溃 | 中（可通过大小检查） |
| 4 | 入口签名变化（如增加参数） | 调用约定不匹配，崩溃 | 中（可通过签名检查） |

### 3.3 缓解措施

1. **S0 不变量断言**：30 项不变量锁定所有标签值、结构体大小、签名（见 `04-测试与验收矩阵.md` §二）
2. **版本字段**：`JitAbi.aura` 增加 `JitTags.VERSION` 常量，FFI 边界检查版本
3. **编译时检查**：Rust 侧 `jit_ffi.rs` 编译时检查 `JitValue` 大小 = 16
4. **运行时检查**：`jit_compile` 调用前检查版本一致性

### 3.4 版本管理

```text
JitTags.VERSION = "1.0.0"  // 语义化版本

// 版本变更规则：
// - 新增标签（向后兼容）：minor 版本 +1
// - 标签值变化（不兼容）：major 版本 +1
// - 修复 bug：patch 版本 +1
```

### 3.5 当前状态

- ✅ S0 不变量断言已设计（30 项）
- ⏳ S0 实施中（待开始）
- ⚪ 版本字段（未来考虑）

## 五、开放问题

### Q1：Cranelift 文本 IR 格式是否有官方稳定版本？

**描述**：Cranelift 的 .clif 格式是否保证向后兼容？是否有稳定版本承诺？

**影响**：S2 的长期可维护性。如果格式频繁变化，每次升级都需要重新验证。

**当前理解**：
- Cranelift 是 Bytecode Alliance 项目，Wasmtime 使用它
- .clif 格式主要用于测试，不是正式 API
- 没有明确的向后兼容承诺

**建议**：
- 锁定 Cranelift 0.116 版本
- 升级前必须重新运行 S2 验证
- 考虑使用 Cranelift 的 Rust API 而非文本 IR（但会增加 FFI 边界复杂度）

**状态**：⚪ 待确认（需查阅 Cranelift 文档或联系 Bytecode Alliance）

---

### Q2：JIT 是否应该支持 Windows 平台？

**描述**：Windows 使用 `VirtualAlloc` 而非 `mmap`，Cranelift 是否已处理？

**影响**：S3 的平台覆盖范围。

**当前理解**：
- Cranelift 的 `JITModule` 已处理跨平台 mmap
- 但 `jit_ffi.rs` 可能需要额外的 Windows 适配
- Aura 项目已有 Windows 开发环境（用户工作目录为 `D:\Code\AuraLang`）

**建议**：
- S3 初期在 Linux/macOS 验证
- S3 后期补充 Windows 支持
- 如果 Windows mmap 失败，标记为「已知限制」

**状态**：⚪ 待验证（S3 实施时确认）

---

### Q3：JIT 白名单是否应该扩展？

**描述**：当前白名单不含 `CallMethod`（虚方法调用）、`PushHandler`（异常处理），是否应该扩展？

**影响**：JIT 覆盖率。当前白名单限制导致面向对象热点函数和含 try/catch 的函数无法 JIT 编译。

**当前理解**：
- 白名单限制是**有意为之**，避免复杂的对象布局或异常处理支持
- 扩展白名单需要 FFI 调用支持完善
- 当前可接受，VM 回退解释器保证语义

**建议**：
- 当前阶段不扩展白名单
- 记录为「未来改进」
- 待 FFI 调用支持完善后逐步扩展

**状态**：📝 已记录，当前不处理

---

### Q4：JIT 优化传递是否与 Rust `jit_opt.rs` 语义一致？

**描述**：`JitOpt.aura` 的 7 个优化传递是否与 Rust `compiler/src/vm/jit_opt.rs` 语义一致？

**影响**：S1 单元测试的准确性。如果优化语义不一致，测试用例的预期输出可能错误。

**当前理解**：
- `JitOpt.aura:24-34` 明确记录了与 Rust 基线的差异（有意为之，语义等价且更严格）
- 差异点：常量折叠单遍实现、强度削弱操作数顺序、内联候选判定
- 这些差异是**改进**，不是 bug

**建议**：
- S1 测试用例按 `JitOpt.aura` 的语义设计，而非 Rust 基线
- 如果需要差分验证，在 S4 阶段做端到端对比
- 记录差异到文档

**状态**：✅ 已记录（`JitOpt.aura:24-34`）

### Q5：JIT 是否应该支持去优化（Deoptimization）？

**描述**：当前设计由 FFI 返回 Deopt 信号，纯 Aura 侧简化处理。是否需要更完善的去优化支持？

**影响**：JIT 的鲁棒性。如果 JIT 代码执行失败，需要回退解释器。

**当前理解**：
- `JitDispatch.aura:12-16` 已实现「不可编译函数永久回退解释器」
- FFI `jit_call` 返回 `"DEOPT"` 标记表示去优化
- 纯 Aura 侧可简化处理：收到 DEOPT 后回退解释器

**建议**：
- 当前阶段简化处理（收到 DEOPT 回退解释器）
- 未来可考虑更完善的去优化（如栈展开、状态恢复）
- 记录为「未来改进」

**状态**：📝 已记录，当前简化处理

---

### Q6：JIT 是否应该支持并发编译？

**描述**：多线程同时触发 JIT 编译时，是否需要并发支持？

**影响**：S3 的并发安全性。

**当前理解**：
- Cranelift 的 `JITBuilder` 不是线程安全的
- `jit_ffi.rs` 需要用 `Mutex` 保护全局状态
- 当前设计：`LOADED_MODULES` 用 `Mutex<HashMap>` 保护

**建议**：
- S3 实现时用 `Mutex` 保护全局状态
- S3 包含并发测试用例（见 `04-测试与验收矩阵.md` §五）
- 未来可考虑线程本地 JITBuilder（性能优化）

**状态**：📝 已记录，S3 实施时处理

---

### Q7：JIT 是否应该支持垃圾回收？

**描述**：JIT 编译的机器码是否需要垃圾回收？

**影响**：内存管理。

**当前理解**：
- 当前设计：`jit_load` 返回 token，但不提供 `jit_unload`
- 机器码在进程生命周期内保留（不卸载）
- 对于编译器进程，这是可接受的（编译完成后退出）

**建议**：
- 当前阶段不实现 `jit_unload`
- 记录为「未来改进」
- 如果需要，未来添加 `jit_unload(token)` FFI 函数

**状态**：📝 已记录，当前不处理

| Q7 | 不支持垃圾回收 | 编译器进程生命周期内保留，可接受 | 本文档 §五 Q7 |

### 6.2 未接受的风险（必须解决）

| # | 风险 | 原因 | 解决方案 |
|---|------|------|---------|
| R1 | Clif IR 格式不兼容 | S2 阻塞，无法推进 | S2 预留 2 天修复 |
| R2 | FFI 数据格式不匹配 | S3 阻塞，无法推进 | S0 定义清晰契约 |

| R7 | ABI 漂移 | 静默错误，难以检测 | S0 不变量断言锁定 |
