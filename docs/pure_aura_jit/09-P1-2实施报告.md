## 一、结论

JIT 的机器码装载从「把占位符原样写进可执行内存」变成「回填后再切 RX」，
闭环成立：

```text
compileEncodeOnly  ── machineCodeHex（含 00 00 00 00 占位符）
                 ── relocRecords      "104|double|R_X86_64_REL32;126|exit|R_X86_64_REL32"
                 ── funcNameOffsets   "double|0;main|60"
                 ── funcOffsets / stringConsts / relocationCount
                          │
                          ▼
emitFunctionRelocated
  1. allocateExecMemory      → base（RW）
  2. writeCode(base+off, hex)
  3. JitRelocationUtils.applyRelocations   ← 回填（本阶段新增）
       ├─ R_X86_64_REL32 : write32(base+off+off, target - (base+off+off+4))
       ├─ R_X86_64_64    : write64(base+off+off, target)
       ├─ R_X86_64_DATA  : 需 dataBase，未分配则跳过（不写错值）
       └─ 未知符号 / 越界 : 跳过并计数
  4. setExecutable(base, size)   → RX（真正的 W^X）
  5. return base + off
```

**测试**：`p12_relocation_test.aura` 24/24 + `p12_jit_pipeline_test.aura` 31/31 全绿；
既有套件零回归（`S1/02_x86_encoder_relocs` 4/4、`S3/08_jit_pipeline_test` 33/33、
`P1/05_functions` 输出一致）。

### 2.3 修改 `X86Emitter.aura`

**分隔符从 `|` 改为 `;`**（这是本阶段发现的真 bug，不只是文档缺口）：

```diff
-        if (i > 0) { parts.add("|") }   // ← 与字段分隔符同字符
+        if (i > 0) { parts.add(";") }
```

`getRelocRecords()` 的消费方 `PhotonObjectWriter.parseRelocEntries` 必须用
「无 `;` 时字段数整除 3」这种启发式才能切开——符号名一旦含 `|` 即崩，
且 JIT 路径无法复用这套启发式。`PhotonObjectWriterUtils.joinRelocRecords`
**早已用 `;`**，说明 AOT 组表路径与 X86Emitter 直出路径的格式本就分叉，
本改动让两者收敛到同一契约。新增 `getFuncNameOffsets()`（扁平表，供
JIT 符号解析用，与 COFF 的 `;;` 分组表区分）。

### 2.4 修改 `JitBackend.aura`

| 新增 | 说明 |
|---|---|
| `writeReloc32(addr, value)` | `Memory.write32`，vmMode 下跳过 |
| `writeReloc64(addr, value)` | `Memory.write64`，vmMode 下跳过 |
| `emitFunctionRelocated(name, hex, relocs, funcOffsets, dataBase)` | **缺口二**：写码 → 回填 → 切 RX |
| `compileMachineCodeResult(...)` | 返回完整 `BackendResult` |
| `lastRelocResult()` / `lastRelocSkippedCount()` | 诊断入口 |
| `getJitCodeLayout()` 附重定位统计 | `reloc total=N applied=M skipped=K` |

旧签名 `emitFunction(name, hex)` 保留为兼容入口（内部委托，不回填）。

**关键设计——段内偏移**：共享可执行内存里顺序追加多段时，
`applyRelocations` 收到的 `codeBase` 是**本段起点** `base + offset`，
不是共享内存基址。`relocRecords` 与 `funcNameOffsets` 都是段内偏移，
两者因此自洽——若用基址，第二段之后所有回填都会错位到第一段的字节上
（本阶段实测确认过这个陷阱，见 §四.2）。

## 三、验收证据

### 3.1 修复前的证据（真根因确认）

`fun main(): Int { return 42 }` 的 `compileEncodeOnly` 输出：

```text
RELOCS[]                    ← 修复前为空串
```

`fun double(a) + main 调 double(21)`：

```text
RELOCS[]                    ← 修复前为空串
```

即：**任何含跨函数调用或 runtime 调用的 JIT 码，`call` 指令的 4 字节位移
恒为 0** ⇒ 跳到下一条指令 ⇒ 必然崩溃。这正是 `fb01f22`
「完成 photon 后端 aot vm 模式，待修复 jit 模式无法执行问题」登记的问题。

### 3.2 修复后

```text
RELOCS[47|exit|R_X86_64_REL32]                        funcNameOffsets[main|0]
RELOCS[104|double|R_X86_64_REL32;126|exit|R_X86_64_REL32]  funcNameOffsets[double|0;main|60]
```

装载结果：`reloc total=2 applied=1 skipped=1`——`double` 被回填
（`disp = (base+60) - (base+104+4) = -48`），`exit` 为外部符号被计为
skipped（AOT 由链接器解析，JIT 需 Phase 1.4 的分派表间接调用或符号表）。

### 3.3 测试输出

```

=== P1-2 集成测试：Photon 管线 -> 装载 === RESULT pass=31 fail=0
```

## 四、实施中发现的问题

### 4.1 分隔符冲突是 latent bug，不是文档缺口

`08-缺口分析` §2.1 只说「`compileEncodeOnly` 没调 `getRelocRecords()`」，
但即使调了，返回的字符串也**无法按「偏移|符号|类型」解析**——
记录间分隔符与字段内分隔符同为 `|`。文档 §附录 A 的示例
`"0|main|RIP32;;56|helper|ABS64"` 用 `;;`，与实际输出的 `|` 不一致，
说明文档本身也记录了契约漂移。

### 4.2 「`codeBase` 是基址还是段起点」决定了正确性

多段共享内存场景下，`emitFunctionRelocated` 第一次把 `base + offset`
加成段内偏移是错的（第一段的偏移语义与第二段错位）。测试
`第二段重定位仍按段内偏移解析` 在修复前失败、修复后通过，
钉住了这个约定。文档 §8.3 描述的 `applyRelocations(base, ...)`
未区分「段基址」与「共享内存基址」，实现时必须显式约定。

### 4.3 外部符号（`exit` / `println`）在 JIT 模式无解析来源

Phase 1.2 只解析**本次编译批次内**的函数（`funcNameOffsets`）。
runtime 函数（`println` / `exit` / `Memory_*`）和字符串常量
（`@str.N`）在 JIT 模式下没有符号表——它们要么被计为 `skipped`
（当前行为，安全），要么需要 Phase 2 的数据段 + 符号表
（缺口五），要么走 Phase 1.4 的分派表间接调用。
本阶段**不做**这个决定，只保证「不写错值」：skipped 的条目
保持 `00 00 00 00`，不会指向内存中的错误位置。

   确认 `executeNative` 返回正确值。
