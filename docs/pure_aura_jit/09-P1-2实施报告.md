## 〇、P1-3 增补（Phase 1.4 + Phase 2.1）

### 0.1 结论

在 P1-2 的单段回填之上，补齐两个缺口：

1. **缺口四（Phase 1.4）**：`compileBatch` 把多个函数段**连续追加**在同一块可执行
   内存里，段间 `call rel32` 位移永不越界；外部符号（`exit` / `println` /
   `@str.N`）改为「跳到本块内的调用存根」，存根体 `mov rax, imm64; jmp rax`
   的目标地址留给调用方事后 `patchCallStubTarget` 回填。
2. **缺口五（Phase 2.1）**：`allocateDataMemory` / `writeDataSection`
   分配可读可写数据段，`R_X86_64_DATA` 重定位从此能被回填为
   `dataBase + offset`，不再一律跳过。

**测试**：`p13_batch_data_test.aura` 46/46 全绿；P1-2 的
`p12_relocation_test.aura` 24/24 + `p12_jit_pipeline_test.aura` 31/31 零回归；
`scripts/photon/run-tests.ps1` 全量套件 109 OK / 25 FAIL，与改动前基线**完全一致**
（那 25 项 FAIL 是环境性缺件，与本次改动无关）。

```text
compileBatch(sources, relocs, funcOffsets, names, stubCount)
  1. segmentOffsets / layoutSizes     → 段 0/16/32… 连续布局，16B 对齐
  2. allocateExecMemory(codeUsed + stubCount*12 + 64)   → 单块 RW
  3. writeCode(base + segOff_i, hex_i)                  → 各段代码
  4. applyBatch(base, segments, funcOffsets, dataBase,
                stubBase=base+codeUsed, stubCount)
       ├─ 命中本块符号   → call rel32 位移（相对块基址）
       ├─ 外部符号       → call rel32 → 本块内调用存根；stub 计数 +1
       ├─ DATA_REF       → write64(dataBase + off)（Phase 2.1 打通）
       └─ 未知/越界      → 跳过，保留 00 00 00 00（不写错值）
  5. setExecutable(base, size)        → 整块切 RX
  6. return [base + segOff_0, …]
```

### 0.2 关键设计决策

**（a）连续块 vs 逐段分配。** `emitFunctionRelocated`（P1-2）每次调用都可能
独立分配一块内存，两段相距 > 2GB 时 `call rel32` 位移必然越界。`compileBatch`
改为**一次性分配整块**、段间 16 字节对齐追加，位移范围收窄到 ±(块大小)，
物理上不可能越界。段间调用计数（`crossSegment`）在测试里被断言 `>= 2`，
专门钉住这条不变量。

**（b）偏移语义。** `relocRecords` 的 offset 是编码器视角的**模块内**偏移
（`enc.byteCount()` 累计）。多段写进连续内存后，各段的实际基址取决于前面
所有段的对齐后尺寸，因此 `compileBatch` 要把记录 offset 平移为段内偏移
（`off - firstModuleOff`）。单段编译时 `firstModuleOff == 0`，语义与
`emitFunctionRelocated` 完全一致。这个约定在代码里用注释钉住，避免下一个
改动人把「段基址」与「模块内偏移」混用（P1-2 已踩过一次坑，见 §4.2）。

**（c）存根长度是契约。** `CallStub.SIZE = 12`（`48 B8` + 8 字节 imm64 +
`FF E0`）、`IMM_OFFSET = 2` 必须与 `JitBackend.buildCallStub` 的输出长度一致——
`patchCallStubTarget` 按 `SIZE` 推进下一条存根的基址，长度漂移会让**后续**
回填落错段。测试里直接断言 `buildCallStub(0).length == CallStub.SIZE * 2`，
把这条隐式契约变成显式断言。

**（d）存根 imm64 不预填。** 外部符号在 JIT 模式下没有符号表来源，
`applyBatch` 只把 `call` 的 rel32 改成「跳到存根入口」，存根体内的
`imm64` 保持 `00 00 00 00 00 00 00 00`。调用方拿到真实地址后必须显式调用
`patchCallStubTarget`——传 `target == 0` 时**不写**，与 P1-2「不写错值」
原则一致，避免用零地址覆盖掉未来可能被回填的正确值。

**（e）数据段独立于代码段。** `allocateDataMemory` 复用 `allocateExecMemory`
（VM 模式下推进同一个 `simNextAddr`，原生模式下各自 `Memory.alloc`），
但**不推进 `usedSize`**——否则下一次 `compileBatch` 的扩容检查会把数据段
的空间误判为代码区已满。数据段保持 RW（不切 RX），便于持续写入。
幂等：已有数据段时返回既有基址，不重复分配。

## 一、结论

JIT 的机器码装载从「把占位符原样写进可执行内存」变成「回填后再切 RX」，
闭环成立：

```text
compileEncodeOnly  ── machineCodeHex（含 00 00 00 00 占位符）
                 ── relocRecords      "104|double|R_X86_64_REL32;126|exit|R_X86_64_REL32"
                 ── funcNameOffsets   "double|0;main|60"
                 ── funcOffsets / stringConsts / relocationCount
                          │
                          ▼
emitFunctionRelocated
  1. allocateExecMemory      → base（RW）
  2. writeCode(base+off, hex)
  3. JitRelocationUtils.applyRelocations   ← 回填（本阶段新增）
       ├─ R_X86_64_REL32 : write32(base+off+off, target - (base+off+off+4))
       ├─ R_X86_64_64    : write64(base+off+off, target)
       ├─ R_X86_64_DATA  : 需 dataBase，未分配则跳过（不写错值）
       └─ 未知符号 / 越界 : 跳过并计数
  4. setExecutable(base, size)   → RX（真正的 W^X）
  5. return base + off
```

**测试**：`p12_relocation_test.aura` 24/24 + `p12_jit_pipeline_test.aura` 31/31 全绿；
既有套件零回归（`S1/02_x86_encoder_relocs` 4/4、`S3/08_jit_pipeline_test` 33/33、
`P1/05_functions` 输出一致）。

## 四、实施中发现的问题

### 4.1 分隔符冲突是 latent bug，不是文档缺口

`08-缺口分析` §2.1 只说「`compileEncodeOnly` 没调 `getRelocRecords()`」，
但即使调了，返回的字符串也**无法按「偏移|符号|类型」解析**——
记录间分隔符与字段内分隔符同为 `|`。文档 §附录 A 的示例
`"0|main|RIP32;;56|helper|ABS64"` 用 `;;`，与实际输出的 `|` 不一致，
说明文档本身也记录了契约漂移。

### 4.2 「`codeBase` 是基址还是段起点」决定了正确性

多段共享内存场景下，`emitFunctionRelocated` 第一次把 `base + offset`
加成段内偏移是错的（第一段的偏移语义与第二段错位）。测试
`第二段重定位仍按段内偏移解析` 在修复前失败、修复后通过，
钉住了这个约定。文档 §8.3 描述的 `applyRelocations(base, ...)`
未区分「段基址」与「共享内存基址」，实现时必须显式约定。

### 4.3 外部符号（`exit` / `println`）在 JIT 模式无解析来源

Phase 1.2 只解析**本次编译批次内**的函数（`funcNameOffsets`）。
runtime 函数（`println` / `exit` / `Memory_*`）和字符串常量
（`@str.N`）在 JIT 模式下没有符号表——它们要么被计为 `skipped`
（当前行为，安全），要么需要 Phase 2 的数据段 + 符号表
（缺口五），要么走 Phase 1.4 的分派表间接调用。
本阶段**不做**这个决定，只保证「不写错值」：skipped 的条目
保持 `00 00 00 00`，不会指向内存中的错误位置。

## 七、原生运行时验证：实施记录（2026-10-08 完成）

§七旧版断言「PhotonHatCompile 忽略入口源文件、输出恒为固定 VM 自举
探针 → 原生验证被自举链阻塞」。真实根因有两层，均已修复：

1. **`PhotonHatCompile.aura` 忽略 `AURA_HAT_AURA` 等环境变量**——
   旧实现硬编码 `srcPath = "build/hat-vmhost/current.aura"`，脚本传入的
   入口源文件被静默丢弃。2026-10-03 探针矩阵记录的「`Env.get` 与

   **Photon 编译参数化原生 VM 宿主（`build/hat-vmhost/jit_vmhost.aura`）
   → `AURA_VM_SELFTEST=1` 运行内建 JIT 自检**（自检是宿主原生代码，
   直接驱动 JitBackend 完整链）。

### 7.4 遗留缺口（P5 清单，按阻塞程度排序）

1. **崩点随构建漂移（原生档）**：同一源码不同构建的原生宿主，JIT

3. **单例初始化缺失**：Aura 版 VmRunner 未实现 Rust VM 的

   解引用即崩。JitBackend 构造器曾试图读 `AURA_JIT` 参数，因此回退

4. **AucLoader 对宿主闭包尺寸脆弱**：宿主闭包含 JitBackend→
   PhotonPipeline 后，.auc 装载在解析期段错误（常量下标错位家族）。
   自检与 .auc 混跑（`AURA_VM_RUNAUC`）在 P5 前不承诺。
5. **compileBatch 原生路径**：重定位解析依赖 `String.substring`

## 七·七、P5-① 实证推进 + 编译期内存修复（2026-10-09 第四轮）

### A. 编译器内存超 10 GB——根因与修复

vmhost 闭包（jit_vmhost + VmRunner + JitBackend 全并集）经驱动编译时
峰值工作集 >10 GB，且第二轮构建 255 s 产出 0 字节 COFF。根因是发射
路径上**三处 O(N²) 字符串累加**（AOT 无 GC，全部中间串常驻）：

| 位置 | 旧形态 | 规模（vmhost 闭包） |
|---|---|---|
| `PhotonObjectWriter.appendFunction` | `textSection += hex` 整段拷贝 + `hexByteCount(textSection)` 每函数**全量扫描** | 数千函数 × 134 MB hex ⇒ 数百 GB 累计拷贝/扫描 |
| 同上 | `relocs += ";;" + entries` | 同族 |
| `X86Emitter.emitCall` | `stackMapRecs += ";" + seg`（**每 call 一条**） | O(call²) |
| `X86Emitter.getFuncOffsets`/`getFuncNameOffsets` | 循环 `out = out + ";;" + ...` | O(函数数²) |

修复：text/relocs/stackMaps 全部转 **List O(1) 追加 + 消费点一次物化**
（coffJoinList/joinPairwise 两两归并，O(总长·log N)）；`.text` 基准偏移
改运行计数。实测驱动峰值工作集 **>10 GB → ~3.8 GB**。

⚠️ 回归教训：`functions` 字段**必须保持直接拼接**——`buildSymbols` 的
调用方（PhotonRuntime ×3 / PhotonPipeline ×2）在组装期就把
`writer.functions` 当实参读走，片段化会让符号表拿到空串 → 链接期
`undefined symbol: Memory_alloc`（实测）。

### B. jit_vmhost 自检 §4 秒崩——手编机器码字节布局三连错

[ST] 探针逐语句定位：崩点在 §4 `allocRW` 之后、`writeCode` 之前。
逐字节核对（capsstone 语义手工复核）：

1. **双 jne**：`buildGuardHex` 已含 `jne rel32` 占位，自检又手工追加
   `0F8508000000` —— 快路径首字节被第二个 jne 占据。
2. **guardBase 错位**：`mov rax,rcx` = `48 89 C8` 是 **3 字节**，旧注释
   按 6 字节排布 → `patchGuardDeopt(be, gb+6, …)` 把 disp32 写到 gb+12
   （真 disp32 在 +11..14），并把 +15 的 `B8`（mov eax,1）覆写成 `00`
   → 快路径变成 `add [rcx],al`（rcx=100 → 写地址 100 → 段错误）。
3. **JitDeopt 常量错位**：`guardDeoptDispOffset` 6→**8**、
   `guardDeoptInsnEnd` 10→**12**（disp32 在 guard 序列 +8..11，非 +6）。
   p16 断言已同步（27/27 全绿）。

另修：patch 必须**先于** `Memory.mprotect(RX)`（mprotect 已是真
VirtualProtect，先保护后补丁 = 写只读页）。

**P5-① 新实证**：`「字面量」+ 跨文件调用结果` 的 strcat 实参物化在
特定布局下崩（§4 `const + buildGuardHex(100)`，allocRW 后 writeCode
前段错误）——§1-3 的 `var + 常量` / `常量 + var` 形态同构建全绿。
自检已改用纯字面量拼接规避；发射器根因（调用结果物化）仍开放。

### C. 「布局轮盘」重新定性

同一驱动二进制对同一源码的编译输出**逐字节确定**（连续 3 次构建
main COFF 均为 1,150,904 B）——历史上观察到的「同源码不同构建崩点
迁移」实为**驱动源码在两轮构建之间被修改**（二分调试）所致的伪随机。

#### A·补充二：编译内存根因定位闭环 + heapArena 迁移 .bss（同日第三轮）

**OOM 归因**（`AURA_MEM_STATS=1 + AURA_ATTR_DUMP=1 + LIMIT=8192` 故意 OOM，
取崩溃点分配画像）：alloc 57M 次 / **free 954 次**；单调用点
`aura_string_concat` 753 万次 / 6.8GB（IR 行文本拼装）；`aura_dup_n`
4728 万次 / 1.27GB（HAT 解析 substring 汤）；big-concat 表最大簇
= PeepholeOptimizer.joinList 线性累加（411MB×3926×6 RA ≈ 2.4GB）。
RA→函数经 hat-native.obj 符号表映射（obj/exe 段布局一致）。

**根因 3 实锤 + 修复**：runtime obj 67MB 中 .text 仅 9.7KB（217 桩正常），
**.data = 64MB+8.6KB**——`dataSymbolName` 声明 `heapArena:67108864`
（64MB 静态堆）且 writer 用零 hex 按声明大小补齐进文件。修复为 COFF
标准形态：小符号留在 .data（声明式数据合成零 hex，KB 级）；
**heapArena 拆到独立 `.bss` 节**（SizeOfRawData=分配量、
PointerToRawData=0、CNT_UNINITIALIZED_DATA）——链接器分配镜像空间、
加载器零填充，文件零字节。writer 新增 bssSymbolName/bssVirtualSize
支持（节号推算：.text(1)+.rdata+.data+.bss 顺序）。
**注意**：对象文件的节 VirtualSize 字段被链接器忽略（首版虚拟尾巴方案
实锤崩溃），未初始化数据必须走独立 .bss 节。

**结果**：runtime obj **67MB → 18KB**（139×）、jit_vmhost.exe
**67MB → 483KB**；驱动编译 vmhost 峰值 14.5GB → 12.46GB；
sum COFF-MAIN 与旧驱动逐字节一致（encoder/流式化零语义漂移）；
vmhost 自检第 1 次构建即过（虚拟尾巴堆实测可用：Heap.init +
sum(1e9)=499999999500000000 精确）；种子 p12/p13/p16 = 31/46/ALL。

**joinList 修复**：线性累加 → List+两两归并（手法同 joinPairwise）。

**剩余 12.4GB = 根因 1（管线 IR）**：7.5M 次 concat（6.8GB，IR 行文本）
+ 47M 次 dup_n（1.27GB，HAT 解析）+ ≤64B 小对象 56M 次（1.1GB），
free_calls≈0。修法 = 指令结构数组化 + 阶段边界回收（大工程，另列）；
终局 = ARC 接通。附：`aura_string_concat` 是**种子 AOT 路径**的字符串

SeedAOT 保留 cffi、PhotonAOT 零 cffi 的现状符合既定架构。

#### A·补充三：7.5M concat 站点定位 + unescape 修复（同日第四轮）
