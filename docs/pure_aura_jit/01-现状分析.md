## 一、三条执行路径总览

Aura 编译器存在三条并行执行路径，由不同 cargo feature 门控：

```text
                    ┌─────────────────────────────────────────────┐
                    │          源码 (.aura)                        │
                    └────────────────┬────────────────────────────┘
                                     ↓
                    ┌─────────────────────────────────────────────┐
                    │   前端：词法 → 语法 → AST → 语义 → HIR → MIR  │
                    │   （Aura 侧已完成，aura/.../compiler/）       │
                    └────────────────┬────────────────────────────┘
                                     ↓
                    ┌─────────────────────────────────────────────┐
                    │   字节码发射（Codegen.aura）→ .auc 模块       │
                    └────────────────┬────────────────────────────┘
                                     ↓
              ┌──────────────────────┼──────────────────────┐
              ↓                      ↓                      ↓
   ┌──────────────────┐   ┌──────────────────┐   ┌──────────────────┐
   │  VM 解释器         │   │  JIT（Cranelift）  │   │  AOT（LLVM）       │
   │  Vm.aura          │   │  JitLower.aura    │   │  Aot.aura         │
   │  ✅ 100%          │   │  + FFI 边界       │   │  + llc/clang      │
   │  默认开启          │   │  ⚠️ FFI 待开发    │   │  ⚠️ 85%           │
   └──────────────────┘   └──────────────────┘   └──────────────────┘
```

### 1.1 三种执行模式对比

| 维度 | VM 解释器 | JIT（Cranelift） | AOT（LLVM） |
|------|----------|------------------|-------------|
| **技术** | 栈式字节码 | Cranelift 0.116 | LLVM 23.1.0 文本 IR + 外部 llc/clang |
| **Aura 侧位置** | `aura/.../vm/` (7 文件) | `aura/.../jit/` (8 文件) | `aura/.../aot/` (16 文件) |
| **完成度** | ✅ 100% | ⚠️ 90%（FFI 待开发） | ⚠️ 85%（6.5 收尾） |
| **Feature 门控** | 默认开启 | `jit` | `llvm` |
| **触发时机** | 立即 | 热点阈值（默认 10000 次调用） | 编译期一次性 |
| **编译耗时** | 0 | 毫秒级（进程内） | 数百毫秒（外部进程） |
| **冷启动开销** | 低 | 中（首次编译） | 高（编译期） |
| **稳态性能** | 基线 | ~1.1–1.5× VM | ~1.05–1.15× VM |
| **可自举** | ✅（Aura 侧 `Vm.aura`） | ❌（依赖 Rust Cranelift） | ❌（依赖外部 llc/clang） |
| **本方案范围** | ✅ | ✅（纯 Aura 侧） | ✅ |

### 1.2 JIT 依赖清单（Cargo.toml）

```toml
cranelift = { version = "0.116", optional = true }
cranelift-jit = { version = "0.116", optional = true }
cranelift-module = { version = "0.116", optional = true }

# ...
jit = ["cranelift", "cranelift-jit", "cranelift-module"]
```

**版本锁定**：Cranelift 0.116（Bytecode Alliance），与 Wasmtime 同源。
**关键 API**：`cranelift::frontend::FunctionBuilder`、`cranelift_jit::JITModule`、
`cranelift_module::{Linkage, Module}`。

### 2.2 关键设计决策

#### 2.2.1 扁平字符串表示

所有 JIT 数据（指令序列、常量池、函数表、分发表）都用**扁平字符串**表示：

- **行表（lines）**：每行一项，`\n` 分隔（如指令序列、常量池）
- **记录表（record）**：每行 `key|value1|value2...`（如分发表、调用计数）
- **解码指令**：每行 `<Opcode> [arg1] [arg2]`（对应 Rust `Instr` 枚举）

**为什么**：当前 Aura VM 对 `List`/`Map` 的支持仍有限制（见 `aura/compiler/README.md`
「已知差异」节），Ast/Hir/Mir/AOT 各阶段均采用同一策略。这是**务实的过渡方案**，
待 VM 对集合类型支持完善后可逐步迁移到结构化数据。

#### 2.2.2 字节码契约（Phase 9 统一）

`JitCore.aura` 直接消费**与 VM 相同的字节码**（`Codegen.emit` 的产物），
不再有独立的引导指令集。常量以字面量内联，分支目标在预解码阶段由绝对行号转为本单元的相对偏移。

**识别的可编译指令**（白名单，共 37 项）：

```text
LoadConst, LoadVar, StoreVar,
Add, Sub, Mul, Div, Rem, Neg, Not,
Eq, Ne, Lt, Gt, Le, Ge,
And, Or, BitAnd, BitOr, BitXor, Shl, Shr,
Jump, JumpIfTrue, JumpIfFalse,
Return, ReturnUnit,
Call, CallNative, CallNativeArgs,
NewObject, NewArray, NewList, NewMap,
IncRef, DecRef, Retain, Release, DropRef
```

**拒绝（→ deopt）的指令**：`GET_FIELD`、`SET_FIELD`、`CallMethod`、`MakeClosure`、
`PushHandler`、`Yield` 等（这些需要复杂的对象布局或异常处理支持）。

#### 2.2.3 共享 ABI 契约

```text
JitValue = { tag: i64, payload: i64 }          // 16 字节，双字段

入口签名（VM/JIT/AOT 三路共用）：
  void entry(JitValue* args, JitValue* out, usize argc, void* dispatch_table)
```

**类型标签**（13 个，与 Rust `vm/abi.rs` 逐位一致）：

| Tag | 名称 | 载荷含义 |
|-----|------|---------|
| 0 | `INT` | 直接存储 i64 |
| 1 | `FLOAT` | 位模式（f64 的 bit pattern） |
| 2 | `BOOL` | 0/1 |
| 3 | `NULL` | 0（无载荷） |
| 4 | `STR` | 句柄/指针 |
| 5 | `PTR` | 裸指针 |
| 6 | `OBJ` | 对象句柄 |
| 7 | `FUNC` | 函数引用 |
| 8 | `ARRAY` | 数组句柄 |
| 9 | `LIST` | 堆列表句柄 |
| 10 | `MAP` | 堆 Map 句柄 |
| 11 | `CLOSURE` | 闭包句柄 |
| 12 | `CSTRING` | NUL 结尾字符串指针 |

#### 2.2.4 Cranelift 文本 IR 格式（.clif）

`JitLower.aura` 输出 Cranelift 文本 IR，格式示例：

```text
function %add(i64, i64, i64, i64) {
block0:
    ; LoadConst 0 -> 3
    v0 = iconst.i64 3
    ; LoadVar 0
    v1 = load.i64 local_payload[0]
    ; LoadVar 1
    v2 = load.i64 local_payload[1]
    ; Add
    v3 = iadd v1, v2
    ; Return
    store.i64 v3, out_payload
    return
}
```

**约定**：
- 局部变量以 `local_tag[s]` / `local_payload[s]` 表示（与 Rust 的 tag/payload 变量对等价）
- 运算栈以 `push/pop` 维护 SSA 值名（对应 Rust 的 `stack_slot` + `sp` 变量与 `MAX_STACK` 深度）
- 入口 ABI 与 `JitAbi` 一致：`(args_ptr, out_ptr, argc, dispatch_table)`

## 三、Bootstrap 边界分析

### 3.1 Bootstrap 层文件清单

位置：`compiler/src/bootstrap/`，9 个文件，~4000 行 Rust。

| 文件 | 职责 | 是否包含 Cranelift |
|------|------|-------------------|
| `mod.rs` | 模块导出 | — |
| `vm_core.rs` | 最小编译器 + VM + FFI 直连 | ❌ |
| `jit_core.rs` | 基线 JIT（预解码 + 回退解释器） | ❌ |
| `aot_core.rs` | LLVM IR 直发（调用 C 符号） | ❌ |
| `memory.rs` | malloc/free/arc/string_* | ❌ |
| `runtime.rs` | 协程 + 最小 GC | ❌ |
| `any_core.rs` | toString/equals/hashCode | ❌ |
| `type_core.rs` | typeOf/isOfType/cast | ❌ |
| `value_check.rs` | 空值/数值检查 | ❌ |

**关键发现**：bootstrap 层**完全不包含 Cranelift**——`jit_core.rs` 是「预解码 + 回退解释器」
的基线 JIT（`JitUnit` + `CInsn` 枚举），不调用任何机器码生成后端。

### 3.2 Bootstrap JIT 的能力边界

`compiler/src/bootstrap/jit_core.rs:8-13` 原文：

> 机器码后端（Cranelift）位于编译器主 VM（`vm::jit`），bootstrap 层保持零外部依赖；
> `JitUnit` 的预解码形态即未来传给机器码后端的输入。

**Bootstrap JIT 能做什么**：
- 热点检测（`hot_threshold` 默认 1000 次）
- 基线编译：字节码 → `JitUnit`（预解码 + 分支重解析 + 内联缓存槽位绑定）
- 去优化（deopt）：编译单元遇到不支持结构或运行期异常前置条件时回退解释器

**Bootstrap JIT 不能做什么**：
- ❌ 生成真正的机器码
- ❌ `mmap` 可执行内存
- ❌ 直接调用 Cranelift

### 3.3 Bootstrap 与完整 VM 的关系

```text
┌─────────────────────────────────────────────────────────────────┐
│  完整 VM（cargo build --features jit llvm）                       │
│  ┌───────────────────────────────────────────────────────────┐  │
│  │  compiler/src/vm/jit.rs (807 行)                           │  │
│  │  - Cranelift 编译                                           │  │
│  │  - mmap(RW) → copy → protect(RX)                          │  │
│  │  - dispatch_table + call_indirect                          │  │
│  └───────────────────────────────────────────────────────────┘  │
│                          ↑ 调用                                  │
│  ┌───────────────────────────────────────────────────────────┐  │
│  │  compiler/src/bootstrap/（9 文件，~4000 行）                │  │
│  │  - vm_core.rs + jit_core.rs（基线 JIT）                    │  │
│  │  - aot_core.rs + memory.rs + runtime.rs                    │  │
│  │  - any_core.rs + type_core.rs + value_check.rs            │  │
│  └───────────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────────┘
```

**关键点**：完整 VM 的 `vm/jit.rs` **不依赖** bootstrap 的 `jit_core.rs`。
两者是**并行实现**——完整 VM 走 Cranelift 机器码路径，bootstrap 走基线 JIT 路径。

## 四、历史结论：Fix A / Fix B

来源：`docs/JIT性能分析.md`，已在 `JitState.aura` 与 `JitDispatch.aura` 中移植。

### 4.1 旧 JIT「与解释器同速」的四点根因

| # | 根因 | 表现 |
|---|------|------|
| ① | 编译期内联删除了小函数调用点 | 被内联的函数不再触发热点计数 |
| ② | 入口函数（main）不参与热点计数 | main 内的循环热点永远无法触发 JIT |
| ③ | 递归热点被 `is_jit_compilable()` 白名单拒绝 | 递归函数（如阶乘）永远回退解释器 |
| ④ | 仅靠调用频率的检测对「循环热点」天然失效 | 单次调用内的循环热点无法触发 JIT |

### 4.2 两条修复

| 修复 | 位置 | 含义 | 覆盖根因 |
|------|------|------|----------|
| **Fix A** | `vm/mod.rs` `forceEntry()` | 入口函数忽略调用阈值，首次运行时强制编译 | ②④ |
| **Fix B** | `vm/jit.rs` 白名单 + 递归编译 | `Call` 纳入白名单，沿调用图后序编译被调用者，配合 `dispatch_table` + `call_indirect` 支持递归/互递归 | ③ |

### 4.3 纯 Aura 侧的移植

`JitState.aura` 与 `JitDispatch.aura` 已完整移植两条修复：

- **Fix A**：`JitDispatch.aura` 的 `jitDecide` + `jitTryCompile` 支持「入口强制编译」
  （`jitCanForce` 判断未编译且未跳过的函数可强制编译）
- **Fix B**：`JitState.aura` 的 `JitCompilePlanner` 类实现后序编译顺序
  （`plan(funcs, idx)` 返回被调用者先于调用者的后序序列）

**验证**：`JitState.aura:352-402` 的 `JitCompilePlanner` 与 Rust `vm/jit.rs` 的
`try_jit_compile` 逻辑一致——「先递归编译被调用者，再编译自身」。

## 五、当前阻塞与差距

### 5.1 阻塞项

| # | 阻塞项 | 位置 | 影响 |
|---|--------|------|------|
| B1 | Cranelift 编译 + mmap 装载无法在纯 Aura 侧完成 | 物理限制 | 必须通过 FFI 边界 |
| B2 | Aura VM 对 `List`/`Map` 支持有限 | `aura/compiler/README.md` | 所有 JIT 数据必须用扁平字符串表示 |
| B3 | `JitRuntime.aura` 只有描述，无实际 mmap 实现 | `JitRuntime.aura:88-96` | W^X 装载走 FFI，纯 Aura 侧无法验证 |

### 5.2 差距项（已识别但未阻塞）

| # | 差距 | 影响 | 缓解 |
|---|------|------|------|
| G1 | JIT 白名单不含 `CallMethod`（虚方法调用） | 面向对象热点函数无法 JIT 编译 | 当前可接受，待 FFI 调用支持完善后扩展 |
| G2 | JIT 白名单不含 `PushHandler`（异常处理） | 含 try/catch 的函数无法 JIT 编译 | 当前可接受，VM 回退解释器保证语义 |
| G3 | `JitLower.aura` 的 Cranelift IR 尚未与实际 Cranelift 编译器联调 | 文本 IR 格式可能与实际 cranelift 版本不一致 | 需在 S3 阶段用 Rust 侧 cranelift 验证 |
| G4 | `JitOpt.aura` 的 7 个优化传递未与 Rust `jit_opt.rs` 做差分验证 | 优化结果可能不一致 | 需在 S4 阶段做逐 pass 差分测试 |
| G5 | 纯 Aura 侧 JIT 尚未接入 VM 派发路径 | 纯 Aura 编译器产出的程序无法触发 JIT | 需在 S5 阶段完成派发接线 |

### 5.3 自举链联动

自举闭环已跑通（`docs/pure_aura/03-自举验证报告.md:5-48`）：

```text
Stage-1: Rust 编译器编译 Aura 编译器源码 → aura-compiler-native.exe（原生载体）
Stage-2: 原生载体编译自身 → aura-compiler-native2.exe（自举产物）
Stage-3: 自举产物编译用户程序（含 @native FFI）→ 用户 exe
```

**关键事实**：Stage-2/3 用的是 **AOT（LLVM）后端**，不是 JIT。
JIT 是运行时优化，自举链只验证编译期能力。
