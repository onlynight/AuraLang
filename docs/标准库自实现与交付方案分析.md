# Aura 标准库自实现与交付文件方案分析

> **分析范围**：标准库是否应使用 Aura 自身语言实现，以及编译后应生成哪些交付文件。
> **约束**：本文仅提供分析与建议，不修改任何代码。

---

## 1. 现状架构总览

### 1.1 标准库的三层实现

当前 Aura 标准库存在**三套并行实现**，分别服务于不同的编译模式：

| 层次 | 文件 | 语言 | 用途 | 规模 |
|------|------|------|------|------|
| **A. Rust 实现（VM 后端）** | `compiler/src/std/std_*.rs` | Rust | 字节码/JIT 模式下 VM 调用 | 20 模块 / ~330 函数 |
| **B. C 实现（AOT 后端）** | `compiler/src/std/cffi/aura_std_cffi.c` | C | AOT 编译后原生代码链接 | ~30 函数（不完整） |
| **C. 声明元数据** | `compiler/src/std/decl.rs` | Rust | 编译期单一真相源 | 338 个函数名 |

**设计原则**：「按需免import + 按需链接」——17 个 prelu 函数免import，320+ 命名空间函数需 `import`。

### 1.2 编译/交付路径

```
Aura 源码 (.aura)
  │
  ├─► 字节码模式 ──► .auc ──► Aura VM 解释 ──► 调用 Rust NativeRegistry
  │                                      └──► 调用 CFFI 运行时 (C)
  │
  ├─► JIT 模式 ──► 热点函数 → Cranelift 机器码 ──► 链接 Rust 运行时
  │
  └─► AOT 模式 ──► LLVM IR ──► llc/clang ──► .o/.exe ──► 链接 aura_std_cffi.c
```

## 2. 核心问题分析

### 2.1 问题一：标准库应该用 Aura 自身实现吗？

**结论：不应该。应保持当前的 Rust + C 双实现架构。**

#### 理由

**（1）语言自举的代价与收益不匹配**

Aura 当前处于 P4–P10 阶段，编译器前端已完成、字节码 VM 已可运行、AOT 后端已可生成原生代码，但标准库的语义覆盖（集合、泛型、协程、Actor、异常）尚未完全实现。在此阶段用 Aura 重写标准库面临以下**鸡生蛋问题**：

- **集合类型依赖**：`std.collections`（List/Map/Set）是大量 API 的基础，但集合类型需要在编译器和 VM 中先有完整实现
- **泛型单态化依赖**：`std.iter` 的 `map/filter/fold` 等泛型高阶函数需要编译器完整支持泛型单态化
- **协程/Actor 运行时**：`std.concurrent` 依赖 VM 的协程调度器和 Actor 消息队列，这些是 Rust 中手写的，无法用 Aura 自举

如果强行用 Aura 实现，需要先完成：完整的集合类型 → 泛型 → 闭包/高阶函数 → 迭代器 → 协程运行时 → 异常处理 → 反射 → 字符串内建优化 → 垃圾回收/ARC。这至少需要额外 **2–3 个月**的编译器工作，且产出不会优于当前的 Rust 实现。

**（2）Rust 实现的优势明确**

| 维度 | Rust 实现（当前） | Aura 自举 |
|------|:----------------:|:----------:|
| 开发效率 | 利用成熟 crate（serde/regex/base64） | 从零实现 |
| 性能 | Rust 原生速度 | 字节码解释/JIT，慢 2–5x |
| 调试 | Rust 调试器 | 需 Aura 调试器 |
| 安全 | Rust 内存安全 | 需 ARC + 逃逸分析 |
| 生态复用 | 直接调 libc / OS API | 需 Aura FFI 完善 |
| 维护 | Rust 社区支持 | 仅 Aura 维护者 |

**（3）自举不是目标，而是远期副产品**

语言自举（bootstrap）是**成熟度的标志**，而非开发目标。参考：

- **Rust**：自举用 LLVM 完成，标准库用 Rust 实现但**不依赖自身编译器**（先有 rustc-beta）
- **Kotlin**：标准库用 Kotlin 实现，但依赖 Kotlin 编译器 + JVM 运行时
- **Go**：标准库用 Go 实现，自举需要 go1.19 之前的预编译 go 二进制
- **Lua**：标准库用 C 实现，核心用 C 实现

Aura 的定位是**系统级脚本语言**，对标 LuaJIT + Python 开发体验。这意味着：
- 标准库应该**直接调用 OS API**（不经过中间层）
- 运行时是**宿主环境的**（Rust 编译器 + 目标平台 libc）
- **没有独立运行时**的自举语言（如 Swift/WASM 语言）才考虑完全自举

**（4）当前的 CFFI 层已经接近"自举"的效果**

`aura_std_cffi.c` 实现了纯 C ABI 的标准库函数，AOT 编译后直接链接，不依赖 Aura VM。这相当于：
- 字节码模式：标准库 = Rust 实现（VM native）
- AOT 模式：标准库 = C 实现（原生链接）

这种双轨制已经是**最务实的方案**——不同编译模式使用最适合的实现。

### 2.2 问题二：编译后应生成哪些交付文件？

**结论：当前交付方案过于复杂，应简化为分层交付模型。**

#### 当前交付设计的问题

现有设计中提到的交付物包括：

```
当前规划中的 .auz 包含：
├── META-INF/         # 元数据
├── lib/              # 字节码（.auc）
├── ref/              # 类型签名（.sig）
├── native/           # AOT 原生库（多平台）
├── src/              # 源码附件
├── docs/             # 文档
├── resources/        # 资源
└── test/             # 测试
```

问题分析：
1. **交付物过多**：标准库本身不应打包为 `.auz`（它是编译器/VM 内置的，不是外部依赖）
2. **类型签名过早**：`.sig` 文件依赖跨模块类型检查能力，当前编译器尚未实现
3. **AOT 包过于宏大**：多平台原生库（x86_64/aarch64/armv7）需要持续维护多套编译产物
4. **标准库 ≠ 第三方库**：标准库的分发模型应与第三方库截然不同

## 3. 建议方案

### 3.1 标准库实现策略：保持双轨制 + 分阶段演进

#### 架构原则

```
┌─────────────────────────────────────────────────────────┐
│                     标准库实现层                           │
├──────────────┬──────────────┬─────────────────────────────┤
│  Rust 实现   │  C 实现      │  (远期) Aura 实现           │
│  (VM 后端)   │  (AOT 后端)  │  (成熟后自举)               │
├──────────────┼──────────────┼─────────────────────────────┤
│  优先级：高   │  优先级：高   │  优先级：低（远期）          │
│  覆盖：全部   │  覆盖：核心   │  覆盖：纯逻辑模块            │
├──────────────┼──────────────┼─────────────────────────────┤
│  场景：字节码 │  场景：AOT    │  场景：无 VM 依赖场景       │
│         JIT  │  原生执行     │  （纯编译，无解释器）        │
└──────────────┴──────────────┴─────────────────────────────┘
```

#### 分阶段演进路线

**Phase A（当前）：Rust 为主，C 为辅**
- Rust 实现覆盖所有 std 模块（已完成，330+ 函数）
- C 实现覆盖 AOT 编译需要的核心函数（当前 ~30 个，需补齐）
- **目标**：CFFI 实现与 Rust 实现**功能对齐**

**Phase B（中期）：完善 CFFI 覆盖**
- 补齐 `aura.lang.std.FileSystem`（文件操作）、`aura.lang.std.Encoding`（base64/hex）、`aura.lang.std.Json`（JSON）、`aura.collection`（基础集合）的 C 实现
- 引入 `aura_std` 运行时库（静态库，AOT 链接用）
- **目标**：AOT 编译后的二进制不依赖 Aura VM，自成一体

**Phase C（远期）：选择性 Aura 实现**
- 仅对**纯逻辑、无系统调用**的模块考虑 Aura 实现：
  - `aura.lang.std.Iter`（迭代器/函数式）
  - `aura.lang.std.Collections`（集合辅助，非核心容器）
  - `aura.lang.std.Assert` / `aura.lang.std.Test`（测试断言）
- 前提：编译器完整支持泛型 + 高阶函数 + 集合类型
- **目标**：展示 Aura 自举能力，非实用目标

#### 不建议的做法

| 方案 | 不推荐原因 |
|------|-----------|
| 全部用 Aura 实现标准库 | 自举周期过长，当前编译器尚不支持所需的语言特性 |
| 全部用 C 实现标准库 | 失去 Rust 的类型安全和内存安全，OS API 调用需大量样板代码 |
| 标准库用 Rust 编译为 C | 增加编译复杂度，失去 Rust → C ABI 的类型映射优势 |

### 3.2 交付文件策略：分层交付模型

#### 核心理念

标准库不应该被打包为 `.auz`（那是第三方库的格式）。标准库的分发应分为**三个层次**：

```
层次 1：编译器内置（VM Native）
  → 编译进 aura-compiler 二进制
  → 用户不需要单独安装
  → 字节码/JIT 模式使用

层次 2：AOT 运行时库（C 静态库 + 头文件）
  → 随编译器工具链分发
  → AOT 编译时链接
  → 产出的 .exe 不依赖 Aura VM

层次 3：标准库源码（可选，仅用于自举/IDE 跳转）
  → 随源码仓库分发
  → IDE/LSP 跳转定义
  → 开发者参考
```

#### 交付文件详细设计

```
aura-toolchain-{version}/               # 完整工具链分发
│
├── bin/                                # ── 可执行文件 ──
│   ├── aura                           # CLI（compile/run/build）
│   ├── aura-compiler                  # 编译器库（libcompiler.a）
│   └── aura-vm                        # VM 解释器（libloom.a）
│
├── lib/                                # ── 标准库交付 ──
│   ├── runtime/                       # AOT 运行时库
│   │   ├── aura_std.c               # C 标准库实现
│   │   ├── aura_std.h               # C 头文件（声明）
│   │   ├── aura_runtime.c           # ARC/内存/字符串运行时
│   │   ├── aura_runtime.h
│   │   └── libaura_std.a            # 预编译静态库
│   │
│   ├── native/                        # 平台特定原生库
│   │   ├── x86_64-pc-windows-msvc/
│   │   │   └── aura_std.lib
│   │   ├── x86_64-unknown-linux-gnu/
│   │   │   └── libaura_std.so
│   │   └── aarch64-unknown-linux-gnu/
│   │       └── libaura_std.so
│   │
│   └── bytecode/                      # 标准库字节码（VM 模式）
│       ├── aura_std.auc              # 编译好的标准库字节码
│       └── index.json                # 模块索引
│
├── include/                            # ── 头文件（AOT 开发用）──
│   ├── aura.h                         # Aura 运行时 API
│   ├── aura_std.h                     # 标准库 C API
│   └── aura_runtime.h
│
└── docs/                               # ── 文档 ──
    ├── std-api.html                   # 标准库 API 文档
    └── examples/
```

#### 简化为最小交付集

**开发者日常使用只需**：

| 场景 | 交付物 | 大小 |
|------|--------|------|
| 安装编译器 | `aura` CLI 二进制 | ~5–10 MB |
| 字节码运行 | VM 内置 std（自动） | 零额外文件 |
| AOT 编译 | 链接 `libaura_std.a` + 头文件 | ~500 KB |
| 多平台分发 | 对应平台的 `native/{triple}/` | 每平台 ~300 KB |

#### 与当前 .auz 设计的关系

**`.auz` 格式仅用于第三方库分发**，标准库不使用 `.auz`：

```
标准库：嵌入编译器 / 作为 C 静态库分发
第三方库：用 .auz 格式分发（含 lib/*.auc + ref/*.sig + native/）
```

## 4. 补充建议

### 4.1 CFFI 实现需补齐的模块

当前 `aura_std_cffi.c` 仅覆盖约 30 个函数，需要补齐：

| 模块 | 已实现 | 需补齐 | 优先级 |
|------|:------:|:-------:|:------:|
| prelu（17 个） | ~10 | CString / CStr / ptrIsNull / ptrToInt / intToPtr / makeCallback | 高 |
| aura.lang.std.IO | ~4 | readLine / readAll / flush / writeText / writeBytes | 高 |
| aura.lang.std.Math | ~10 | cbrt / round / trunc / atan2 / INT_MAX / INT_MIN / FLOAT_MAX / sign / clamp | 中 |
| aura.lang.std.String | ~10 | split / join / replaceAll / padStart / padEnd / escape / unescape / indexOf / lastIndexOf / countChar / first / last / isBlank / matches / containsAny / containsAll | 中 |
| aura.lang.std.FileSystem | 0 | exists / readText / writeText / readBytes / writeBytes / delete / mkdir / listDir / fileSize | 高 |
| aura.lang.std.Json | 0 | parse / stringify / isValid | 高 |
| aura.lang.std.Encoding | 0 | base64Encode / base64Decode / hexEncode / hexDecode | 中 |
| aura.lang.std.Time | ~3 | now / sleep / diff | 中 |
| aura.lang.std.Random | ~2 | nextInt / nextLong / nextBool / nextIntRange / nextFloatRange / choice / shuffle | 低 |
| aura.lang.std.Env | 0 | get / set / remove / has / keys / home / tmp / pwd / platform / arch | 中 |
| aura.lang.std.Path | 0 | join / dirname / basename / extname / resolve / normalize | 低 |
| aura.lang.std.Collections | 0 | listOf / mapOf / setOf / arrayOf（需先实现集合类型 C ABI） | 远期 |
| aura.lang.std.{Coroutine,Actor,Channel} | 0 | spawn / send / ask / channel（需 VM 协程运行时 C ABI） | 远期 |

### 4.2 标准库模块分层建议

根据**系统依赖程度**将 std 模块分为三层，不同层级的交付和实现策略不同：

```
第一层：核心标准库（Compiler Core）
  → 必须实现，无编译期可选
  → Rust + C 双实现，始终包含
  → 模块：prelu / io / string / math / fs / json / encoding / builtin

第二层：扩展标准库（Compiler Extension）
  → Cargo feature 门控，按需编译
  → Rust 实现，C 实现可选
  → 模块：collections / env / path / time / random / process / console / ascii

第三层：高级标准库（Advanced）
  → 依赖运行时功能（协程/Actor/多线程）
  → 仅 VM 模式可用，AOT 模式标记为 unsupported
  → 模块：concurrent / net / iter（高阶泛型）
```

### 4.3 文档与 API 建议

**标准库 API 文档应包含三种格式**：

| 格式 | 用途 | 交付方式 |
|------|------|----------|
| Markdown | 源码仓库参考 | `docs/api/std_*.md`（已有） |
| HTML | 在线浏览 | `docs/std-api.html`（构建产物） |
| 注释内建 | IDE 补全 | `decl.rs` 中的 doc 注释 |

### 4.4 CI 构建建议

建议 CI 产出以下制品：

```
CI 产出（每次 tag 发布）：
1. aura-toolchain-{version}-{os}-{arch}.zip  # 完整工具链
2. aura-compiler-{version}-{os}-{arch}.zip   # 仅编译器
3. aura-vm-{version}-{os}-{arch}.zip         # 仅 VM（JIT 模式用）
4. libaura_std-{version}-{os}-{arch}.zip     # AOT 运行时库
5. aura-std-sources-{version}.zip            # 标准库源码（自举参考）
```

## 5. 总结

| 决策项 | 建议 | 理由 |
|--------|------|------|
| **标准库实现语言** | **保持 Rust + C 双实现，不要 Aura 自举** | 自举周期过长，当前编译器能力不足，Rust/C 实现更可靠 |
| **AOT 后端标准库** | **补齐 CFFI 实现，目标是 AOT 二进制自包含** | 当前 CFFI 仅 30 个函数，需与 Rust 实现对齐 |
| **交付格式** | **分层交付，标准库不用 .auz** | 标准库是编译器内置，不是外部依赖；.auz 仅用于第三方库 |
| **模块分层** | **三层架构：核心/扩展/高级** | 核心模块始终包含，扩展按需，高级仅 VM 模式 |
| **自举时机** | **远期目标，不列入近期计划** | 等编译器支持泛型+集合+高阶函数后再考虑 |

### 实施优先级

```
P0（当前）：Rust std 模块已完善，Cargo feature 门控已就绪
P1：补齐 aura_std_cffi.c 的核心函数（fs/json/encoding/io），使 AOT 自包含
P2：设计标准库 API 文档生成流水线（decl.rs → API 文档）
P3：CI 发布分层制品（compiler/VM/runtime/sources）
P4（远期）：评估 Aura 自举可行性（需先完成泛型+集合+迭代器）
```
