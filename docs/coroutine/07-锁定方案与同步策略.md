# Aura VM — 锁定方案与同步策略

> 本文补充《03-Phase-B-VM运行时改造》中缺失的锁设计。
> 没有锁方案，"加 Mutex" 只是一个笼统的说法——具体加在哪、怎么加、如何避免死锁，必须明确定义。

## 1. 总体设计原则

### 1.1 线程模型

```
每个 OS 线程拥有独立的 VM 实例
┌────────────────────────────────────────────────────────────────┐
│  OS Thread 1                     OS Thread 2                    │
│  ┌──────────────┐               ┌──────────────┐               │
│  │ VM Instance  │               │ VM Instance  │               │
│  │  ├─ Heap*    │               │  ├─ Heap*    │               │
│  │  ├─ Frame    │               │  ├─ Frame    │               │
│  │  ├─ Modules  │               │  ├─ Modules  │               │
│  │  └─ Coroutines│              │  └─ Coroutines│               │
│  └──────────────┘               └──────────────┘               │
│           \                          /                           │
│            \                        /                            │
│             ┌──────────────────────┐                            │
│             │    共享资源池          │                            │
│             │  ├─ ModuleRegistry   │ ← 只读（初始化后冻结）        │
│             │  ├─ NativeRegistry   │ ← 只读                      │
│             │  ├─ Heap (if shared) │ ← Mutex 保护                 │
│             │  └─ JIT Cache        │ ← Mutex 保护                 │
│             └──────────────────────┘                            │
└────────────────────────────────────────────────────────────────┘
```

**核心决策：VM 实例不共享，只共享资源。**
- 每个 OS 线程有自己的 `Vm` 结构体（帧栈、局部变量、操作数栈）
- 跨线程通信通过 Channel / Actor mailbox 消息传递
- 共享可变状态（如共享 Heap）使用锁保护

### 1.2 锁分类

| 锁类型 | 适用场景 | 粒度 |
|--------|---------|------|
| `Mutex` | 互斥访问共享可变状态 | 细粒度（按字段/对象） |
| `RwLock` | 读多写少的共享状态 | 粗粒度（整个注册表） |
| `Atomic` | 单一整数/布尔值 | 无锁 |
| `Condvar` | 等待条件满足 | 配合 Mutex |
| `RwLock` | JIT 编译缓存 | 读多写少 |
| 全局锁（GIL） | **不采用** — 避免 GIL 式瓶颈 |

## 2. 逐组件锁方案

### 2.1 Heap（`vm/heap.rs`）

**问题**：Heap 是所有 VM 实例共享的可变数据结构。多线程同时操作 Heap 会产生数据竞争。

#### 方案 A：全局 Mutex（推荐起步）

```rust
use std::sync::{Mutex, MutexGuard};

pub struct Heap {
    /// 所有可变状态包裹在 Mutex 中
    data: Mutex<HeapData>,
}

struct HeapData {
    objects: HashMap<u64, Obj>,
    lists: HashMap<u64, Vec<Value>>,
    maps: HashMap<u64, BTreeMap<Value, Value>>,
    arrays: HashMap<u64, Vec<Value>>,
    next_id: u64,
}

impl Heap {
    /// 获取 Heap 数据的可变引用（加锁）
    pub fn lock(&self) -> MutexGuard<'_, HeapData> {
        self.data.lock().unwrap()
    }
    
    /// 安全地分配新对象
    pub fn alloc(&self, fields: Vec<Value>) -> u64 {
        let mut data = self.data.lock().unwrap();
        let id = data.next_id;
        data.next_id += 1;
        data.objects.insert(id, Obj { fields, refcount: 1 });
        id
    }
    
    /// 增加引用计数（原子操作，无锁）
    pub fn inc_ref(&self, id: u64) {
        // 如果对象头是原子的，可以直接原子加
        // 否则需要加锁
        let data = self.data.lock().unwrap();
        if let Some(obj) = data.objects.get(&id) {
            // 原子操作（见 2.6 ARC）
            unsafe {
                __sync_fetch_and_add(&*(obj.refcount.get()), 1);
            }
        }
    }
}
```

**优点**：简单，正确性容易保证。
**缺点**：所有 Heap 操作串行化，性能瓶颈。

#### 方案 B：Per-Thread Shard + 全局锁回退

```rust
pub struct Heap {
    /// 线程本地分片（无锁访问）
    shards: [Mutex<HeapData>; SHARD_COUNT],
    /// 全局后备分片（跨线程访问时锁定）
    global: Mutex<HeapData>,
    /// 用于判断对象在哪个分片
    shard_hint: AtomicUsize,  // 最近使用的分片
}

const SHARD_COUNT: usize = 8;

impl Heap {
    /// 获取当前线程对应的分片
    fn shard_for_current_thread(&self) -> &Mutex<HeapData> {
        let tid = get_thread_id();
        &self.shards[tid % SHARD_COUNT]
    }
    
    /// 跨线程访问对象（需要全局锁）
    pub fn get_cross_thread(&self, id: u64) -> Option<&Value> {
        // 先查所有分片，再查全局
        ...
    }
}
```

**优点**：同线程无锁访问，性能高。
**缺点**：跨线程访问需要扫描所有分片；复杂度高。

#### 方案 C：无锁 Heap（Lock-Free）

```rust
pub struct Heap {
    arena: AtomicPtr<HeapNode>,  // 侵入式链表头
}

struct HeapNode {
    next: AtomicPtr<HeapNode>,
    id: u64,
    obj: Obj,
    _padding: [u8; 56],  // cache line 对齐
}
```

**优点**：最佳性能。
**缺点**：实现极其复杂，调试困难，内存回收问题。

**建议**：**Phase B 用方案 A，后续按需迁移到 B。**

### 2.2 ARC 引用计数（线程安全）

ARC 的 `inc_ref`/`dec_ref` 必须在多线程环境下安全。

```rust
struct Obj {
    fields: Vec<Value>,
    /// 原子引用计数（无需锁）
    refcount: AtomicUsize,
    /// drop 回调（需要在锁保护下执行）
    drop_fn: Option<DropFn>,
}

impl Heap {
    /// 原子增加引用计数（无锁）
    pub fn inc_ref(&self, id: u64) -> bool {
        let data = self.data.lock().unwrap();
        if let Some(obj) = data.objects.get(&id) {
            obj.refcount.fetch_add(1, Ordering::Relaxed);
            true
        } else {
            false
        }
    }
    
    /// 原子减少引用计数，归零时释放
    pub fn dec_ref(&self, id: u64) -> bool {
        let data = self.data.lock().unwrap();
        if let Some(obj) = data.objects.get(&id) {
            let old = obj.refcount.fetch_sub(1, Ordering::AcqRel);
            if old == 1 {
                // 最后一个引用，释放对象
                // 注意：这里持有 Heap 锁，所以其他线程看不到此对象
                // drop_fn 在锁保护下执行
                if let Some(dfn) = obj.drop_fn {
                    dfn(id, &self);
                }
                data.objects.remove(&id);
                true
            } else {
                false
            }
        } else {
            false
        }
    }
}
```

**关键问题：drop 回调的死锁**

```rust
// 场景：线程 A 释放对象 X，X 的 drop 回调尝试访问 Heap
// 此时线程 A 已经持有 Heap 锁 → 自己锁自己 → 死锁！

// 解决方案：drop 回调在释放锁之后执行
// 需要两阶段：
// 1. 锁内：将 refcount 减到 0，标记为"待释放"
// 2. 锁外：执行 drop 回调

pub fn dec_ref(&self, id: u64) -> bool {
    let mut data = self.data.lock().unwrap();
    if let Some(obj) = data.objects.get_mut(&id) {
        let old = obj.refcount.fetch_sub(1, Ordering::AcqRel);
        if old == 1 {
            let drop_fn = obj.drop_fn.take();  // 在锁内取出回调
            data.objects.remove(&id);
            drop(data);  // 先释放锁
            // 锁外执行 drop 回调（不会死锁）
            if let Some(dfn) = drop_fn {
                dfn(id, &self);
            }
            return true;
        }
    }
    false
}
```

### 2.3 模块注册表（`ModuleRegistry`）

模块注册表在 VM 初始化后是**只读**的，不需要锁。

```rust
pub struct ModuleRegistry {
    /// 初始化后只读，使用 OnceLock 保证线程安全的一次性初始化
    modules: OnceLock<HashMap<String, Arc<BytecodeModule>>>,
}

impl ModuleRegistry {
    pub fn get(&self, name: &str) -> Option<Arc<BytecodeModule>> {
        self.modules.get().and_then(|m| m.get(name)).cloned()
    }
}
```

### 2.4 原生函数注册表（`NativeRegistry`）

同上，初始化后只读。使用 `LazyLock` 或 `OnceLock` 包装。

### 2.5 JIT 编译缓存（`JitState`）

JIT 缓存是读多写少的——大量线程调用已编译的函数，少数线程触发编译。

```rust
pub struct JitState {
    /// 已编译的函数（读多写少）
    compiled: RwLock<HashMap<usize, JitEntry>>,
    
    /// 正在编译中的函数（防止重复编译）
    compiling: Mutex<HashMap<usize, Arc<Condvar>>>,
    
    /// 跳过编译的函数
    skipped: Mutex<HashMap<usize, String>>,
    
    /// 分发表（读多写少）
    dispatch_table: RwLock<Vec<Option<JitEntry>>>,
}

impl JitState {
    /// 线程安全地获取或编译函数
    pub fn get_or_compile(&self, idx: usize, module: &BytecodeModule) -> Option<JitEntry> {
        // 1. 快速路径：查缓存（读锁，非阻塞）
        {
            let compiled = self.compiled.read().unwrap();
            if let Some(entry) = compiled.get(&idx) {
                return Some(*entry);  // 命中
            }
        }
        
        // 2. 检查是否正在编译中
        {
            let compiling = self.compiling.lock().unwrap();
            if let Some(cv) = compiling.get(&idx) {
                // 另一个线程正在编译，等待
                drop(compiling);
                // 等待编译完成（条件变量）
                // 注意：这里需要配合 compiled 的写锁
                return self.wait_for_compile(idx);
            }
            // 标记为正在编译
            let cv = Arc::new(Condvar::new());
            compiling.insert(idx, cv);
        }
        
        // 3. 执行编译（无锁）
        let entry = self.do_compile(idx, module);
        
        // 4. 注册结果
        if let Some(entry) = entry {
            self.compiled.write().unwrap().insert(idx, entry);
        } else {
            self.skipped.lock().unwrap().insert(idx, "compilation failed".into());
        }
        
        // 5. 唤醒等待者
        if let Some(cv) = self.compiling.lock().unwrap().remove(&idx) {
            cv.notify_all();
        }
        
        self.compiled.read().unwrap().get(&idx).copied()
    }
}
```

### 2.6 线程安全的数据结构选择

| 数据结构 | 用途 | 线程安全方案 |
|----------|------|-------------|
| `Heap.objects` | 对象表 | `Mutex<HashMap>` |
| `Heap.next_id` | 对象 ID | `AtomicU64` |
| `Actor.mailbox` | 消息队列 | `Arc<Mutex<VecDeque>>` |
| `Channel.buffer` | 消息缓冲区 | `Mutex<VecDeque>` + `Condvar` |
| `Channel.bound` | 容量上限 | 不可变（创建时确定） |
| `JitState.compiled` | 编译缓存 | `RwLock<HashMap>` |
| `ModuleRegistry` | 模块表 | `OnceLock<HashMap>`（只读） |
| `NativeRegistry` | 原生函数表 | `OnceLock<HashMap>`（只读） |
| `CoroutineScheduler.coroutines` | 协程表 | `Mutex<HashMap>` |
| `CoroutineScheduler.ready_queue` | 就绪队列 | `Mutex<VecDeque>` |

## 3. 锁顺序与死锁预防

### 3.1 全局锁顺序

所有锁必须按以下顺序获取，违反此顺序会导致死锁：

```
锁顺序（从外到内）：
  1. Heap 锁（最外层）
  2. Actor mailbox 锁
  3. Channel 锁
  4. Condvar 锁（配合对应 Mutex）
  5. JIT 缓存锁

❌ 禁止：
  - 同时持有两个 Channel 锁
  - 持有 Channel 锁时获取 Heap 锁（应该反过来）
  - 持有 Actor 锁时获取 Channel 锁（应该反过来）
```

### 3.2 死锁预防策略

```rust
// 策略 1：锁超时
fn try_lock_with_timeout<T>(mutex: &Mutex<T>, timeout: Duration) -> Option<MutexGuard<T>> {
    // 如果锁等待超过 timeout，返回 None 而不是死等
    match mutex.try_lock_for(timeout) {
        Ok(guard) => Some(guard),
        Err(_) => None,  // 调用者需要处理降级
    }
}

// 策略 2：不嵌套不同类型锁
// Channel 操作永远不嵌套持有 Heap 锁
pub fn channel_send(&self, ch: ChannelId, val: Value) {
    // 先克隆值（需要 Heap 锁，然后释放）
    let val_clone = {
        let heap = self.heap.lock().unwrap();
        val.clone_from_heap(&heap)  // 深克隆
    };
    // 然后操作 Channel（不需要 Heap 锁）
    let mut buf = self.channels[ch].buffer.lock().unwrap();
    buf.push_back(val_clone);
}

// 策略 3：检测死锁（可选，开发模式）
#[cfg(debug_assertions)]
fn assert_no_deadlock(current_locks: &HashSet<LockType>) {
    // 检查是否违反锁顺序
    ...
}
```

### 3.3 自死锁（Self-Deadlock）

```rust
// 危险：线程已经持有锁，再次尝试获取同一把锁
// Rust 的 Mutex::lock 在已经持有时会 panic（不是死锁，是运行时错误）

// 防止：使用 lock() 而不是 lock() 多次
// 或者：使用 parking_lot::Mutex（支持递归）

// 我们的策略：禁止递归锁获取
// 所有函数要么持有锁要么不持有，不在持有锁的函数中再次获取同一把锁
```

## 4. 内存模型与 Happens-Before

### 4.1 基本规则

| 操作 | Happens-Before 保证 |
|------|-------------------|
| 线程 A 写共享变量 → 线程 B 读共享变量 | 只有在使用同步原语（Mutex/Atomic）时才保证 |
| `thread::spawn` → 新线程第一次执行 | spawn 之前的所有操作对子线程可见 |
| 线程结束 → `thread::join` | 子线程的所有操作对 join 之后的主线程可见 |
| `Mutex::lock` → `Mutex::unlock` → 另一个线程 `Mutex::lock` | unlock 之前的操作对下一个 lock 之后的操作可见 |
| `Atomic` 顺序一致（SeqCst）操作 | 全局全序，所有原子操作有确定的顺序 |

### 4.2 推荐原子操作顺序

```rust
// 默认使用 SeqCst（最严格，最安全）
AtomicU64::new(0).fetch_add(1, Ordering::SeqCst);

// 对于性能关键路径，可以降级：
// - 读：Ordering::Relaxed（只读值，不需要同步）
// - 写：Ordering::Release（写完后释放之前的写）
// - 读/写：Ordering::Acquire（读前获取之前的写）
// - 读+写：Ordering::AcqRel（读+写）

// 示例：无锁引用计数
// inc_ref: Relaxed（只加 1，不关心其他内存顺序）
// dec_ref: AcqRel（减到 0 时需要获取之前的写，确保看到所有引用）
```

### 4.3 禁止的操作

```rust
// ❌ 禁止：非原子的跨线程共享可变状态
// 这是数据竞争，未定义行为！

// ❌ 禁止：在持有 Mutex 时调用用户代码（可能导致死锁）
let guard = mutex.lock().unwrap();
user_callback();  // user_callback 可能尝试获取同一把锁
drop(guard);

// ❌ 禁止：引用一个被另一个线程释放的对象
// 没有同步的情况下，对象可能已经被 free
```

## 5. 并发场景下的具体锁策略

### 5.1 场景：两个线程共享一个 Heap 操作对象

```
线程 A:                    线程 B:
inc_ref(obj_X)            dec_ref(obj_X)
  │                          │
  ▼                          ▼
Heap.lock()               Heap.lock()   ← 串行化
  │                          │
  ▼                          ▼
obj_X.refcount += 1       obj_X.refcount -= 1
  │                          │
  ▼                          ▼
Heap.unlock()             Heap.unlock()
```

### 5.2 场景：两个线程通过 Channel 通信

```
线程 A (发送):                    线程 B (接收):
channel.send(val)                  channel.recv()
  │                                  │
  ▼                                  ▼
lock(channel.buffer)              lock(channel.buffer)
  │                                  │
  ▼                                  ▼
buffer.push(val)                  buffer.pop()
  │                                  │
  ▼                                  ▼
notify(not_empty)                 wait(not_empty)  ← 如果 buffer 为空
  │                                  │
  ▼                                  ▼
unlock(buffer)                    unlock(buffer)
```

### 5.3 场景：Actor 消息调度

```
线程 A (发送消息):                    Actor 调度线程:
actor.send(msg)                       actor.loop()
  │                                      │
  ▼                                      ▼
lock(mailbox)                        lock(mailbox)
  │                                      │
  ▼                                      ▼
mailbox.push(msg)                   mailbox.pop()  ← 阻塞等待
  │                                      │
  ▼                                      ▼
notify(not_empty)                   wait(not_empty)  ← 如果没有消息
  │                                      │
  ▼                                      ▼
unlock(mailbox)                     unlock(mailbox)
                                       │
                                       ▼
                                   handler.handle(msg)
```

## 6. 实现检查清单

实现每个 Phase 时，必须检查：

- [ ] 所有共享可变状态都有 Mutex/RwLock/Atomic 保护
- [ ] 锁顺序符合全局锁顺序（Heap → Actor → Channel → Condvar → JIT）
- [ ] 不存在递归锁获取
- [ ] drop 回调在释放锁后执行
- [ ] Arc 引用计数使用原子操作
- [ ] JIT 编译缓存有 Mutex 保护
- [ ] 没有数据竞争（Rust 编译器 + Miri 检测）
- [ ] 没有死锁（并发测试覆盖）

## 7. 总结

```

│  组件             锁方案              理由                            │
├────────────────────────────────────────────────────────────────────┤
│  Heap             Mutex<HeapData>     简单，正确性优先                │
│  ARC refcount     AtomicUsize         无锁，高性能                    │
│  ModuleRegistry   OnceLock<...>       初始化后只读                    │
│  NativeRegistry   OnceLock<...>       初始化后只读                    │
│  JIT compiled     RwLock<HashMap>     读多写少                        │
│  JIT compiling    Mutex<HashMap>      少量并发编译                    │
│  Actor mailbox    Mutex<VecDeque>     消息队列需要串行化              │
│  Channel buffer   Mutex + Condvar     事件驱动阻塞                    │
│  Coroutines       Mutex<HashMap>      协程状态需要串行化              │
│  ReadyQueue       Mutex<VecDeque>     就绪队列需要串行化              │
└────────────────────────────────────────────────────────────────────┘

锁顺序：Heap > Actor > Channel > Condvar > JIT
禁止：嵌套不同类型锁 / 递归锁获取 / 持锁调用用户代码
```
