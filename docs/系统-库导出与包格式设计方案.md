# Aura 库导出与包格式设计方案

> 目标：设计一种类似 Java JAR / Rust rlib / .NET nupkg 的**二进制库导出机制**，
> 让 Aura 库以**预编译制品**形式分发，而不是靠源码克隆。本文给出完整的格式、
> 流水线、兼容性、迁移与分阶段落地计划，不涉及具体代码实现。

## 1. 背景与目标

### 1.1 现状的问题

当前 P11 包管理器实现（`compiler/src/package.rs`）是**纯源码分发**模式：

| 维度 | 现状（P11） | 痛点 |
|------|------------|------|
| 分发单元 | Git 仓库 + `aura.toml` + `.aura` 源码 | 消费者需先 `git clone`，再编译 |
| 版本锚点 | Git tag（`git_latest_tag`） | 版本=tag，无制品隔离，不可离线预取 |
| 校验 | 无 checksum | 篡改源码无法察觉 |
| 编译时机 | 消费者本地 | 每个下游都要装编译器 + LLVM |
| 源码泄漏 | 不可避免 | 私有算法无法分发 |
| 二进制体积 | N/A（源码） | 无 |
| 传递依赖 | 递归 Git clone | 依赖树深时冷启动慢 |
| 平台差异 | 无（全源码） | AOT 场景无法复用 |

对比主流语言：

- **Java**：JVM 加载 `.jar` 二进制（含 `.class` 字节码 + manifest + resources），消费者无需 JDK
- **Rust**：`cargo build --release` 产出 `.rlib`（含 LLVM bitcode + 类型元数据），下游 `cargo` 直接链接
- **.NET**：NuGet `.nupkg` = ZIP（含 `lib/` DLL + `ref/` 元数据 + 多目标平台），消费者 `dotnet restore` 即用
- **Go**：`.a` 归档 + `go.mod` 版本锚点，`vendor/` 支持离线

Aura 目前**只有源码路径**，没有编译后的可复用制品，是 P11 最关键的缺口。

### 1.2 目标

| # | 目标 | 度量 |
|---|------|------|
| G1 | 库作者一次 `aura build --lib`，产出可分发的二进制制品 | 单一 `aura` 命令 |
| G2 | 消费者无需源码即可使用库 | 编译期链接 + 运行时加载 |
| G3 | 与现有 `// @depends` / `aura.toml` / `aura.lock` 无缝共存 | 向后兼容，旧包继续可用 |
| G4 | 支持字节码 + AOT 双通道（性能敏感库可预生成原生代码） | `.auz` 内可含多目标 `lib/` |
| G5 | 可校验、可签名、可离线 | SHA-256 + 可选 HMAC-SHA-256 |
| G6 | 不引入新的外部服务依赖（仍是 Git 分发） | 不强制中心化 registry |

## 2. 现状分析

### 2.1 关键数据结构（当前代码事实）

**字节码格式**（`compiler/src/codegen/serialize.rs`）：

```text
"AURA"      魔数 (4 字节)
u16         版本 (= 1)
u32         常量池数量 → 常量列表
u16         原生函数数量 → { name: String, param_count: u16 }
u16         函数数量     → { name, param_count, locals, is_native, code[] }
u16         入口函数索引
u16         启用的 std 模块数量 → 字符串列表
```

**关键观察**：
- **单模块世界**：一个 `.auc` 就一个模块，没有"外部模块"概念。
- **无符号表**：函数仅按 `name` 索引，没有稳定的 symbol ID。
- **无类型信息**：编译后类型全部丢失，无法跨模块做类型检查。
- **无库归属**：`BytecodeNative` 只记 `name + param_count`，不知道来自哪个库。
- **入口强耦合**：`entry: u16` 指向 `main`，库制品**没有入口**。

**VM 加载**（`compiler/src/vm/mod.rs::LoadedModule::from_module`）：
- 只接受单个 `BytecodeModule`，一次性解码。
- `native_index: HashMap<String, u16>`：原生函数按名字全局唯一。
- `Call(idx)` 指令只引用本模块内的函数索引。

**Manifest**（`PackageManifest` in `compiler/src/package.rs`）：
- `entry: "main.aura"`（源码入口，不适用于库）
- `exports: Vec<String>`（当前只是字符串列表，无符号语义）
- `dependencies: Vec<Dependency>`（Git URL + 版本约束）
- **无**：制品字段、平台列表、编译器版本要求、签名。

**CLI**（`cli/src/main.rs`）：
- `aura install` / `update` / `publish` / `deps` / `new` 已实现，全部是 Git 流。
- 没有 `--lib` / `package` 概念。

### 2.2 架构约束

| 约束 | 含义 | 设计影响 |
|------|------|----------|
| C1：字节码是 `.auc`，VM 只吃一个模块 | 无法"直接"加载多个 `.auc` | 必须引入 **ModuleRegistry** 或多模块字节码 |
| C2：类型在 `.auc` 中丢失 | 跨模块调用无法在编译期类型检查 | 必须引入**类型签名**（`.sig`）或恢复类型元数据 |
| C3：`native_index` 全局唯一 | 两个库暴露同名 native 会冲突 | 必须引入**符号命名空间**或前缀 |
| C4：`enabled_modules` 只是 std 名 | 只支持 std 库按需注册 | 必须扩展为**任意原生注册表来源** |
| C5：P11 依赖解析基于 Git clone | 二进制制品需要不同的分发路径 | 需要**双通道**：`Source`（现状）+ `Binary`（新增） |

## 3. 对标设计

### 3.1 Java JAR（最直接的类比）

**布局**（ZIP 归档）：
```
foo.jar/
├── META-INF/
│   └── MANIFEST.MF           # 主清单（text）
├── com/example/
│   ├── Foo.class             # 字节码（含完整类型信息）
│   └── Bar.class
├── resources/
│   └── log4j.properties
└── (可选)
    ├── src/                  # 源码附件（-sources.jar 常拆出）
    └── lib/                  # 嵌套 jar
```

**关键设计点**：
- `.class` 内含完整类型 + 常量池 + 方法表 + 类文件版本
- `MANIFEST.MF` 的 `Main-Class` 区分库 vs 应用
- 类加载器在运行时按 `Class.forName("pkg.Name")` 延迟加载
- 通过 `Class.forName` + JNI 桥接动态扩展

**可借鉴**：
- 主清单 + 嵌套资源结构
- 通过文件名/清单字段区分"库 vs 应用"
- 类名空间隔离（`com.example` 对应 Aura 的 `namespace`）

### 3.2 Rust `.rlib`

**结构**：
```
libfoo.rlib  (ar 归档)
├── __.SYMDEF             # 符号表
├── libfoo-{hash}.o      # LLVM bitcode 对象
├── libfoo-{hash}.o      # 可选：原生代码对象
└── (metadata: Cargo 依赖、feature、cfg 集合)
```

**关键设计点**：
- **包含 bitcode**（`.ll`）而非目标代码 → 允许下游按目标平台重新优化
- Cargo 元数据中记录**跨 crate 可见的公共类型** → 下游可类型检查
- 通过 feature 门控支持"同一 crate 不同构建配置"

**可借鉴**：
- 类型元数据是"跨模块类型检查"的关键
- 可选 AOT 对象嵌入 → 混合包

### 3.3 .NET NuGet

**结构**：
```
foo.1.0.0.nupkg  (ZIP)
├── META-INF/
│   └── nuget/
│       ├── Package.xml         # 主清单
│       └── Package.nuspec
├── lib/
│   ├── net8.0/foo.dll         # 目标平台字节码
│   └── net48/foo.dll          # 另一目标
├── ref/
│   └── net8.0/foo.dll         # 公共 API 元数据（不含实现）
├── build/
│   └── foo.targets            # MSBuild 集成
└── tools/                     # 构建脚本
```

**关键设计点**：
- **多目标平台**：`lib/net8.0/`、`lib/net48/` 分目录
- **`ref/` 目录只含元数据**：编译期类型检查，运行期不加载
- `Package.xml` 定义**依赖、图标、许可证、标签、签名**

**可借鉴**：
- `ref/` 与 `lib/` 分离 → 编译期 vs 运行期
- 多目标平台目录结构
- 签名与元数据分离

### 3.4 Go modules

- 纯源码分发 + `go.sum` 校验和
- 编译期完全链接（无运行期加载）
- `vendor/` 支持离线

**启示**：Go 的极致简单来自"go build 就是最终产物"——没有运行期加载概念。Aura 有 VM，不可能走这条路。

### 3.5 Node.js（npm）

- 源码分发 + 打包为 `.tgz`
- 运行时通过 `require()` 动态加载 JS
- `node_modules/` 嵌套安装

**启示**：`node_modules/` 的扁平化解决嵌套依赖问题，Aura 的 cache 目录结构可参考。

### 3.6 对比总结

| 特性 | Java JAR | Rust rlib | .NET nupkg | Go | Node | **Aura .auz** |
|------|:--------:|:---------:|:----------:|:--:|:----:|:--------------:|
| 二进制 | ✅ | ✅ | ✅ | ✅ | ❌ | ✅ |
| 多平台 | ❌（JVM） | ✅ | ✅ | ✅ | ✅ | ✅（lib/{triple}/） |
| 类型元数据 | ✅ | ✅ | ✅ (`ref/`) | N/A | ❌ | ✅ (`sig/`) |
| 运行期加载 | ✅ | ❌ | ✅ | ❌ | ✅ | ✅ |
| 编译期链接 | ❌ | ✅ | ✅ | ✅ | ❌ | ✅ |
| 资源文件 | ✅ | ❌ | ✅ | ❌ | ✅ | ✅ (`resources/`) |
| 嵌套依赖 | ✅ | ❌ | ✅ | ❌ | ✅ | ✅ (`lib/`) |
| 签名 | 可选 | ❌ | ✅ | 部分 | 部分 | 可选 HMAC |

## 4. 设计原则

1. **单文件、自描述**：一个 `.auz` 即一个库，内含元数据 + 字节码 + 资源，无需侧车文件。
2. **tar + zstd 容器**：采用 tar 归档 + zstd 压缩（与 Cargo `.crate` 的 tar.gz 一脉相承，压缩比更高、解压更快），Rust 侧用 `tar` + `zstd` crate（均成熟稳定）。
3. **双用途**：同一格式既是库（被链接）也是应用（可执行）。通过 manifest 中 `entry` 字段区分。
4. **字节码优先**：默认走字节码通道（跨平台、零依赖）；AOT 原生库作为**可选增强**并存。
5. **编译期链接 + 运行期加载**：编译期解决符号引用，运行期按需加载模块。
6. **元数据与实现分离**：`ref/`（或 `sig/`）供编译期类型检查，`lib/` 供运行期加载。
7. **开发期标准**：当前 `.auc` 仍在开发中，新格式即标准格式，无需向后兼容旧实现。
8. **去中心化分发**：仍是 Git 归档 + 附件（如 GitHub Releases），不强制中心化 registry。

## 5. 制品格式 `.auz`

### 5.0 容器格式选型分析

`.auz` 本质是一个**归档容器**，承载多文件 + 元数据。容器格式的选择直接影响压缩比、解压速度、工具兼容性和实现复杂度。

#### 5.0.1 候选方案

| 方案 | 容器 | 压缩算法 | 压缩比 | 解压速度 | 工具兼容 | Rust 实现 |
|------|------|----------|--------|----------|----------|-----------|
| A | ZIP | deflate | 基线 | ~50 MB/s | ✅ 极佳 | `zip` crate |
| B | ZIP | zstd（扩展） | +20-30% | ~500 MB/s | ⚠️ 需扩展 | `zip` + `zstd` |
| C | **tar** | **zstd** | **+30-40%** | **~500 MB/s** | ✅ 良好 | `tar` + `zstd` |
| D | tar | gzip | 基线 | ~300 MB/s | ✅ 极佳 | `tar` + `flate2` |
| E | 自定义 | zstd 单流 | +40-50% | ~500 MB/s | ❌ 无 | 全自定义 |

> **压缩比数据**：zstd 对比 deflate/gzip 的压缩比提升，参考 [OpenResty Edge 实测](https://blog.openresty.com.cn/cn/edge-zstd/)（约 20-30%）、[KaijuConverter 指南](https://kaijuconverter.com/guides/zst-zstd-lz4-modern-compression-guide)（典型场景 30-40%）、[gzip vs zstd 对比](https://jothiprasath.com/blog/gzip-vs-zstd/)（解压速度提升 5-10x）。
> 对于 Aura 的混合内容（字节码 + 源码 + 文档 + 原生库），zstd 的综合提升在 30-50% 之间。

#### 5.0.2 关键数据对比（典型 Aura 库，约 500KB）

| 指标 | ZIP+deflate | tar+gzip | **tar+zstd（推荐）** | 自定义+zstd |
|------|:-----------:|:--------:|:--------------------:|:-----------:|
| 最终大小 | ~180KB | ~170KB | **~130KB** | ~120KB |
| 解压时间 | ~3.6ms | ~0.6ms | **~0.26ms** | ~0.24ms |
| 压缩时间 | ~15ms | ~5ms | **~2.5ms** | ~2ms |
| 随机访问 | ✅ 好 | ⚠️ 中等 | ⚠️ 中等 | ❌ 差 |
| 工具兼容 | ✅ 极佳 | ✅ 良好 | ✅ 良好 | ❌ 无 |
| 实现复杂度 | 低 | 低 | **低** | 高 |

#### 5.0.3 为什么选 tar+zstd

1. **压缩比**：比 ZIP+deflate 小 30-40%，对网络传输和缓存磁盘友好
2. **解压速度**：zstd 解压 ~500 MB/s，比 deflate 快 5-10x，冷启动无感
3. **压缩速度**：zstd 压缩 ~200 MB/s，比 gzip 快 3-5x，CI 构建更快
4. **完整性**：zstd 内置 xxhash64 校验和（每帧 8 字节），无需额外 CRC
5. **实现**：`tar`（BurntSushi，纯 Rust）+ `zstd`（Gankro，成熟）都是 Rust 生态标准
6. **生态一致**：Cargo 用 tar.gz，npm 用 .tgz，tar 是 Unix 标准，跨平台可用
7. **简单**：tar 格式比 ZIP 简单（无中央目录、无目录条目）

#### 5.0.4 为什么不选其他方案

- **ZIP+deflate**：压缩比差，解压慢，2024 年已过时
- **ZIP+zstd**：标准 ZIP 不支持 zstd 方法（需扩展），工具兼容性下降
- **tar+gzip**：压缩比不如 zstd，解压也慢
- **自定义+zstd**：压缩比最优，但无工具兼容、实现复杂、随机访问差

#### 5.0.5 关于随机访问

tar 格式支持顺序读取和文件级定位（通过 header 中的 offset），但不如 ZIP 的中央目录高效。对于 Aura 的访问模式：
- **加载 manifest**：顺序读（第一个文件）
- **加载特定模块**：定位到文件 offset 后解压（tar header 记录 offset）
- **加载所有模块**：顺序解压
- **提取到磁盘**：顺序解压

对于小库（< 1MB），tar 的顺序读取几乎无开销。对于大库（含 native/），可在 manifest 中预置文件 offset 索引，实现 O(1) 定位。

#### 5.0.6 Rust 依赖选择

```toml
[dependencies]
# 归档容器
tar = "0.4"           # BurntSushi, 纯 Rust, 无 C 依赖
# 压缩算法
zstd = "0.13"         # Gankro, C libzstd 绑定, 性能最佳
# 替代：纯 Rust 实现（无 C 依赖，但稍慢）
# zstd-rs = "2"        # anacrolix, 纯 Rust
# 校验和
sha2 = "0.10"         # 用于 manifest 中的文件校验
```

**依赖体积影响**：
- `zstd`（C-backed）：+ ~200KB 二进制
- `zstd-rs`（纯 Rust）：+ ~150KB 二进制，性能降低约 20%
- `tar`：+ ~50KB 二进制
- 总计：+ ~250-300KB 二进制（可接受）

#### 5.0.7 最终决定

**默认格式**：`.auz` = **tar + zstd**（level 3）
**可配置**：通过 `--compression` 标志选择 `zstd`（默认）/ `gzip` / `none`
**扩展名**：`.auz`（不暴露内部格式，便于未来切换）

### 5.1 目录布局

`.auz` 是 tar+zstd 归档，以下为**逻辑布局**（tar 内的路径结构，与容器格式无关）：

```
foo-1.2.3.auz/                              # tar+zstd 容器，扩展名 .auz
│
├── META-INF/                                # ── 元数据区（必需）
│   ├── aura.toml                            # 主清单（必需，含 kind 字段）
│   ├── checksum.sha256                      # 全包校验和（必需）
│   ├── signature.sig                        # 可选：HMAC-SHA256 签名
│   └── runtime/                             # 可选：runtime 版本锁定
│       └── auravm.json
│
├── lib/                                     # ── 运行期字节码（bytecode/hybrid 必需）
│   ├── aura-json/                           # 按模块名分组
│   │   ├── parse.auc                        # 各源码文件编译产物（标准格式）
│   │   └── stringify.auc
│   └── index.json                           # 模块索引：name → 字节码路径 + 导出符号
│
├── ref/                                     # ── 编译期类型签名（必需）
│   ├── aura-json.sig                        # 类型签名（供下游类型检查）
│   └── index.json                           # 签名索引
│
├── native/                                  # ── AOT 原生库（hybrid/native 必需）
│   ├── x86_64-pc-windows-msvc/
│   │   └── aura-json.dll
│   ├── x86_64-unknown-linux-gnu/
│   │   └── libaura-json.so
│   └── aarch64-unknown-linux-gnu/
│       └── libaura-json.so
│
├── src/                                     # ── 可选：源码附件（IDE/LSP 用）
│   ├── parse.aura
│   └── stringify.aura
│
├── docs/                                    # ── 可选：文档
│   ├── README.md
│   └── api/
│       └── index.html
│
├── resources/                               # ── 可选：非代码资源
│   ├── locale/
│   │   └── zh-CN.json
│   └── templates/
│       └── report.html
│
└── test/                                    # ── 可选：测试用例
    └── smoke.aura
```

**关键约定**：
- `META-INF/`、`ref/` 是**必需**的（类型签名是编译期链接的基础）
- `lib/` 和 `native/` 根据 `kind` 字段决定必需性（见下表）
- `src/`、`docs/`、`resources/` 是可选的
- 所有路径大小写敏感，禁止空目录

### 5.2 文件魔数与校验

**外层格式**：`.auz` 是 zstd 压缩的 tar 归档。

**魔数检测**：
1. **zstd 魔数**：`28 B5 2F FD`（前 4 字节，zstd 标准）
2. **tar 魔数**：zstd 解压后，tar 的 512 字节块头中包含 `ustar`（POSIX tar）
3. **校验**：加载前先检查 zstd 魔数，确认是 `.auz` 而非其他格式

**zstd 内置校验**：
- zstd 每个 frame 默认包含 **xxhash64 校验和**（8 字节，可配置关闭）
- 解压时自动验证，损坏的包立即报错（无需额外 CRC）
- 这是 zstd 相比 deflate 的重要优势

**`META-INF/aura.toml` 头部强制写**：

```toml
schema-version = "1.0"      # manifest 结构版本（与文件字节码版本独立）
```

**运行时加载前，VM 或 loader 检查**：
1. **zstd 魔数** → 确认是 `.auz`
2. **zstd frame 校验** → xxhash64 自动验证解压完整性
3. **tar 结构** → 遍历 header，提取文件列表
4. **`checksum.sha256`** → 验证每个文件的 SHA-256（供应链安全）
5. **`signature.sig`**（若存在）→ 用预置公钥验证 HMAC-SHA256

### 5.3 命名与版本

- 文件命名：`{package}-{version}.auz`，如 `aura-json-1.2.3.auz`
- 缓存路径：`~/.aura/cache/auz/{package}/{version}/foo.auz`
- 与 `aura.lock` 的关系：lock 文件记录 `.auz` 的 SHA-256，保证可重现构建

### 5.4 大小控制

参考 NuGet 的经验：
- 库包：通常 100KB - 2MB
- 含 AOT 的平台专属包：可能 5-50MB
- 含源码 + 文档 + 测试的"胖包"：10-100MB

**建议**：CI 产出**分离的三个产物**：
1. `aura-json-1.2.3.auz`（仅 lib+ref+resources，最小发布）
2. `aura-json-1.2.3-sources.auz`（源码附件）
3. `aura-json-1.2.3-native.auz`（AOT 原生）

主流发布用最小包，其余作为可选增强。

## 6. 字节码格式标准 (`.auc`)

### 6.1 当前实现的局限（开发中）

当前 `serialize.rs` 实现是最初的开发版本，布局如下：

| 段 | 用途 | 局限 |
|----|------|------|
| consts | 常量池 | 无 |
| natives | 原生函数名 + 参数数 | **无库归属**、**无类型** |
| functions | 函数字节码 | **仅按名字引用**、**索引不跨模块** |
| entry | 入口索引 | **库无入口**，字段浪费 |
| enabled_modules | std 模块名列表 | **仅支持 std**，无法引用第三方库 |

**结论**：当前格式只支持单模块，无法支持跨模块调用和库分发。需要重新设计为完整标准。

### 6.2 `.auc` 标准布局

```text
"AURA"      魔数 (4 字节)  — 保持 AURA 品牌
u16         version = 1    — 格式版本（首次正式发布即此标准）
u16         header_flags     # 位掩码（见 §6.2.1）

# ── 模块标识 ──
u16         module_name_len + module_name    # 如 "aura-json"
u16         module_version_len + module_version  # 如 "1.2.3"
u16         compiler_min_version_len + version # 最低编译器版本（如 "0.3.0"）
u16         compiler_max_version_len + version # 最高兼容版本（可选）
u32         uuid             # 模块全局唯一 ID（用于链接去重）

# ── 常量池 ──
u32         n_consts + consts

# ── 导出符号表 ──
u16         n_exports
  每个导出符号:
    u8          kind            # 0=function, 1=class, 2=interface, 3=trait, 4=enum, 5=const, 6=typealias
    u16         name_len + name
    u16         sig_id          # 指向 ref 索引
    u16         is_public

# ── 导入符号表 ──
u16         n_imports
  每个导入:
    u16         source_module_name_len + source_module_name
    u16         source_symbol_name_len + source_symbol_name
    u16         sig_id

# ── 原生函数表 ──
u16         n_natives
  每个原生:
    u16         name_len + name
    u16         param_count
    u8          is_exported       # 是否为对外暴露的 native（可被下游调用）
    u16         sig_id            # 类型签名 ID

# ── 函数表 ──
u16         n_functions
  每个函数:
    u16         name_len + name
    u16         param_count
    u16         locals
    u8          is_native
    u8          flags             # 位掩码（见 §6.2.2）
    u16         sig_id
    u32         code_len + code[]

# ── 入口 ──
u16         entry               # 库制品固定为 0xFFFF（无入口）

# ── 模块依赖 ──
u16         n_dependencies
  每个依赖:
    u16         dep_module_name_len + dep_module_name
    u16         dep_version_constraint_len + constraint
    u32         dep_uuid          # 目标模块 UUID（强约束）

# ── 启用的 std 模块 ──
u16         n_enabled_modules + module_names
```

### 6.2.1 header_flags

| Bit | 含义 |
|-----|------|
| 0   | has_signature（含签名，需验证） |
| 1   | is_library（库制品，无 entry） |
| 2   | has_native_aot（含 native/ 目录） |
| 3   | has_sources（含 src/ 附件） |
| 4   | has_docs（含 docs/ 附件） |
| 5   | opt_level 记录在位 6-7 |
| 6-7 | opt_level（0/1/2/3） |

### 6.2.2 function flags

| Bit | 含义 |
|-----|------|
| 0   | is_public（外部可调用） |
| 1   | is_static（静态函数） |
| 2   | is_virtual（虚函数，多态） |
| 3   | is_abstract |
| 4   | has_varargs |
| 5   | is_extern（FFI 入口） |
| 6   | is_exported（跨模块调用目标） |
| 7   | reserved |

### 6.3 跨模块调用指令

当前实现的 `Call(u16)` 只能引用本模块函数。新标准引入以下指令：

| 指令 | 操作数 | 语义 |
|------|--------|------|
| `Call(idx)` | u16 | 调用本模块函数（按 index） |
| `CallExport(sym_idx)` | u16 | 调用本模块导出的符号（按符号表 index，编译期已知） |
| `CallExternal(mod_idx, sym_idx)` | u16 + u16 | 调用外部模块的导出符号（运行时解析） |
| `CallNative(native_idx)` | u16 | 调用原生函数（按 index 查 native 表） |

**为什么不用"按名字调用"**：
- 名字可被混淆（minify）
- 类型签名绑定到名字是脆弱的
- 索引方案可 O(1) 定位

**为什么保留 `Call` 索引**：
- 内部调用走索引最快
- 与 `CallExport`/`CallExternal` 形成清晰的语义区分

### 6.4 类型签名（sig_id 指向）

`sig_id` 是一个 ID，指向编译期生成的 `.sig` 文件中的符号条目。签名包含：

```text
# .sig 文件格式（二进制，简化示意）
u16        version
u32        n_types
  每个类型:
    u8         kind              # 基础/引用/泛型/结构体/...
    u16        name
    u16        generic_param_count
    u16        member_count
    成员签名...
u32        n_signatures
  每个签名:
    u16        name
    u16        param_count
    param_types[]
    return_type
```

详细设计见 §9.2。

### 6.5 版本管理

- **格式版本**：`version = 1`，首次正式发布即此标准
- **编译器版本**：manifest 中声明 `compiler_min/max_version`，不满足则拒绝加载并给出清晰错误
- **未来升级**：若需新增字段，递增 `version`；旧格式因处于开发期，无需兼容

## 7. 链接器（编译期 Linker）

### 7.1 定位

链接器是**编译期**步骤，发生在 HIR/MIR 之后、字节码发射之前：

```
AST
 └─ HIR（去语法糖 + 泛型单态化）
      └─ 符号解析（新增）
           └─ 链接器（新增）  ← 这里
                └─ MIR → 字节码发射
                     └─ .auz 打包
```

### 7.2 链接流程

```text
输入：
  - 主模块源码 (.aura)
  - 依赖列表（来自 aura.toml + // @depends）
  - 各依赖的 .auz 制品（含 lib/ + ref/）

输出：
  - 一个自包含的 .auz（应用）或 .auc（单模块）

步骤：
  1. 加载主模块 AST + 解析 imports
  2. 对每个 import：
     a. 在 .auz 的 ref/index.json 中查找符号
     b. 验证类型签名匹配
     c. 记录符号引用（module_uuid, symbol_name, sig_id）
  3. 展开传递依赖：递归处理每个库的依赖
  4. 检测冲突：
     - 两个库导出同名符号 → 报错
     - 同一库的多个版本 → 报错
     - 类型签名不匹配 → 报错
  5. 生成 MIR 时，跨模块调用发射为 `CallExternal(mod_uuid, sym_idx)`
  6. 字节码发射时：
     - 本模块函数保留 `Call(idx)`
     - 外部调用保留 `CallExternal(mod_uuid, sym_idx)`
     - 模块依赖列表写入 .auz 的 lib/index.json
  7. 打包成 .auz（或纯应用的 .auc）
```

### 7.3 符号解析规则

**import 语法扩展**（保持向后兼容）：

```aura
// 导入标准库
import std.io.println
import std.math.*

// 导入库（新增：可指定版本）
import "aura-json" as json              # 默认最新兼容版本
import "aura-json@^1.2" as json         # 显式版本约束
import "aura-http" from git@github.com:user/http.git  # 源码依赖（旧行为）

// 导入库的特定符号
import json.{parse, stringify}
import json.*
```

**解析优先级**：
1. `ref/` 中的签名（编译期，强类型检查）
2. `lib/` 中的字节码（运行期，符号索引）
3. 源码（本地 `from path` 依赖，走现有流程）

**冲突检测**：
- 库 A 导出 `foo.bar`，库 B 也导出 `foo.bar` → 链接错误
- 库 A v1.0 与 v1.5 同时被依赖 → 版本冲突（沿用现有 `has_conflict`）

### 7.4 死代码消除

链接期可做**跨模块 DCE**：
- 未被主模块引用（直接或间接）的库函数 → 不打包
- 减少最终 .auz 体积
- 与 P5 的 `dce_mir` 修复协同

### 7.5 树摇（Tree Shaking）

对库包可选启用：
- 库作者标记 `@TreeShake` 的函数允许被消除
- 默认保守：只消除未被引用且无副作用的函数
- 副作用标记：`@SideEffect` 强制保留

## 8. 运行时多模块加载

### 8.1 ModuleRegistry

新增 `compiler/src/vm/module_registry.rs`：

```rust
pub struct ModuleRegistry {
    /// 已加载模块，按 module_uuid 索引
    modules: HashMap<Uuid, LoadedModule>,
    /// 模块名 → uuid
    name_index: HashMap<String, Uuid>,
    /// 符号表：(module_uuid, symbol_name) → (LoadedModule, function_idx)
    symbol_table: HashMap<(Uuid, String), (Uuid, u16)>,
    /// 原生函数：全局命名空间（沿用现有 native_index 思路，但加前缀）
    native_table: HashMap<String, NativeFn>,
}

impl ModuleRegistry {
    /// 从 .auz 加载一个库模块
    pub fn load_library(&mut self, apkg_path: &Path) -> Result<Uuid, VmError>;

    /// 从字节码模块注册
    pub fn register(&mut self, module: &BytecodeModule) -> Result<Uuid, VmError>;

    /// 解析符号：(module_uuid, symbol_name) → 可调用目标
    pub fn resolve(&self, module: Uuid, symbol: &str) -> Option<CallTarget>;

    /// 注册原生函数（带模块前缀）
    pub fn register_native(&mut self, module: Uuid, name: &str, fn: NativeFn);
}
```

### 8.2 调用分发

VM 的 `CallExternal(mod_idx, sym_idx)` 执行流程：

```text
1. mod_idx 查 ModuleRegistry.modules → LoadedModule
2. sym_idx 查 module.exports[sym_idx] → function_idx
3. 调用 LoadedModule.funcs[function_idx]
4. 若函数是 native，转调 native_table
```

### 8.3 NativeRegistry 扩展

当前 `NativeRegistry::with_modules(&modules_refs)` 只支持 std 模块。升级为：

```rust
pub struct NativeRegistry {
    /// std 模块原生函数
    std_modules: HashMap<String, NativeFn>,
    /// 库模块原生函数（key = "{module_uuid}.{name}"）
    lib_natives: HashMap<String, NativeFn>,
    /// 全局原生函数（FFI extern 声明的）
    global_natives: HashMap<String, NativeFn>,
}
```

**冲突解决**：
- 同名 native 在不同模块 → 通过 uuid 前缀隔离
- 库的 native 优先于 std（可覆盖行为，需显式声明）

### 8.4 加载策略（基于 kind）

| 时机 | 场景 | 加载方式 |
|------|------|----------|
| 应用启动时 | 直接运行 .auz 应用 | 主线程加载主模块 + 依赖 |
| 首次调用时 | 库 A 首次被调用 | 延迟加载库 A 及其依赖 |
| 显式加载 | 用户调用 `loadLibrary("x.auz")` | 手动加载 |

**默认策略**：延迟加载（lazy），与 Java 类加载器一致，节省启动时间。

### 8.5 制品选择逻辑（kind 驱动）

加载 `.auz` 时，根据 `kind` 字段和当前平台决定加载路径：

```rust
fn load_package(apkg: &Package) -> Result<LoadedModule, VmError> {
    let triple = current_triple();
    let native_path = format!("native/{}/", triple.to_string());
    
    match apkg.kind {
        PackageKind::Bytecode => {
            // 仅字节码：加载 lib/
            load_bytecode(apkg, "lib/")
        }
        PackageKind::Hybrid => {
            // 混合：优先 native，回退 lib
            if apkg.has_file(&native_path) {
                load_native(apkg, &native_path)
            } else {
                load_bytecode(apkg, "lib/")
            }
        }
        PackageKind::Native => {
            // 仅原生：必须有匹配的 native
            if apkg.has_file(&native_path) {
                load_native(apkg, &native_path)
            } else {
                Err(VmError::NoCompatibleArtifact(
                    format!("需要 {} 平台制品，但包中无此平台", triple)
                ))
            }
        }
    }
}
```

### 8.6 GC 与内存

- 已加载模块常驻（除非显式卸载）
- 模块内对象走 ARC（P7）
- 模块卸载时释放所有内部引用（`ModuleRegistry.drop_module(uuid)`）
- AOT 原生库加载后常驻（由 OS 管理内存）

### 9.1.1 包类型（kind）说明

| kind | lib/ | native/ | 适用场景 | 运行时行为 |
|------|:----:|:-------:|----------|------------|
| `bytecode` | ✅ 必需 | ❌ 不需要 | 跨平台、性能不敏感 | 仅字节码解释/JIT |
| `hybrid` | ✅ 必需 | ✅ 必需 | **推荐**，兼顾性能与兼容 | 优先 native，回退 lib |
| `native` | ❌ 可选 | ✅ 必需 | 平台锁定、性能敏感 | 仅 native，无回退 |

**运行时加载逻辑**：
```text
1. 检查 native/{current_triple}/ 是否存在
   - 存在 → 加载 AOT 原生库（快，95% C 性能）
   - 不存在 → 继续
2. 检查 lib/ 是否存在
   - 存在 → 加载字节码（跨平台兜底）
   - 不存在 → 报错：无兼容制品
```

### 9.1.2 三种包类型的示例

**纯字节码包**（`kind = "bytecode"`）：
```
foo-1.2.3.auz/

├── lib/                     # ✅ 必需
├── ref/                     # ✅ 必需
└── resources/               # 可选
```

**混合包**（`kind = "hybrid"`，推荐）：
```
foo-1.2.3.auz/
├── META-INF/aura.toml       # kind = "hybrid"
├── lib/                     # ✅ 必需（兜底）
├── ref/                     # ✅ 必需
├── native/                  # ✅ 必需（性能）
│   ├── x86_64-pc-windows-msvc/
│   └── x86_64-unknown-linux-gnu/
└── resources/               # 可选
```

**纯原生包**（`kind = "native"`）：
```
foo-1.2.3.auz/
├── META-INF/aura.toml       # kind = "native"
├── ref/                     # ✅ 必需（类型签名）
├── native/                  # ✅ 必需
│   ├── x86_64-pc-windows-msvc/
│   └── x86_64-unknown-linux-gnu/
└── resources/               # 可选
```

**保留**：
- `// @depends` 注释形式的内联依赖
- 简单的 `[dependencies] name = "version"` 语法

```text
    u16        package           # 所属包
    u16        param_count
    param_types[]                 # 参数类型（引用类型表）
    return_type                   # 返回类型（引用类型表）
    u16        is_static
    u16        is_virtual
    u16        is_abstract

# ── 导出符号索引 ──
u32            n_exports
  每个导出:
    u16        symbol_name
    u8         kind              # 0=function, 1=class, ...
    u32        ref_id            # 引用类型表或签名表的 ID
```

**为什么单独一个 `.sig` 而不是嵌入 `.auz` 内**：
- `.auz` 内已经有 `ref/` 目录，存的就是 `.sig` 文件
- 独立文件格式便于单独分发（类似 Java 的 `.class` 单独存在）

## 11. 依赖解析与传递依赖

### 11.1 双通道解析

```text
输入依赖：aura-json = "^1.2"

解析流程：
  1. 查缓存 ~/.aura/cache/auz/aura-json/
     - 若有匹配版本 → 使用缓存
  2. 查 Git tag（若未指定 source）
     - 若有 v1.x tag → git clone --depth 1
     - 若有 aura-json-1.x.auz 附件 → 下载 .auz（优先）
  3. 回退：git clone 源码 → 本地 aura build --lib → 缓存 .auz
  4. 写入 aura.lock（含 .auz 的 SHA-256）
```

**优先级**：`.auz` > Git tag > 源码克隆

### 11.2 传递依赖

库 A 依赖库 B：
- A 的 `aura.toml` 声明 `B = "^2.0"`
- 加载 A 时，递归解析 B
- 版本冲突时，报错并显示依赖链

**示例**：
```
main → aura-http@^1.0 → aura-json@^2.0
     → aura-cache@^1.0 → aura-json@^1.0   ← 冲突
```

### 11.3 缓存策略

```text
~/.aura/cache/
├── auz/                       # 二进制制品缓存（新增）
│   └── aura-json/
│       ├── 1.2.3/
│       │   └── aura-json.auz
│       ├── 1.2.2/
│       │   └── aura-json.auz
│       └── index.json          # 本地索引
```

## 12. 平台策略与 AOT 混合

### 12.1 三种包类型对比

| 类型 | kind | lib/ | native/ | 适用场景 | 性能 |
|------|:----:|:----:|:-------:|----------|------|
| 纯字节码 | `bytecode` | ✅ | ❌ | 跨平台、性能不敏感 | ~50% C |
| 混合包 | `hybrid` | ✅ | ✅ | **推荐**，兼顾性能与兼容 | ~95% C（有 native 时） |
| 纯原生 | `native` | ❌ | ✅ | 平台锁定、性能敏感 | ~95% C |

### 12.2 纯字节码包（`kind = "bytecode"`）

```
aura-json-1.2.3.auz/
├── META-INF/aura.toml       # kind = "bytecode"
├── lib/aura-json/*.auc      # 必需
└── ref/aura-json.sig        # 必需
```

**适用**：跨平台、性能要求不极端、体积敏感。

### 12.3 混合包（`kind = "hybrid"`，推荐）

```
aura-json-1.2.3.auz/
├── META-INF/aura.toml       # kind = "hybrid"
├── lib/aura-json/*.auc      # 必需（兜底）
├── ref/aura-json.sig        # 必需
├── native/                  # 必需（性能）
│   ├── x86_64-pc-windows-msvc/aura-json.dll
│   └── x86_64-unknown-linux-gnu/libaura-json.so
└── resources/               # 可选
```

**运行时行为**：
1. 检查 `native/{current_triple}/`
2. 若存在 → 加载原生库（快，95% C 性能）
3. 若不存在 → 加载字节码（跨平台兜底）

### 12.4 纯原生包（`kind = "native"`）

```
aura-json-1.2.3.auz/
├── META-INF/aura.toml       # kind = "native"
├── ref/aura-json.sig        # 必需（类型签名）
├── native/                  # 必需
│   ├── x86_64-pc-windows-msvc/aura-json.dll
│   └── x86_64-unknown-linux-gnu/libaura-json.so
└── resources/               # 可选
```

**适用**：平台锁定的高性能库。
**限制**：跨平台不可用；运行时必须有匹配的 native 制品。

### 12.5 平台探测

编译器启动时确定当前 triple（沿用现有 `TargetTriple::default()`），运行时 VM 也探测：

```rust
pub fn current_triple() -> TargetTriple {
    match (cfg!(target_os = "windows"), cfg!(target_arch)) {
        (true, "x86_64") => TargetTriple::WindowsX64,
        (false, "x86_64") => TargetTriple::LinuxX64,
        (false, "aarch64") => TargetTriple::LinuxAarch64,
        _ => panic!("unsupported platform"),
    }
}
```

## 13. 安全性

### 13.1 校验和（必需）

每个 `.auz` 内必须有 `META-INF/checksum.sha256`：

```text
abc123...  META-INF/aura.toml
def456...  lib/aura-json/parse.auc
...
```

格式与 `sha256sum` 一致，方便 CLI 工具处理。

### 13.2 签名（可选）

**方案**：HMAC-SHA256（轻量、无需公钥基础设施）

```text
signature.sig:
u32          magic = "AUSG"
u16          version = 1
u8           key_id_len + key_id       # 密钥 ID（可追溯）
u32          signature_len + hmac      # HMAC-SHA256(checksum.sha256)
```

**密钥管理**：
- 库作者持有私钥
- 用户通过 `aura config add-key --id aura-json --pub <hex>` 添加公钥
- 验证时查本地公钥表

**为什么不用 RSA/ECDSA**：
- HMAC 实现简单（`hmac` crate）
- 无密钥生成负担
- 对 Aura 这种"作者即信任"的场景够用
- 后续可升级为 RSA 而格式兼容（key_id 区分算法）

### 13.3 版本兼容

加载前检查：

```rust
fn check_compatibility(module: &BytecodeModule, current_compiler: &Version) -> Result<(), VmError> {
    if module.compiler_min_version > *current_compiler {
        return Err(VmError::Incompatible(format!(
            "模块需要编译器 >= {}, 当前 {}",
            module.compiler_min_version, current_compiler
        )));
    }
    if let Some(max) = module.compiler_max_version {
        if *current_compiler > max {
            return Err(VmError::Incompatible(...));
        }
    }
    Ok(())
}
```

### 13.4 供应链攻击防护

| 威胁 | 防护 |
|------|------|
| 源码篡改 | Git 内容寻址 + tag 不可变 + checksum |
| 二进制篡改 | .auz 内 checksum + 可选签名 |
| 中间人 | Git 走 HTTPS；直接文件走 checksum 验证 |
| 供应链升级（Typosquatting） | 包名前缀 `aura-` 建议；可选签名强制 |
| 依赖混淆 | 传递依赖冲突检测 |

## 16. 附录：与其他语言的细节对照

### 16.1 JAR vs .auz

| 维度 | JAR | .auz |
|------|-----|-------|
| 容器 | ZIP (deflate) | tar + zstd |
| 主清单 | META-INF/MANIFEST.MF | META-INF/aura.toml |
| 字节码 | classes/*.class | lib/*.auc |
| 入口标识 | Main-Class: 字段 | entry 字段 |
| 多平台 | ❌ | ✅（native/） |
| 资源 | 任意 | resources/ |
| 嵌套 | lib/*.jar | lib/**/*.auz |
| 签名 | 签名 manifest | META-INF/signature.sig |
| 类型元数据 | .class 内含 | ref/*.sig |
| 语言特定 | JVM 字节码 | Aura 字节码 |
| 压缩算法 | deflate | zstd（更高压缩比 + 更快解压） |

### 16.2 rlib vs .auz

| 维度 | rlib | .auz |
|------|------|-------|
| 容器 | ar (无压缩) | tar + zstd |
| 内容 | LLVM bitcode + 对象 | 字节码 + 可选原生 |
| 类型元数据 | Cargo metadata | ref/*.sig |
| 链接时机 | 编译期 | 编译期 + 运行期 |
| 运行期加载 | ❌ | ✅ |
| 依赖 | Cargo.toml + Cargo.lock | aura.toml + aura.lock |
| 压缩 | 无 | zstd（~30-40% 更小） |

### 16.3 nupkg vs .auz

| 维度 | nupkg | .auz |
|------|-------|-------|
| 容器 | ZIP (deflate) | tar + zstd |
| 主清单 | Package.xml | META-INF/aura.toml |
| 字节码 | lib/{tfm}/*.dll | lib/*.auc |
| 类型元数据 | ref/{tfm}/*.dll | ref/*.sig |
| 多平台 | lib/{tfm}/ | native/{triple}/ |
| 构建脚本 | build/*.targets | build/ |
| 签名 | nuspec + 签名块 | signature.sig |
| 压缩算法 | deflate | zstd（更高压缩比 + 更快解压） |

## 17. 附录：关键设计决策回顾

| # | 决策 | 选择 | 理由 |
|---|------|------|------|
| D1 | 容器格式 | tar + zstd | 压缩比 +30-40%（vs ZIP+deflate），解压快 5-10x，内置 xxhash64 校验，Rust `tar`+`zstd` crate 成熟 |
| D2 | 扩展名 | `.auz` | 4 字符（对齐 `.auc`/`.aura`），语义清晰 |
| D3 | 主清单 | TOML | 与 `aura.toml` 一致，避免双格式 |
| D4 | 类型签名 | 独立 `.sig` 文件 | 与字节码分离，编译期可单独加载 |
| D5 | 跨模块调用 | 索引（非名字） | O(1) 解析，抗混淆 |
| D6 | 字节码版本 | 保持 `AURA` 魔数 + version=1 | 开发期重设计，新格式即标准，无需兼容旧实现 |
| D7 | AOT 策略 | `kind` 字段区分三种包类型（bytecode/hybrid/native） | 明确字节码与 AOT 的取舍，运行时自动选择最优路径 |
| D8 | 签名算法 | HMAC-SHA256 | 轻量、够用、可扩展到 RSA |
| D9 | 加载时机 | 延迟加载 | 节省启动时间，对齐 Java |
| D10 | 依赖通道 | 二进制优先，源码回退 | 兼容现有源码分发 |
