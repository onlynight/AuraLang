## 1. 当前基线

### 1.1 关键数字

自编译一次（`--mem-trace`）：

```
[mem] start = 0 MB
[mem] link done modules=51 nodes=54184 = 38 MB
[mem] emit + toolchain done = 67 MB
```

| 指标 | 数值 | 说明 |
|---|---|---|
| 峰值 RSS | **110.4 MB** | `WorkingSet64` 25 ms 采样取最大 |
| 终态存活（`aura_mem_used`） | **67 MB** | 其中 link 38 MB、emit 29 MB |
| 耗时 | **9.3 s** | 与优化前持平 |
| 产物 IR 文本 | **≈ 4.1 MB** | `*.ll` 文件大小 |

### 1.2 三个阶段的累计效果

| 指标 | 优化起点 | 现在 | 累计降幅 |
|---|---|---|---|
| link 存活 | 57 MB | 38 MB | −33% |
| 发射+工具链存活 | 195 MB | 67 MB | **−66%** |
| 峰值 RSS | ≈ 412 MB | 110.4 MB | **−73%** |

已完成的三阶段（本文的起点）：

| 阶段 | 主要手段 |
|---|---|
| 一 | 原生 `StringBuilder`（`EmitBuffer`）替代「List 分段 + 树形归并」拼 IR |
| 二 | `inferType` 记忆化、并行键列精确比较、`sanitizeLlvm` 单趟快路径 |
| 三 | 签名表**只建一次**、跳过 C 后端备选源码、词法关键字表去 `split`+O(n²)、逐字符字面量改单次切片、`emitFunction` 去临时缓冲、声明生成改缓冲区累积 |

### 1.3 一个重要口径问题：16 B 头部不计入统计

`aura_mem_used_bytes()` 返回的是 **payload 字节数**，不含分配头：

```c
// compiler/src/std/cffi/aura_std_cffi.c
typedef union AuraMemHdr {          // sizeof == 16（int64 size + int64 pad / 对齐）
    struct { int64_t size; int64_t pad; } h;
    long double align_ld;
    void *align_p;
} AuraMemHdr;

void *aura_mem_alloc(int64_t n) {
    AuraMemHdr *h = malloc(sizeof(AuraMemHdr) + n);
    h->h.size = n;
    g_aura_mem_used += n;           // ← 只累加 payload
    return (char *)h + sizeof(AuraMemHdr);
}
```

因此：

- **每笔分配隐式多花 16 B**，`aura_mem_used` 看不到；
- 终态 67 MB 存活 vs 峰值 RSS 110.4 MB，**约 43 MB 差额**里的主要部分就是这个头部开销 + 分配器碎片 + 进程基线；
- 想估算真实开销，可以临时给 `aura_mem_alloc` 加一个「分配次数」计数器：`RSS ≈ 67 MB + 16 B × 分配次数 + 基线`。

> **结论**：后续优化若以「减少分配**次数**」为目标，收益会大于 `aura_mem_used` 上的数字。

## 2. 测量方法论（继续归因前必读）

这三阶段的所有结论都来自「先测量、再动手」，且**插桩完成后必须全部清除**。可复用的手法：

### 2.1 分阶段标记（现成）

```powershell
.\build\bin\aura-compiler-opt5.exe .\aura\compiler\aura\lang\compiler\Main.aura -o out.exe --mem-trace
```

`--mem-trace` → `aotBuildExeFileTraced` → `aotMemMark(tag)` → 打印 `[mem] <tag> = <n> MB`。
插入点见 `aura/compiler/aura/lang/compiler/Main.aura`（`start` / `link done` / `emit + toolchain done`）。

### 2.2 字节级细粒度探针

`aotMemMB()` 只有 MB 精度，看不到 <1 MB 的增量。需要字节粒度时临时暴露：

1. `compiler/src/codegen/aot/runtime.rs`：`RUNTIME_FUNCTIONS` 里加 `aura_mem_used_bytes`（`i64`，无参）；
2. `aura/.../aot/Runtime.aura`：`runtimeTable()` 加一行 `"aura_mem_used_bytes|i64|\n"`；
3. `aura/.../aot/AotUtil.aura`：加 `fun aotMemBytes(): Long { return aura_mem_used_bytes() }`。

> ⚠️ 第 1、2 步会让 **每份产出 IR 多一条 `declare`**，使 IR 逐字节对比全数 DIFF；**必须在提交前删掉**。
> ⚠️ 第 2 步会改变 `runtimeFunctionCount()`，`tests/phase6_aot_tests.aura` / `phase6_5_aot_tests.aura` 断言它为 `11`，插桩期间这两个套件会失败。

### 2.3 两种高价值归因手法

**(a) 自耗减子耗（exclusive attribution）**

对被测函数做 `X` / `XInner` 包装，用「当前嵌套累计」字段把子调用的开销减掉：

```aura
var tpKids: Long = 0
var tpWX: Long = 0

fun X(...): T {
    val m:  Long = aotMemBytes()
    val k0: Long = this.tpKids
    val r: T = this.XInner(...)
    val m2: Long = aotMemBytes()
    this.tpWX = this.tpWX + (m2 - m) - (this.tpKids - k0)
    this.tpKids = k0 + (m2 - m)
    return r
}
```

多返回点函数也一样适用（包装层只有一个返回点）。递归也正确。

**(b) 对照实验（删掉再测）**

比继续插桩更快、更可信。例：想确认「6 条 span Int 列表」的占比，就把 `Lexer.emit()` 里那 6 行 `add` 注释掉，重新编译并对比 —— 实测 **42.3 MB → 35.4 MB，即 6.9 MB**。测完恢复。

> 对照实验可以故意让程序功能不正确（比如停写字面量），只要还能跑完到打点位置即可。

### 2.4 内存以外：性能的归因入口

`Lexer.peek()` 每次都落 `aura_string_charAt(s, idx)`，而该实现里有 `strlen(s)`：

```c
const char *aura_string_charAt(const char *s, int64_t idx) {
    if (!s || idx < 0 || (size_t)idx >= strlen(s)) return "";
    return aura_char_cache((unsigned char)s[idx]);   // 1 字符串有缓存，不分配
}
```

所以**单字符取用不分配**（这是好事），但 `strlen` 让「逐字符扫描」变成 **O(n²) 时间**。
`aura_lang_std_String_charCodeAt` 已经去掉了 `strlen`（O(1)）；**纯比较场景应改用 `charCodeAt`**：

```aura
if (list.charCodeAt(i) == 44) { ... }      // 优于 toStr(list[i]) == ","
```

这条是**时间优化**（不影响内存），但在词法/解析的热循环里收益明显。

## 3. 内存去向分解

### 3.1 link 阶段 38 MB

| 子项 | 实测 | 占比 | 备注 |
|---|---|---|---|
| `read` | 1.19 MB | 3% | `FileSystem.readText` 的源码文本（51 份，永久驻留） |
| `lex` | **21.0 MB** | **55%** | 词法分析 |
| `ast` | **9.2 MB** | **24%** | 建 AST arena |
| `lower` | **7.4 MB** | **20%** | AST → HIR |
| `join` | 23 KB | 0% | 已优化（`joinPieces` 树形归并） |
| `pre` | 163 KB | 0% | `normalizePath` / `exists` 等 |

> 注意：`ast` 与 `lower` 的产物 HIR **是后续发射必需的存活数据**；AST 在降级后即成为垃圾（AOT 无 GC ⇒ 永久驻留）。

### 3.2 词法 21 MB（107.5 k tokens，≈200 B/token）

| 子项 | 实测 | 含义 |
|---|---|---|
| `all` | 20.9 MB | `scanAll()` 整体 |
| └ `emit` | 9.3 MB | **8 条并行列表的 `add`**（几何扩容含 realloc 拷贝） |
| └ `ident` | 15.4 MB | `scanIdentifier`（含其 emit 部分） |
| └ `doc` | 203 KB | 文档注释切片 |
| └ `str` | 788 KB | 字符串/字符字面量扫描 |
| └ `num` | 287 KB | 数字字面量扫描 |
| └ `rest` | 4.2 MB | `skipTrivia` + 类型分派 + `peek` |
| `init` | 22 KB | 关键字表（已优化，原为 8.8 MB × 2） |

`Lexer` 的输出是 **8 条按 token 对齐的并行列表**（`kindList` / `litList` / `spanStart` / `spanEnd` / `spanStartLine` / `spanStartCol` / `spanEndLine` / `spanEndCol`）：

```
8 条最终数组：107.5k × 8 槽 × 8 B         ≈ 6.9 MB
几何扩容浪费（容量翻倍，旧块被 realloc 复用，但最终容量可达 2×） ≈ 3 MB
────────────────────────────────────────────────
列表本体合计                               ≈ 10 MB   （对照实验实测 6.9 MB 仅 span 6 列）
```

### 3.3 发射阶段 29 MB

| 子项 | 实测（阶段二插桩，之后又降约 5 MB） | 备注 |
|---|---|---|
| `emitProgram` 合计 | 36 MB → 现约 **29 MB** | |
| └ 函数定义发射（`emitFunction`） | 26 MB → 现约 **22 MB** | 其中 body 14.8 MB、params 1.06 MB、其余为缓冲拷贝 |
| └ 结构体 / 签名表 / 别名 | 0.6 MB | |
| └ 模块组装 | ≈ 4 MB | `funcParts → out` 的一次全量拷贝 |

IR 文本本身约 4.1 MB。发射期**每次跨缓冲区合并就是一次 IR 量级的拷贝**：

```
函数级：fAlloca → funcParts    (1 次，≈4 MB 总和)
        fBody   → funcParts    (1 次，≈4 MB 总和)
模块级：structParts  → out     (≈ 小)
        stringParts  → out     (≈ 小)
        funcParts    → out     (1 次，≈4 MB)
```

## 4. 优化清单

按**收益 ÷ 风险**排序。每项给出：现状 / 证据 / 改法 / 预期 / 风险 / 验证。

### L1 · 词法：span 的 4 条行列列表惰性化  ★★★☆☆

- **现状**：`Lexer.emit()` 每 token 追加 6 个 Int（`spanStart` / `spanEnd` / `spanStartLine` / `spanStartCol` / `spanEndLine` / `spanEndCol`）。
- **证据**：对照实验 —— 停写 6 条 ⇒ 21 MB 档位的 lex 从 42.3 MB 降到 35.4 MB（**6.9 MB**）。其中 4 条是行列。
- **改法（推荐）**：只保留 `spanStart` / `spanEnd`（字节偏移），行列改为**按需计算**：
  - 在 `Lexer` 里建一次「行首偏移表」（`List<Int>`，约 3 万行 ⇒ 240 KB）；
  - `spanFieldAt(index, 2..5)` 用二分查找偏移 → (line, col)；
  - `Parser.prsCurSpan()` 已经是「每节点一次」的调用点，成本可控。
- **预期收益**：约 **−5 MB**（4 条列表 + 其扩容），并让 `Lexer` 状态更简单。
- **风险**：中。错误信息的行列若算错会影响 `phase1_lexer_tests` 的报错断言；需逐个校验。
- **更小的替代方案**：把 (startLine,startCol) 打包成一个 Int（`line * 100000 + col`）、(endLine,endCol) 同理 ⇒ 4 条降为 2 条，约 −2.5 MB，风险低。

### L2 · 词法：列表预分配 / 合并  ★★☆☆☆

- **现状**：8 条 `arrayListOf` 从容量 4 开始几何翻倍；107.5 k 元素要经历约 15 次扩容，且**最终容量常是实际用量的 1.0–2.0 倍**。
- **改法**：
  - 若运行时有「按容量构造」的入口（`ArrayList<String>(cap)`），用源码长度估算：`cap ≈ src.length() / 4`；
  - 或者把 6 条 Int 列表合并为 1 条「stride = 6」的列表（同样的槽位数，但只经历一次扩容序列，realloc 复用率更高）。
- **预期收益**：约 **−2 ~ −3 MB**（扩容浪费）。
- **风险**：低（合并列表需同步改 `emit` / `spanFieldAt` 两处）。
- **注意**：合并成 stride 形式**不会**减少槽位总量，收益只来自扩容序列的减少。

### L3 · 词法：`keywordLookup` 的每次 2 次小分配  ★★☆☆☆

- **现状**：每次标识符（约 5 万个）都要构造 `word + "|"` 与 `"\n" + word + "|"` 两个针串，命中时再加 2 次 `substring`。
- **改法**：把关键字表按**首字母分桶**（`a|...`、`b|...`），先用 `word.charCodeAt(0)` 定位桶，再在桶内线性比较；或直接在表上按「行首 + 逐字符 `charCodeAt` 比较」扫描（表约 1.3 KB，纯整数比较）。
- **预期收益**：约 **−2 ~ −4 MB**（每标识符 2 次小分配 × 5 万次）。
- **风险**：中低（改写查找逻辑，`phase1_lexer_tests` 有完整关键字断言可回归）。

### P1 · 前端：避免 AST 与 HIR 双份常驻  ★★★★☆

- **现状**：`AotModuleLinker.loadPath` 为每个文件构造 `Parser`（内含完整 token 列表 + `Ast`），降级成 HIR 后，**token 列表与 AST 全部成为永久垃圾**。
- **证据**：`lex` 21 MB + `ast` 9.2 MB = **30 MB 属于「用完即弃」**，占 link 的 79%。
- **改法（按难度递增）**：
  1. **单文件流式**：`Parser` 消费完即丢弃（已经如此），但 AOT 无 GC ⇒ 无效，除非有回收。
  2. **引入区域分配 + 单文件边界重置**：`loadPath` 返回后把「本文件专属的 arena」整体丢弃。需要运行时支持「区域」语义（见 D1）。
  3. **不做 AST，直接 `Parser → HIR`**：把 `lowerXxx` 的逻辑内联进 `parseXxx`，省掉整个 AST arena（**约 −9 MB**）与一次遍历。这是**收益最大**的一项，但改动面覆盖 Parser + HirLowerer 两个模块。
- **预期收益**：**−9 MB（省 AST）**，若配合区域分配可再省 token 列表的 21 MB。
- **风险**：高（P1-3）；建议**放在有充分回归能力之后**再动。
- **验证**：IR 逐字节一致 + HIR `dump()` 逐字节一致。

### E1 · 发射：消除 `funcParts → out` 的全量拷贝  ★★★☆☆

- **现状**：`emitProgram` 末尾 `out.sbAdd(this.funcParts.sbBuild())`，把约 4 MB 的函数文本整体复制进最终缓冲。
- **阻塞点**：输出顺序是 `头 → 结构体 → 字符串常量 → runtime 声明 → 调试 → 函数`，而**字符串常量是在发射函数体过程中累积的**，所以 `funcParts` 无法直接当最终缓冲。
- **改法**：
  1. 让 `stringParts` 也成为「可提前」的：在函数发射**之前**先扫一遍 HIR 收集字符串字面量（一次只读遍历，不发射），把 `stringParts` 提前填好；
  2. 之后就能把 `out` 直接换成 `funcParts`：头部/结构体/字符串/runtime/调试全部先写进 `funcParts`，函数再原地追加 ⇒ **函数文本 0 次额外拷贝**。
- **预期收益**：约 **−4 MB**。
- **风险**：中。需要保证「预扫描」与「发射期注册」得到的字符串常量集合、**顺序与编号完全一致**（`@str.N` 编号会写进 IR）。
- **替代低风险方案**：只把 `structParts` / `runtimeDeclarations()` 提前写入 `structParts`，让拷贝次数从 3 降到 2 ⇒ 约 −2 MB。

### E2 · 发射：函数体内的 String 返回形态  ★★☆☆☆

- **现状**：`emitExpr` / `emitCall` / `emitBinary` / `coerceValue` / `freshVar` 等仍返回 `String`（SSA 名、常量文本）。每次调用至少 1 次分配；`freshVar()` 为 `"%var." + toStr(n)` 共 2 次。
- **改法**：
  - `freshVar` / `freshBb`：用**原生缓冲区 + 计数器**直接产出名字（或让名字只在下标处按需拼装）；
  - 把「返回拼接结果」的辅助函数改为「追加进传入缓冲区 + 返回值名」。
- **预期收益**：约 **−2 ~ −4 MB**，并且同时减少**分配次数**（对 RSS 有额外好处）。
- **风险**：中高（调用点数量大）。建议先做 `freshVar` / `freshBb` 这两个最热的。

### E3 · 发射：`runtimeDeclarations` 的 `split("\n")` 残留  ★☆☆☆☆

- **现状**：`appendDeclarations` / `appendNameList` 仍用 `table.split("\n")` 一次切出全部行（约 300 行 ⇒ 300 个子串 + 一张 List），且 `preludeTable()` / `runtimeTable()` 在一次 `emitProgram` 里会被取多次。
- **改法**：改为 `aotFieldAt`-style 单趟扫描（按 `\n` 定位、`substring` 只切需要的字段），或把三张表在 `emitProgram` 的 `fStdTable`/`fRtTable`/`fCffiTable`/`fPreTable` 之外再补一个「名字清单」缓存。
- **预期收益**：约 **−1 MB**。
- **风险**：低。

### E4 · HIR：`kids` 的字符串编码  ★★★☆☆

- **现状**：`Hir.kids` 是 `List<String>`，每个节点的子节点列表形如 `"1,2,3"`。
  - `hirKidsCount(list)` 逐字符扫描；
  - `hirKidsAt(list, i)` = 定位第 i 段 + 内联解析十进制（**已改为零分配**，但仍是 O(len) 扫描）。
- **改法**：改为 CSR 布局（`kidsFlat: List<Int>` + `kidsOffset: List<Int>`）：
  - `hirKidsAt(id, i) = kidsFlat[kidsOffset[id] + i]` **O(1) 零分配**；
  - `hirKidsCount(id) = kidsOffset[id+1] - kidsOffset[id]`。
- **预期收益**：内存上主要是**去掉 `kids` 的字符串数组**（每节点 1 个 String 槽 + 内容串）⇒ 约 **−2 ~ −3 MB**；**时间收益更大**（消除发射/降级最热路径上的线性扫描）。
- **风险**：中高（`Hir.add` / `hirKidsAdd` / 全部 `hirKidsAt` 调用点）。需要 IR 逐字节一致作为红线。

### D1 · 运行时：区域分配 / 单文件边界回收  ★★★★★

- **现状**：AOT 运行时没有 GC，`aura_mem_free` 存在但几乎无人调用 ⇒ 一切「临时数据」都是永久泄漏。
- **改法**：给 `AuraMemHdr` 增加一个 **arena tag**，允许「按 tag 整体释放」。典型用法：`loadPath` 在解析+降级期间把 arena 标为 `file:tmp`，函数返回前统一释放（字符串池与 HIR 归 `persist`）。
- **预期收益**：**最大的一项** —— link 阶段 30 MB 的「用完即弃」数据（token 列表 21 MB + AST 9.2 MB）可以被真正回收，link 存活有望从 38 MB 降到 **10 MB 量级**。
- **风险**：高。需要非常小心地界定「哪些数据在降级后仍被 HIR 引用」（HIR 的 `texts` 里有很多切片来自源码串）。**建议先写清所有权规则，再动代码**。
- **前置**：这是 P1 的「通用解」，比逐个模块优化更根本。

### D2 · 口径：把 16 B 头部计入统计  ☆☆☆☆☆

- **现状**：`g_aura_mem_used` 只统计 payload，导致 `--mem-trace` 的数字系统性低估真实占用（见 1.3）。
- **改法**：`g_aura_mem_used += n + sizeof(AuraMemHdr)`（或另加一个 `g_aura_mem_alloc_count`）。
- **收益**：不是优化，但让后续所有归因**更接近 RSS**，避免「优化了体积、RSS 不降」的困惑。
- **风险**：极低（只影响诊断数值）。**注意**：会改变现有 `--mem-trace` 的历史数值可比性，需在文档中说明。

## 5. 已知编译器缺陷（会阻塞这类改动）

### 5.1 AOT 后端：方法内「首次赋值类字段」被错误编译

**症状**：Aura AOT 后端产出的编译器，在编译**任何**程序时生成**空函数段** —— 产物 IR 只有头部与声明，链接报：

```
lld-link: error: undefined symbol: main
```

（`--mem-trace` 显示 `link done modules=N nodes=6`：HIR 正常，是**发射**丢了函数。）

**最小触发形态**：

```aura
class Lexer {
    var kwTable: String = ""

    fun lxKwKind(word: String): String {
        if (this.kwTable == "") {          // ← 惰性初始化
            this.kwTable = keywordSearchTable()
        }
        return keywordLookup(this.kwTable, word)
    }
}
```

**隔离过程**：

1. `git stash` 掉改动后，用 HEAD 源码构建编译器 ⇒ 自举正常；
2. 逐个 `git checkout -- <file>` 回退，锁定到 `Lexer.aura`；
3. 再细分到「惰性初始化」这一处；改回 `init()` 内即时构建即恢复。

**两种来源的编译器都复现**：`opt3`（Aura 自举产物）与 `opt4`（Rust 后端产物）编译同一份源码均失败 —— 说明问题在「Aura 后端把该源码编译成编译器」这一步，而不是某一次运行。

**规避方式**：不要在方法内做「首次赋值类字段」的惰性初始化，改为在 `init()` 中即时构建。

**待办**：这是一个**独立的 AOT 后端缺陷**，建议单独立项定位（最小复现已具备）。它会直接阻塞 L2/L3/D1 这类「加缓存字段」的优化 —— 任何「惰性缓存」写法都要先确认是否踩中。

### 5.2 其它已知限制（写代码时避开）

| 限制 | 现象 | 规避 |
|---|---|---|
| `List<T>` 元素与 Int 直接比较 | 生成非法 IR（`icmp eq i8*, i32`） | 用 `List<String>` 存十进制串，或改 `charCodeAt` 整数比较 |
| 「经字段访问得到的对象再调方法」 | `this` 绑定错乱 | 先取局部变量再调用（`ModuleLink` / `CBackend` 均有此注释） |
| 字符串字面量 `+` 链 | **不做常量折叠**，每次调用都重新分配 | 需要常驻的表改为「缓存到 emitter/lexer 字段」，或写成**单一段字面量**（AOT 下是全局常量，零分配） |
| `split("\n")` | 每次调用切出整表（子串 + List） | 用 `tableSignature` 式的 `startsWith` / `contains` + 两次 `substring` 定位 |

## 6. 不建议做的事

| 想法 | 为什么不做 |
|---|---|
| 给 `aura_mem_alloc` 加「小对象池」 | 池本身有管理成本；当前瓶颈是**分配次数**而非单次成本，先减少次数更划算 |
| 把整份 IR 先写盘再流式拼装 | 增加 IO 与错误面；当前 IR 才 4 MB，收益小 |
| 用 `String` 编码替代并行 `List` | 已被历史证明是 O(n²)（词法/`hirKidsAt` 都因此重写过） |
| 把 `emitFunction` 的 `fAlloca`/`fBody` 合并成一个缓冲 | 会改变 IR 里 alloca 的布局位置（须保持 alloca 提前到 entry 块），**破坏 IR 逐字节一致** |
| 在发射期引入 GC | 与「零 GC 快速 AOT 产物」的整体设计冲突；用 D1 的区域分配更合适 |

## 8. 附录：完整测量脚本

### 8.1 峰值 RSS

```powershell
function PeakMB($exe, $out) {
    $p = Start-Process -FilePath $exe `
        -ArgumentList @(".\aura\compiler\aura\lang\compiler\Main.aura", "-o", $out) `
        -PassThru -NoNewWindow -RedirectStandardOutput "$out.log"
    $peak = 0
    while (-not $p.HasExited) {
        try { $p.Refresh(); if ($p.WorkingSet64 -gt $peak) { $peak = $p.WorkingSet64 } } catch {}
        Start-Sleep -Milliseconds 25
    }
    return [math]::Round($peak / 1MB, 1)
}

"baseline_MB=" + (PeakMB ".\build\bin\aura-compiler-BASE.exe" ".\build\_base.exe")
"new_MB="      + (PeakMB ".\build\bin\aura-compiler-NEW.exe"  ".\build\_new.exe")
```

> 采样间隔取 25 ms：编译器整体约 9.3 s，足够捕获峰值，又不至于拖慢。
