## 1. 总览

两个编译器性能问题截然不同：

| | `compiler/`（Rust） | `aura/compiler/`（自举） |
|---|---|---|
| 执行环境 | Rust 编译产物，原生速度 | Aura 源码 → Rust VM 解释执行 |
| 执行速度 | ns/op | ~1µs/op（README 实测 `loop1M=1.18s`） |
| 能否用多核 | **能，但未实现**（无 rayon 依赖） | **不能，架构上不可能**（单线程 VM，无并发原语） |
| 主要浪费 | 前端跑 2–3 遍；每函数全量 HIR clone；无并行 | 字符串 VM 数据结构的 O(n²)；无并发原语 |
| 优化上限 | 4–8×（多核）+ 2×（去冗余）= **~10×** | ~5×（算法清理），**架构瓶颈无法突破** |

### 1.1 关键发现

**Rust 编译器**：
- `compile_source` 对同一 source 跑 **两次** Lexer + Parser（`codegen/mod.rs:167-214`）
- `lower_function` 对每个函数做 **全量 HIR clone**（`mir.rs:1269`）
- HIR desugar 用 **9 个 thread-local RefCell 全局**，结构性阻塞并行（`hir.rs:58-75`）
- 整个编译器 **无 rayon、无 par_iter、无 thread::spawn**
- AOT emit 有 **426 处 `format!`**，每条 LLVM 指令一次堆分配

**自举编译器**：
- 编译器是 **解释执行的解释器**：Aura 源码 → Rust VM 解释 → ~1µs/op
- VM 全部数据结构用 **String** 表示（栈、locals、bytecode、funcTable），操作全 O(n²)
- `getBytecodeLine` 每指令从位置 0 扫描到 `ip` → **O(N²) 总计**
- `dispatch` 是 **30 分支 `if (opcode == "CONST_INT") { ... }` 链**
- GC / 协程 / 并发原语 **全部是 phantom 存根**（`version = "0.5.0-phase4-phantom"`）
- `Coroutine.aura` 仅 37 行，无调度器；`Gc.aura` 的 `malloc` 返回 `null`

## 2. Rust 编译器（compiler/）

### 2.1 前端重复执行（最大单一浪费）

**`compiler/src/codegen/mod.rs:167-214`** — `compile_source` 对同一 source 跑两次 Lexer + Parser：

```rust
// pass 1：解析，结果仅用于检查错误，然后丢弃
let mut lexer = Lexer::new(source);
let tokens = lexer.tokenize();
let mut parser = Parser::new(tokens);
let program = parser.parse_program();   // ← 这个 program 被丢弃

// pass 2：sema 内部再次 lex + parse
let (ast, sema) = analyze_source(source);  // ← 重新 lex + parse
```

`analyze_source`（`sema/checker.rs:4162`）内部再次 `Lexer::new(source).tokenize()` + `Parser::new(tokens).parse_program()`。

**CLI 路径更糟**：

| 命令 | 前端执行次数 |
|------|-------------|
| `aura build` | 2× |
| `aura build --aot` | 3× |
| `aura build --aot-embed` | **3×**（`embed_into_auc` 再加 1 轮） |

### 2.2 MIR 降级每函数全量 clone HIR

**`compiler/src/codegen/mir.rs:1264-1270`**：

```rust
pub fn lower_function(f: &HirFunction, ctx: &mut LowerCtx, hir: &HirProgram) -> MirFunction {
    ...
    builder.hir_program = Some(hir.clone());  // ← 每函数全量 clone！
}
```

`lower_program`（`mir.rs:1284-1303`）循环 `for f in &hir.functions` → **N 个函数 = N 次全量 HIR clone**。对编译器自身（48 模块 / 49876 HIR 节点），这是 O(N × total_size)。

### 2.3 完全无并行

`compiler/src` 下 grep `rayon|par_iter|thread::spawn|spawn_blocking` 仅匹配 `vm/thread_pool.rs:55`（运行时线程池，非编译器）。整个 lex → parse → sema → HIR → MIR → emit 管线 **100% 单线程**。

### 2.4 HIR desugar 用 thread-local RefCell 全局

**`compiler/src/codegen/hir.rs:58-75`**：

```rust
thread_local! {
    static IMPORT_RESOLUTION: RefCell<Option<ImportResolution>> = ...;
    static TYPE_NAMES: RefCell<Vec<String>> = ...;
    static SEMA_INFO: RefCell<Option<SemaInfo>> = ...;
    static CLASS_TABLE: RefCell<HashMap<String, ClassEntry>> = ...;
    static CLASS_CTX: RefCell<Option<ClassCtx>> = ...;
    static ACCESSOR_PROP: RefCell<Option<String>> = ...;
    static FUNCTION_PARAMS: RefCell<HashMap<String, Vec<HirParam>>> = ...;
    static INTERFACE_NAMES: RefCell<HashSet<String>> = ...;
    static ENUM_TABLE: RefCell<HashMap<String, Vec<String>>> = ...;
}
```

**9 个 thread-local RefCell** — 两个 desugarer 在同一进程内会竞争同一个 RefCell，**无法并行**。这是并行化的最大结构性障碍。

### 2.5 `&mut LowerCtx` 阻塞并行降级

`mir.rs:1284-1303` 的 `lower_program` 用共享 `&mut ctx` 遍历所有函数。即使去掉 clone，也需在 `LowerCtx` 上拆分可变状态才能并行。

### 2.6 HIR 优化通道全量树重建

`opt.rs:21-27`（`fold_hir`）、`opt.rs:237-277`（`inline_hir`）、`mono.rs:20-76`（`mono_hir`）全部 `&mut HirProgram` 原地重建整棵 `Box<HirExpr>` 树。3 个通道 = HIR 被重建 3 次。

`inline_hir` 对**每个**函数调用 `contains_lambda` / `calls_param_as_callee` / `expr_references`（`opt.rs:280-474`）—— 每个都是全树递归。

### 2.7 AOT emit 每指令一次 `format!`

`compiler/src/codegen/aot/emit.rs`（5168 行）中有 **426 处 `format!`** 和大量 `Vec<String>` 拼接。`BasicBlock { body: Vec<String> }`（`emit.rs:128`），最终 `to_string()` 再拼接一遍（`emit.rs:904-920`）。

### 2.8 Lexer 为整个源码构建 `Vec<(char, usize)>`

**`lexer.rs:135`**：

```rust
source.char_indices().map(|(idx, ch)| (ch, idx)).collect()
```

双倍内存 + 逐字符分配。对 1MB 源码即 100 万个小 tuple。

### 2.9 `lookup_keyword` 线性扫描

**`lexer.rs:104-111`**：遍历 ~70 条关键字数组。对每个标识符调用一次。O(n·K)，K≈70。

### 2.10 `resolve_aura_imports` 串行磁盘读，无缓存

**`codegen/mod.rs:253-319`**：递归 `std::fs::read_to_string` + `canonicalize`，每次编译重新执行。48 模块 = 48 次 syscall + 48 次字符串拼接。

### 2.11 `link_stdlib` 线性查找

**`link_stdlib.rs:81`** + **`resolve_stdlib.rs:62`**：`stdlib_exports.iter().find(...)` 每次调用一次 → O(calls × exports)。

### 2.12 Parser 的 `advance()` 克隆 Token

**`parser.rs:144-161`**：

```rust
fn advance(&mut self) -> Token {
    let tok = self.tokens[self.pos].clone();  // 每 token 一次 clone
    ...
}
```

且 `parse_expression`（`parser.rs:2458`）对每个复合赋值做 `lhs.clone()` — 深度树克隆。

### 2.13 JIT 现状（已修复）

`docs/JIT性能分析.md` 文档化的 Fix A/B 均已实现：

- **Fix A**（`vm/mod.rs:1234`）：入口函数 `force_jit_compile`
- **Fix B**（`vm/mod.rs:1435` + `jit.rs:174-178`）：`is_jit_compilable` 白名单已含 `Call`，递归编译被调者
- 实测 sum(60000): 58.8→0.51ms (**115×**)，fib(25): 243→2.67ms (**91×**)

### 2.14 各阶段瓶颈概览

| 阶段 | 文件:行 | 浪费类型 | 主导成本 | 可并行? |
|------|---------|----------|---------|---------|
| Lexer | `lexer.rs:135, 104` | 冗余分配 + 线性关键字扫描 | O(n·K) | 是（但 source 单一） |
| Parser | `parser.rs:147, 2458` | token clone + 深度 LHS clone | O(n) 大常数 | 是 |
| Sema | `checker.rs:4162` | re-lex + re-parse | 2× 前端 | 否 |
| `compile_source` | `codegen/mod.rs:167-214` | 丢弃首次解析 | 2× 前端 | 是 |
| HIR desugar | `hir.rs:58-75, 1135` | thread-local RefCell; Box 树重建 | O(n) 串行 | **否（结构性阻塞）** |
| mono_hir | `mono.rs:51, 75` | `orig.clone()` per 特化 | O(specs × fn size) | 是 |
| fold/inline | `opt.rs:21, 237` | 全量树重建 × 2 通道 | O(n) × 2 | 是 |
| MIR lower | `mir.rs:1269, 1284` | **`hir.clone()` per function** | O(N × HIR size) | 是 |
| AOT emit | `emit.rs:904-920` | 逐指令 String 分配 | O(instrs) 大常数 | 是 |
| resolve_imports | `codegen/mod.rs:234-320` | 串行磁盘读 | O(imports) I/O | 是 |
| link_stdlib | `link_stdlib.rs:81` | 线性 find | O(calls × exports) | 是 |

## 3. 自举编译器（aura/compiler/）

### 3.1 核心架构问题：编译器是「解释执行的解释器」

```
Aura 源码 ──→ Rust VM 解释执行 (~1µs/op)
                │
                └── Aura 编译器管线（Main.aura:150-198）
                    Parser → TypeChecker → HirLowerer → MirLowerer → Codegen → VmRunner
                    全部是 Aura 代码，在 Rust VM 上解释执行
```

README 结论：**「发射期成本本质是 Aura 编译器跑在 Rust 解释器上的执行速度」**。

### 3.2 并发设施现状

#### Aura 核心库的 Coroutine/Actor — 同步门面，非真正并发

`aura/core/aura/lang/coroutine/` 定义了协程和 Actor API，但实现是**同步门面**：

| 文件 | 行 | 实现 | 并发能力 |
|------|----|------|----------|
| `Coroutine.aura` | 36-44 | `spawn` 只存 closure 到 List | ❌ 不启动执行 |
| `Coroutine.aura` | 51-62 | `ask` **同步执行** `body()` | ❌ 无 yield/调度 |
| `Actor.aura` | 31-35 | `send` 只追加到 mailbox | ❌ 无处理循环 |
| `Actor.aura` | 39-41 | `reply` 直接返回 `null` | ❌ 注释"简化实现" |
| `Actor.aura` | 63-67 | `supervise` 空操作 | ❌ |
| `Actor.aura` | 88-95 | `recvProcessActor` 直接返回 `mailbox[0]` | ❌ 非阻塞 |

#### Rust VM 内部有并发基础设施，但未暴露给 Aura

| 设施 | 位置 | 功能 | Aura 可用? |
|------|------|------|-----------|
| `ThreadPool` | `vm/thread_pool.rs` | `thread::spawn` 工作线程池，默认 CPU 核心数 | ❌ 无 FFI 桥接 |
| `CoroutineScheduler` | `vm/coroutine.rs` | 绿色线程调度器，Ready/Suspended/Done 状态机 | ❌ Aura 的 `Coroutine.spawn` 调用的是自己的同步实现 |
| `Yield`/`ResumeCoroutine` 指令 | `vm/mod.rs:265,267` | 字节码指令，支持协程挂起/恢复 | ❌ 编译器管线不使用 |
| `VM_STACK`（thread_local） | `vm/native.rs:612` | 允许多个 VM 实例并存 | ❌ 编译器管线未利用 |
| `Process.spawn` | `std_process.rs:77` | OS 子进程 `std::process::Command::spawn` | ✅ 但这是子进程，不是线程 |

#### 自举编译器内的并发文件 — 全部 phantom

| 文件 | 状态 |
|------|------|
| `aura/compiler/.../runtime/Coroutine.aura` | 37 行，`version = "0.5.0-phase4-phantom"`，`start` 仅设 state |
| `aura/compiler/.../gc/Gc.aura` | phantom，`malloc` 返回 `null` |
| `aura/compiler/.../gc/MarkSweep.aura` | phantom |
| `aura/compiler/.../gc/Concurrent.aura` | phantom，`start` 仅设 `state["running"] = true` |
| `aura/compiler/.../gc/Incremental.aura` | phantom |
| `aura/compiler/.../memory/*.aura` | 单方法存根 |

#### 即使暴露并发设施，编译器管线仍无法并行

三个结构性障碍（与 Rust 编译器相同）：

1. **thread-local RefCell 全局**（`hir.rs:58-75`）— 两个 desugarer 竞争同一 RefCell
2. **`&mut HirProgram` 可变引用** — 优化通道原地修改，无法并行
3. **`&mut LowerCtx` 共享** — 降级上下文可变，无法并行

#### 让自举编译器用多核需要什么

| 方案 | 工作 | 预期 |
|------|------|------|
| **暴露 ThreadPool** | 新增 `Thread.spawn` FFI 桥接 + 线程安全重构 | 能，但需 9 个 RefCell → 显式 Context |
| **绿色线程（协程）** | 利用已有 `Yield`/`ResumeCoroutine` | 仍单核（除非配合 ThreadPool） |
| **Rust 编译器用 rayon** | 最实际的方案（见 §4.1 R3） | 4–8× 多核 |

### 3.3 VM 数据结构全是字符串 → O(n²)

`vm/VmRunner.aura` 的每一个核心结构都是 `String`：

| 结构 | 位置 | 操作 | 复杂度 |
|------|------|------|--------|
| `stack: String` | `:161` | `push = stack + value + "\n"` | 每 push O(n)，总计 O(n²) |
| `pop` | `:166-185` | 从末尾扫描 + `stackSlice` | O(n) |
| `locals: String` | `:218-241` | `setLocal` = `localsRemoveSlot` + 拼接 | O(n) per set |
| `getLocal` | `:199-215` | 线性扫描整串找槽位 | O(n) per load |
| `bytecode: String` | `:734-755` | `getBytecodeLine` 从位置 0 扫描到 `ip` | **每指令 O(ip)，总计 O(N²)** |
| `dispatch` | `:312-433` | 30 行 `if (opcode == "CONST_INT") { ... }` 链 | 每指令 30 次字符串比较 |
| `parseOpcode/Arg1/Arg2/Arg3` | `:758-843` | 4 次独立 char-scan 循环 | 每指令 4 次扫描 |
| `stackSlice` | `:892-904` | 逐字符 `String +=` | O(n) per slice |
| `callOrBuiltin` | `:464-465` | `savedLocals = savedLocals + locals + "\u0001"` | 每次调用复制整个 locals 表 |
| `funcOffset` | `:514-528` | 线性扫描整个 funcTable | O(funcTable) per CALL |
| `funcParamCount` | `:532-547` | 线性扫描整个 funcTable | O(funcTable) per CALL |
| `fieldAtRow` | `:915-935` | 从头扫描找分隔符 | O(n) per call |
| `fieldAtCol` | `:938-958` | 从头扫描找分隔符 | O(n) per call |
| `vrToInt` | `:967-990` | 嵌套循环（10 次字符串比较 per digit） | 10× per digit |

### 3.4 HIR 已修复，MIR 未修复

- ✅ `hir/Hir.aura:50-81`：已改为 `List<String>` / `List<Int>` 堆列表，`Hir.add` 摊还 O(1)
- ❌ `mir/Mir.aura:66-90`：**仍是 `String +=`**，5 条 arena 流每节点各一次拼接 → O(n²)
- ❌ `codegen/Codegen.aura:47-69`：`bytecode`、`constPool`、`varTable`、`funcTable` 全用 `String +=`
- ⚠️ `codegen/Codegen.aura:310-354`：`lookupConst` / `lookupVar` 每次线性扫描

### 3.5 AOT Emit — 部分修复

`aot/Emit.aura`（3884 行）的累积器已改用 `EmitBuffer`（`EmitBuffer.aura:32-51`，native `StringBuilder` 包装），但所有查找函数（`structFieldIndex`、`funcSignatureOf`、`fvField`、`inferType` 等）仍是线性扫描。

### 3.6 JIT 是第二个解释器

`jit/JitCore.aura:354-449` 的 `jitCoreExecute` 调用 `JitCoreVm.run` — **又是 Aura 手写的解释器**，同样用字符串栈和线性分派。文件头自承：「机器码后端位于 Rust `vm::jit`；本层保持零外部依赖」。

## 4. 优化建议汇总

### 4.1 Rust 编译器（compiler/）— 预期 4–8× 多核 + 2× 去冗余

| # | 建议 | 位置 | 预期收益 | 风险 |
|---|------|------|---------|------|
| **R1** | 去掉 `compile_source` 的重复 lex+parse：已有 AST，直接传给 sema；或让 `analyze_source` 接受预解析的 `Program` | `codegen/mod.rs:167-214` | ~1.6–2× | 低（纯重构） |
| **R2** | 去掉 `lower_function` 的 `hir.clone()`：改为传 `&HirProgram` 引用 | `mir.rs:1269` | ~2–4× | 低（改一行 + 类型调整） |
| **R3** | 引入 rayon 并行化 `lower_program` / `fold_hir` / `inline_hir` / `mono_hir`；需先把 9 个 thread-local RefCell 提取为显式的 `DesugarContext` 结构体 | `hir.rs:58-75` + `mir.rs:1284` + `opt.rs:22,270` + `mono.rs:76` | ~3–6× 多核 | 中（需重构 RefCell） |
| **R4** | AOT emit 改用单一 `String` + `write!`：替代 `Vec<String>` + 逐指令 `format!` | `emit.rs:128, 904-920` | ~1.3–2× AOT | 中（机械重构） |
| **R5** | `resolve_aura_imports` 缓存 + 消除 `embed_into_auc` 第三遍前端 | `codegen/mod.rs:234-320` + `cli/main.rs:211-253` | ~1.1–1.5× | 低 |
| **R6** | Lexer 去掉 `Vec<(char, usize)>` 中间表示；`lookup_keyword` 改用 `BTreeMap` 或二分 | `lexer.rs:135, 104` | ~1.1× | 低 |
| **R7** | `link_stdlib` / `resolve_stdlib` 的 `iter().find()` 改为 `HashMap` | `link_stdlib.rs:81` + `resolve_stdlib.rs:62` | 小幅 | 低 |
| **R8** | Parser 的 `advance()` 改为返回引用而非 clone；消除 `parse_expression` 的 `lhs.clone()` | `parser.rs:147, 2458` | ~1.1× | 低 |

**建议执行顺序**：R1 → R2 → R3。R1+R2 可在不引入依赖的前提下独立落地，预期 2–4×；R3 引入 rayon 后预期再 3–6×。

### 4.2 自举编译器（aura/compiler/）— 三层优化

#### 第一层：VM 核心（`vm/VmRunner.aura`）→ 预期 5–20×

| # | 改动 | 位置 | 当前复杂度 | 目标 | 预期收益 | 改动量 |
|---|------|------|-----------|------|---------|--------|
| **V1** | `stackSlice` → `String.substring` | `:892-904` | O(n²) per call | O(n) per call | **5–20× 全局** | ~5 行 |
| **V2** | `getBytecodeLine` 预计算行偏移表 | `:734-755` | O(N²) 总计 | O(N) 总计 | **5–10× VM** | ~30 行 |
| **V3** | VM 栈 → `List<String>` | `:161-185` | O(n²) | O(n) | **5–10× VM** | ~20 行 |
| **V4** | `setLocal`/`getLocal` → `List<String>` | `:199-241` | O(n) per call | O(1) | **3–5× VM** | ~30 行 |
| **V5** | `parseLine` 单次解析 | `:758-843` | 4×O(len) per instr | 1×O(len) | **3–4× VM** | ~20 行 |
| **V6** | `dispatch` 改 `else if` 链 | `:312-433` | 30× per instr | ~3× avg | **3× VM** | 改关键字 |
| **V7** | `vrToInt` 数字解析简化 | `:967-990` | 10× per digit | 1–3× | **2–3×** | ~15 行 |
| **V8** | `funcOffset`/`funcParamCount` 预计算映射 | `:514-547` | O(funcTable) per CALL | O(1) | **2–3×** | ~20 行 |

#### 第二层：编译器各阶段 → 预期 5–20×

| # | 改动 | 位置 | 当前复杂度 | 目标 | 预期收益 | 改动量 |
|---|------|------|-----------|------|---------|--------|
| **C1** | `Mir.aura` → `List<String>`/`List<Int>`（照抄 Hir.aura 修复模式） | `Mir.aura:66-90` | O(N²) | O(N) | **5–20× MIR** | ~50 行 |
| **C2** | `Codegen.aura` 累积器 → `EmitBuffer`/`List` | `Codegen.aura:47-69` | O(N²) | O(N) | **5–20× Codegen** | ~40 行 |
| **C3** | `Codegen.aura` `lookupConst`/`lookupVar` 优化 | `Codegen.aura:310-354` | O(n) per call | O(1) | **2–3×** | ~20 行 |

#### 第三层：架构突破 → 预期 100–1000×

1. 类类型值必须按引用传递（`i8*`/`%struct.X*`），而非 `%struct.X` 值拷贝
