## 2. 性能基准结果

### 2.1 编译器自举编译（编译 Main.aura → AOT 可执行文件）

> 测试日期：2026-09-18
> 目标：`aura/compiler/aura/lang/compiler/Main.aura`
> 模式：AOT（Ahead-of-Time），含 HIR → LLVM IR → llc → link 全流程

| 编译器 | 冷编译 | 热编译 | 热编译(2) | 缓存加速 | 备注 |
|--------|--------|--------|-----------|---------|------|
| Rust (`aura.exe`) | **6.57s** | **6.45s** | **6.37s** | 1.8% | .auc 缓存收益极低 |
| Aura (`aura-compiler.exe`) | **45.11s** | **45.06s** | **44.87s** | 0.1% | .auc 缓存收益极低 |

**关键发现：**

1. **Rust 比 Aura 快 ~6.9x**：冷编译 6.57s vs 45.11s，热编译 6.45s vs 45.06s
2. **缓存几乎无效**：两种编译器的冷/热差异都 <2%，说明瓶颈不在字节码编译阶段
3. **瓶颈在 AOT 阶段**：`.auc` 缓存只加速字节码编译，而 AOT（HIR→IR→llc→link）占总耗时的 95%+
4. **Aura 编译器开销**：Aura 自举编译器每次都要执行完整的 HIR→IR 发射（Emit.aura），
   而 Rust 编译器可直接复用缓存的中间表示

## 5. 结论

### 已实现优化（7 项）

| 优化 | 类型 | 收益 |
|------|------|------|
| A1: HashMap | 数据结构 | 减少查找耗时 |
| A2: ArrayList | 数据结构 | 减少拼接耗时 |
| A3: 合并 verify | 进程优化 | 减少 1 次进程启动 |
| B1: 文件缓存 | I/O 优化 | 消除重复读取 |
| R1: 合并 verify | 进程优化 | 减少 1 次进程启动 |
| R2: C FFI 缓存 | I/O 优化 | 跳过不变文件重编 |
| **R4: rayon 并行** | **多核并行** | **0.91→0.20s (78%)** |

### 多核编译优化

- **Stdlib 编译**：12 核 rayon 并行，4.55x 加速
- **Aura 编译器**：受限于 Aura 并发原语（Thread.spawn AOT 不兼容），暂无法并行
- **Rust 编译器**：已通过 rayon 实现并行，后续可扩展到 pass 级并行

### 自举编译瓶颈分析（2026-09-18 新增）

| 阶段 | Rust 耗时 | Aura 耗时 | 占比 | 优化方向 |
|------|-----------|-----------|------|---------|
| 字节码编译 (Lexer→Parser→VM) | ~0.2s | ~0.5s | <2% | .auc 缓存已覆盖 |
| HIR → LLVM IR 发射 | ~2.0s | ~25.0s | ~55% | Emit.aura 优化 |
| llc 编译 (IR→x64) | ~3.5s | ~15.0s | ~40% | 外部工具，不可控 |
| 链接 (lld-link) | ~0.5s | ~2.0s | ~5% | C FFI 缓存 |
| **总计** | **~6.5s** | **~45s** | **100%** | |

**结论：**
1. **AOT 发射是主要瓶颈**：Aura 的 Emit.aura 占 ~55% 耗时，远超 Rust 的同等阶段
2. **llc 是第二大瓶颈**：两种编译器都依赖外部 llc，无法通过编译器优化消除
3. **缓存收益有限**：.auc 缓存只加速字节码阶段，AOT 阶段无缓存复用
4. **优化方向**：
   - Emit.aura 发射优化（减少 IR 冗余、避免重复计算）
   - HIR 增量编译（只重新发射变更的函数）
   - llc 并行编译（多目标文件并行处理）
